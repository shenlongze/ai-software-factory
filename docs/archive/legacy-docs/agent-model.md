# Agent 模型 (agent-model)

## 1. 核心概念

**Agent(执行单元)** 是工厂中承担一项专业工作的最小执行主体。一个 Agent 实例 =
**角色(Role)** + **技能(Skill)** + **一次委派(Delegation)**。

```
Agent 实例 = Role(职责边界) + Skill(操作知识) + Delegation(任务上下文)
```

- **Role**: 定义"做什么、不做什么、产出什么",决定职责边界。角色是静态的、注册在角色注册表中。
- **Skill**: 定义"怎么做的知识",决定操作方法。角色与 Skill 一对一绑定(一个角色对应一个主 Skill)。
- **Delegation**: 一次具体的任务委派,定义"这一次做什么",携带 goal / context / 文件范围 / 验证要求。

三者缺一不可:有 Skill 无 Role 会越界(工程师去定架构);有 Role 无 Skill 会不知道怎么做;
无 Delegation 就没有任务边界,无法验证。

**两个主体**:

| 主体 | 职责 |
|:-----|:-----|
| 协调器 Orchestrator | 拆解任务、委派 Agent、独立验证结果、推进流程、裁决冲突。**不亲自执行专业工作**。 |
| Agent | 按委派与 Skill 执行专业工作,产出工件 + 自报告。**不自我验收,不越界**。 |

## 2. 角色定义方式

角色 = **职责边界声明**。每个角色在注册表中声明三类内容:

```yaml
role:
  name: 开发工程师            # 角色名
  skill: development          # 绑定的主 Skill 标识
  scope:                      # 做什么
    - 按委派实现代码修改
    - 本地构建验证(调试构建)
  outputs:                    # 产出物
    - 修改后的文件
    - 变更摘要
  forbidden:                  # 禁止(边界)
    - 不定义架构方案
    - 不修改测试基线文件
    - 不执行发布构建
  verify: independent         # 验证责任:不自验,由协调器/测试角色独立验证
```

**边界铁律(实证教训)**:职责边界一旦被突破(如协调器亲自写代码、开发角色自行宣布测试通过),
轻则产出无效,重则破坏流程可信度。边界违反必须记录并回滚重派。

### 2.1 基准角色注册表(实证验证过的六个角色)

| 角色 | 主 Skill | 产出 | 禁止 |
|:-----|:---------|:-----|:-----|
| 产品经理 product-manager | 需求/验收标准定义 | 验收标准、用户需求、期望行为 | 不决定技术方案 |
| 架构师 architecture | 架构审计 | 根因分析、设计决策、推荐改动方案 | 不提交代码 |
| 开发工程师 development | 代码实现 | 实现代码、变更文件清单 | 不定义架构、不自我验收 |
| 测试工程师 testing | 测试与验证 | 测试用例、验证结果、回归状态 | 不修改生产代码 |
| 调试工程师 debugging | 根因调查 | 事件链、根因结论、修复建议 | 不直接改代码(修复由开发执行) |
| 发布验证 release-validation | 构建/打包/安装验证 | 构建产物、安装验证报告 | 不判断业务正确性 |

> 这六个角色覆盖一条完整生产流水线;更多角色按第 4 节接口新增。

## 3. Agent 生命周期

Agent 实例从创建到归档共 7 个状态。**每个状态转换都要写事件记录**(谁、何时、什么、证据),
这是事后审计与指标(first_attempt_success 等)的数据来源。

```
Created → Assigned → Working ⇄ Waiting → Validation → Completed → Memory Update
                          │
                          └→ Failed(由协调器按失败策略处理:重派/换法/上报)
```

| 状态 | 进入条件 | 记录什么 |
|:-----|:---------|:---------|
| **Created** | 协调器拆解任务,生成委派规范 | 任务 ID、目标、角色、创建时间 |
| **Assigned** | 委派发出(携带 goal/context/role/文件范围/验证要求) | 委派参数快照(目标、文件范围、验证要求) |
| **Working** | Agent 开始执行 | 关键步骤进展、中间产物、遇到的环境/路径问题 |
| **Waiting** | 阻塞(缺信息、缺授权、API 故障、依赖未就绪) | 阻塞原因、等待对象、恢复条件 |
| **Validation** | Agent 提交自报告 | 自报告全文、验证证据(文件存在/命令输出)、验证结论 |
| **Completed** | 协调器独立验证通过 | 验收证据、结果摘要 |
| **Memory Update** | 完成后沉淀 | 经验教训、新 pitfall、Skill 修补建议(见 skill-model) |

**Failed 分支规则(两次失败上限)**:

| 失败次数 | 动作 |
|:--------:|:-----|
| 第 1 次 | 同一 Agent 修复(补齐缺陷) |
| 第 2 次 | 更换方法:先做只读分析(事件链/数据流追踪),再重新设计后重派 |
| 第 3 次 | **禁止再试**。升级为阻塞,交由人类决策。 |

**Waiting 的特殊情形**:
- 基础设施类故障(超时/服务不可用/余额不足):按指数退避重试(1s→2s→4s…封顶 30s,最多 3 次),仍失败则转阻塞,不盲目重派。
- 任务被中断(会话中断/迭代上限):**必须先做状态恢复检查**(读 Agent 的中断自报 + 检查工作区实际状态),从中间态继续,禁止从头重派导致重复修改。

## 4. 角色注册表设计

角色注册表是"工厂有哪些角色"的权威清单。建议以 `roles/` 目录组织,每角色一个文件:

```
roles/
  product-manager.md
  architecture.md
  development.md
  testing.md
  debugging.md
  release-validation.md
  README.md            # 注册表索引:角色速查表 + 新增指引
```

每个角色文件的元数据字段(与 2.1 表一致):

| 字段 | 必填 | 说明 |
|:-----|:----:|:-----|
| name | ✅ | 角色标识,全局唯一 |
| skill | ✅ | 绑定的主 Skill 标识(须已在 Skill 注册表) |
| description | ✅ | 一句话职责描述(用于委派匹配) |
| scope / outputs / forbidden | ✅ | 职责边界三要素 |
| verify | ✅ | 验证责任声明(independent / n/a) |
| use_cases | 建议 | 适用场景与不适场景,防止误派 |

### 4.1 新增角色接口(5 步)

1. **起草**:按上述元数据模板填写 `roles/<name>.md`,scope/forbidden 必须具体到可判定。
2. **登记 Skill**:若需新操作知识,先在 Skill 注册表新增对应 Skill(见 skill-model),角色文件引用其标识。
3. **评审**:由协调器对照现有角色检查职责重叠(是否侵蚀已有角色边界)、检查 forbidden 是否覆盖已知事故模式。
4. **注册**:写入注册表索引 README,角色可被委派。
5. **试用沉淀**:首个任务结束后,把实际暴露的边界歧义回写角色文件(禁止项只增不减)。

**撤销角色**:从索引移除,标记 `deprecated`;已有任务完成前不销毁,已归档事件保留。

## 5. 调用方式:委派规范 (Delegation Spec)

每次委派必须携带以下参数。**参数缺失是路径错误、越界修改、假报告等事故的第一来源。**

```yaml
delegation:
  goal:        # 目标:一句话,可验收(必须)
  role:        # 角色标识(必须)
  context:     # 上下文:项目根路径、架构约束、关键代码位置(必须)
  files:       # 文件范围:allowed(必须) / forbidden(必须) / expected 新文件(必须)
  validation:  # 验证要求:验证命令或验证级别 L1/L2/L3(必须,见 validation-model)
  constraints: # 约束:禁止命令、语言偏好、禁止触碰的模块(必须)
```

**四项硬性文件规则(实证:路径错误曾占失败 50%)**:

1. **绝对路径**:context 开头必须给项目根路径与工作目录的绝对路径,并声明"写入路径必须是 <root>/<file>"。
2. **Allowed Files**:允许修改/新建的文件清单(新建文件标注 `(new)`)。
3. **Forbidden Files**:禁止触碰的清单(如测试基线文件、工厂自身基础设施)。
4. **禁止破坏性命令**:委派中明示禁止 `git checkout / restore / reset / clean` 等会销毁他人工作区改动的命令。

### 5.1 Agent 自报告格式

Agent 完成时提交结构化自报告,作为验证环节的输入(不等于事实,详见 validation-model):

```markdown
## 自报告
任务: <delegation.goal>
完成项: 1. … 2. …        # 逐条,与 goal 对应
文件变更: <路径> → 新建/修改
验证已运行: <命令 + 输出摘要>   # 未运行的必须如实写"未运行"
未完成/风险: …                 # 诚实声明部分状态,禁止隐瞒
```

**诚实原则**:被截断/中断的 Agent 必须报告"哪些没做、哪些没验证";"验证未运行"一律按未验证处理,由协调器补验。

## 6. 角色边界与流程衔接(小结)

- 协调器只做:拆解 → 委派 → 独立验证 → 汇总 → 裁决 → 推进。**任何专业工作必须走注册角色**。
- 开发角色完成 ≠ 任务完成;必须经独立验证(validation-model 的双验证机制)。
- 三个暂停挡板(产品方向冲突 / 架构变更 / Scope 扩展)出现时,流程必须停在决策门,见 workflow-model。
- 角色只增不减边界,新增角色不得侵蚀既有角色 forbidden 项。
