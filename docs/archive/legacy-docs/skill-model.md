# Skill 模型 (skill-model)

> 状态: DESIGN ONLY (蓝图, 未实现或部分实现: Core 有基础 Registry/CLI, Skill 未进执行流程 — 见 ./audit/architecture-reality-audit.md)

> 通用 AI Software Factory 的 Skill 定义。Skill 是工厂的**程序性记忆**:把"某类任务怎么
> 做、有哪些坑、怎么验证"编码为可加载、可复用、可维护的知识单元。Agent 凭 Role 决定
> 做什么,凭 Skill 决定怎么做。本模型从 Hermes + MarkPad 实践归纳,与具体工具无关。

---

## 1. 核心概念

- **Skill = 一个知识单元**,对应"一类任务"的完整操作方法,而不是一个命令或一段提示词。
- 一个角色绑定一个主 Skill(agent-model §2);复杂 Skill 可引用附属文件(参考/模板/脚本)。
- Skill 与 Agent 解耦:同一 Skill 可被多个 Agent 加载,同一 Agent 在不同任务加载不同 Skill。
- **Skill 是活的**:使用中发现过时、缺步骤、有坑,必须当场修补(见 §4),不允许带病复用。

---

## 2. Skill 结构

一个 Skill 是 `skills/<category>/<name>/` 目录,内含 `SKILL.md` 主文件与可选附属文件:

```
skills/
  software-development/
    development/
      SKILL.md                    # 主文件(必填)
      references/xxx.md           # 可选:深入参考、模式库、真实案例
      templates/plan.md           # 可选:可复用模板
      scripts/verify.sh           # 可选:可执行验证脚本
```

### 2.1 SKILL.md 五段式结构

| 段 | 内容 | 要求 |
|:---|:-----|:-----|
| **frontmatter** | `name` / `category` / `description` / `trigger` | description 一句话说清"何时用",trigger 写清触发场景,两者是加载匹配的依据 |
| **触发条件** | 明确"什么任务必须加载本 Skill" | 与 trigger 呼应,写成可判定的 if-then |
| **步骤** | 编号的分步操作(1. 2. 3. …) | 每步可执行、含精确命令/参数;关键步骤标注出口条件 |
| **pitfalls** | 已知坑与对应解法(实证事故) | 每条 = 现象 + 原因 + 预防/检测/恢复 |
| **验证** | 任务完成的验证门(命令/检查项) | 必须可独立执行,供协调器二次验证复用 |

### 2.2 frontmatter 字段规范

```yaml
---
name: development          # 全局唯一,小写连字符
category: software-development
description: >            # 一句话:本 Skill 做什么、何时用(匹配依据)
  按委派实现代码修改,遵守文件范围与验证要求…
trigger: |                # 触发场景:出现以下情形必须加载
  当任务需要修改代码实现功能时…
---
```

**好 description 的标准**:让"任务匹配器"只凭 description 就能判断该不该加载本 Skill。
写"何时用"而非"是什么"(如"当需要修改代码时" ✅,而非"软件开发技能" ❌)。

### 2.3 步骤段规范

- 编号步骤,长任务允许小节(阶段)分组。
- 每步给出**可执行动作**与**出口条件**(做完这步如何知道对了)。
- 禁止含糊动词("适当修改""合理优化"),改写成可判定动作("修改 <文件> 的 <符号>,使 <行为> 成立")。
- 需要并行/可跳过/必须等待依赖的步骤显式标注。

### 2.4 pitfalls 段规范(实证知识密度最高的部分)

每条 pitfall 用统一模板:

```markdown
### <坑名>
现象: 发生了什么(证据:报错/行为异常)
原因: 根因
预防: 如何避免
检测: 如何快速发现(命令/检查)
恢复: 已发生时如何处置
```

真实来源示例(可抽象化后收录):
- **路径漂移**:Agent 声称创建了文件,实际写到了临时目录 —— 检测:在预期绝对路径检查文件存在。
- **假通过**:Agent 自报"测试通过",实际未运行或运行的是无关用例 —— 检测:协调器独立重跑验证命令。
- **自验无效**:开发者自行验证自己的修改,测试者修改生产代码 —— 边界规则,见 agent-model。
- **破坏性回滚**:执行 git checkout/reset 清掉了他人工作区改动 —— 委派中明示禁止。
- **验证命令的误报陷阱**:用带行号前缀的文本匹配做断言会误判 —— 验证用精确匹配(grep/命令退出码),不用格式化后的阅读视图。

## 3. 加载机制(匹配 → 加载 → 应用)

### 3.1 匹配(Match)

协调器拿到任务后,在 Skill 注册表中检索:

1. **语义匹配**:用任务目标/关键词对比每个 Skill 的 `description`,候选集合。
2. **触发条件命中**:候选 Skill 的 `trigger` 与任务类型逐条比对,确定唯一命中的 Skill。
3. **角色约束**:任务委派了角色,则只在该角色绑定 Skill 集合内匹配(防止"测试任务加载了开发 Skill")。

无命中 → 任务可能超出既有能力,按"新增角色接口"(agent-model §4.1)先补 Skill 再执行,
禁止用"通用做法"硬套(实证:跳过专业 Skill 直接执行是流程事故 E1 级)。

### 3.2 加载(Load)

- 读取 `SKILL.md` 全文注入任务上下文;必要时按需加载 `references/` 附属文件(不是全量读取,避免上下文膨胀)。
- **加载顺序纪律**:Skill 内容在委派 context 中的位置靠后,文件范围/绝对路径/语言偏好必须在其之前(实证:路径规则被架构描述淹没时,路径错误率回升)。
- 模板/脚本类附属文件直接可执行,不要求 Agent 重述。

### 3.3 应用(Apply)

- Agent 按 SKILL.md 步骤顺序执行,将步骤与委派 goal 对齐;步骤与任务不符时**记录偏差及理由**,不许静默跳过。
- 每步出口条件满足才进入下一步;步骤失败走 agent-model 的失败策略(1 修复 / 2 换法 / 3 上报)。
- 执行结束按 SKILL.md 的"验证"段自验,然后按 agent-model §5.1 提交自报告。

## 4. 复用与维护

Skill 是工厂资产,**维护即生产**。三种维护动作:

| 动作 | 时机 | 说明 |
|:-----|:-----|:-----|
| **patch(增量修补)** | 默认动作。使用中发现步骤缺失、命令过时、新 pitfall,当场修 | 小范围 old/new 替换,只改缺陷部分 |
| **edit(整体重写)** | 结构性过时:流程彻底变化、适用范围变更 | 重写全文,保留仍有效的 pitfalls |
| **delete(废弃)** | 不再使用/被合并 | 标记 `absorbed_into=<新技能名>` 指向承接者,防止引用断裂 |

### 4.1 强制维护触发点(实证规则)

- 使用本 Skill 时踩到未记录的坑 → 当场补一条 pitfall(记录到坑比任务完成更重要)。
- Skill 中的命令/路径/版本已失效 → 立即 patch。
- 任务结果证明 Skill 的步骤顺序有缺陷 → patch 调整并注明事故编号。
- Skill 被废弃合并 → 先创建/修补承接 Skill,再 delete 原 Skill,并更新引用它的角色注册表。

### 4.2 版本与审计

- 每次 patch 在文件内记录一行变更说明(`<!-- 2026-08: +pitfall: 路径漂移 -->` 或 changelog 段),
  便于回溯"这条教训是哪个事故来的"。
- 定期(如每 N 个任务)按"最近使用/最近修改"清单审一遍注册表,清理从未命中的 Skill。

## 5. Skill 注册表设计

注册表是"工厂有哪些知识"的索引,供匹配器与维护者使用:

```
skills/
  <category>/<name>/SKILL.md      # 技能本体(分散在各分类目录)
  README.md                       # 索引:技能速查表(name × description × 绑定角色)
```

索引行字段:

| 字段 | 说明 |
|:-----|:-----|
| name | 技能标识 |
| category | 分类(软件工程/测试/发布/产品…) |
| description | 匹配用一句话 |
| binds_role | 绑定的角色(可为空:通用技能) |
| updated | 最近维护时间 |
| status | active / deprecated |

**维护规则**:
- 新增 Skill 走"草拟 → 登记 → 试用 → 沉淀"(与新增角色接口对应,先有 Skill 后有角色绑定)。
- description 变更必须同步更新索引 README,否则匹配器找不到。
- 索引 README 是唯一权威清单;目录里存在但索引没有的 Skill 视为未注册,不可被委派加载。

## 6. 好 Skill 的质量标准(自查清单)

- [ ] frontmatter 的 description/trigger 可判定、无歧义
- [ ] 步骤编号、可执行、含出口条件
- [ ] pitfalls 按"现象/原因/预防/检测/恢复"模板,至少覆盖本领域已发生事故
- [ ] 验证段可被协调器独立执行(不依赖 Agent 自报)
- [ ] 使用中的每个新教训都已回写
