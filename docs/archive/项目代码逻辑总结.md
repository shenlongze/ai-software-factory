# AI Software Factory — 项目代码逻辑全景总结

> 扫描方式: 全量静态阅读核心模块 + 实测 CLI 运行 (init/skill/workflow/org/mcp/demo)
> 扫描时间: 2026-08-11

---

## 一、总体架构逻辑

**四层单向依赖**架构,一个 CLI (`factory`, 91 个命令 / 25 命令组) 驱动全部能力:

```
factory-console/  Human Console 人类审核台 (FastAPI 59 路由 + React 页面)
        │ 只读聚合 (依赖向下)
intelligence/     决策/推荐/经验 (规则驱动, 只读复用 events+product)
        │ 事件 + 只读复用
product/ providers/ git/ change/ changeflow/ understanding/  (Extension 声明式注册)
        │ 只 import events
events/ tasks/ workflows/ execution/ runtime/ agents/ assignment/  (Core 冻结原语)
orchestration/ recovery/ validation/ metrics/ dashboard/ workspace/ project/
```

核心设计逻辑:**事件是唯一事实源**。所有业务动作发事件 (append-only SQLite, 双层防改: 应用层无 update/delete 方法 + 数据库层 BEFORE UPDATE/DELETE 触发器物理拒绝), 状态可回放、可审计、可恢复。

## 二、Core 冻结层 (factory-core, 33,814 行)

### 1. events/ — 事件溯源地基
- `EventStore`: SQLite append-only, WAL 模式, 单连接+RLock 线程安全
- 语义列: `seq/type/source/project_id/task_id/agent_id/stage/action/result/evidence/payload`
- 索引: task/agent/project/type/ts 五维
- 纠错模式: 以"补发新事件"纠正, 绝不改写旧事件

### 2. tasks/ — 任务模型 (最薄, 216 行)
- 五状态: BACKLOG → ARCHITECTURE → DEVELOPMENT → TESTING → DONE
- Task = Pydantic 模型, JSON 文件持久化, id 即文件名 (防路径注入校验)

### 3. workflows/ — 工作流引擎
- `WorkflowEngine`: 定义管理 (create/list) + 运行管理 (start/step 推进/execute/fail)
- 状态机: Workflow: CREATED/RUNNING/COMPLETED/FAILED; Step: PENDING/RUNNING/COMPLETED/FAILED
- 关键: `execute_step` 产生 `ExecutionRequest` 交接给 Runtime (分层解耦)
- `_resolve_agent_id`: 按 role/skill 从 AgentRegistry 找执行者

### 4. execution/ — 执行分发 (薄, 497 行)
- `ExecutionDispatcher`: `resolve_runtime_id` (显式 → 首个 AVAILABLE → 报错) → `get_adapter` → `adapter.execute(request)` → 校验结果绑定本请求
- `ExecutionRunner`: 执行记录管理, 结果按 request_id 绑定校验 (契约违反即抛错)

### 5. runtime/ — 运行时注册表
- `RuntimeRegistry`: hermes/echo/mock 内建定义 + 用户注册
- `RuntimeAdapter` 协议: echo/hermes 两个实现; 冒烟测试可验证

### 6. orchestration/ — 工作流自动编排器 (核心组装层)
- `OrchestrationEngine.execute_workflow(task_id)`: **完整链路装配**
  `ensure_run → 循环: next_pending_step → 匹配 Agent → 分配 → 执行 → 结果 → 推进 → 直至 COMPLETED/FAILED`
- 失败语义: 任一步失败 → fail_workflow (Workflow FAILED, 无半完成) + orchestration.failed
- 实测: 补全 agent + runtime 后 4 步 workflow 全部 COMPLETED, agent 用完正确释放

### 7. recovery/ — 断点续跑
- `checkpoint(task_id)` → `recover(task_id)`: 事件回放重建 + 状态纠正
- CheckpointStore: 停靠点快照

### 8. agents/ + assignment/ — 智能体与分配
- `AgentRegistry`: 注册/查找 (find_by_skill)
- `AgentAllocator`: 分配/释放 Agent (assignment.* 事件)

### 9. validation/ — 三层验证
- `ValidationEngine.validate`: L1/L2/L3 验证引擎 (任务验收)

### 10. metrics/ + dashboard/ — 观测
- 六域指标聚合 + Dashboard 20 视图 (Rich 渲染)

## 三、Extension 层 (factory-core 内, 声明式注册, 零 Core 破坏)

### 1. providers/ — LLM Provider 抽象 (3,213 行)
- `ProviderDefinition`/`ProviderRequest`/`ProviderResponse` 契约
- `CostAwareSelector.recommend`: 四因素可解释评分 (Capability/Cost/Performance/Experience, 权重 0.35/0.30/0.20/0.15)
- Adapter: hermes (真实) + mock; `provider test` 冒烟
- `ProviderRegistry`: 默认 hermes + 注册定义

### 2. product/ — Product Intelligence (4,063 行, 最大 Extension)
- **生命周期引擎** `ProductLifecycleEngine`: `start_lifecycle` → `advance` 逐阶段推进 8 阶段链 (idea→research→prd→approval→ui→approval→architecture→task)
- 审批门: mandatory 门自动申请 → 人工 decide → 联动推进
- 决策链: product → architecture → task_plan, source_artifact 引用完整
- `ProductGenerator`: TaskRequirement → CostAwareSelector → ProviderAdapter 生成 Artifact
- Experience Store: 成功/失败/审批经验记录

### 3. understanding/ — 项目理解 (1,233 行)
- `UnderstandingService.analyze(path)`: 阶段识别/产物检测/缺失分析/建议
- 只读规则分析, 禁 LLM

### 4. git/ + change/ + changeflow/ — 变更智能
- GitService: status/diff/commits 只读查询 (Git 可选, 零硬依赖)
- ChangeService: 提交-任务关联/路径分析/L4 验证
- ChangeFlowEngine: trigger 注册 → evaluate → workflow 联动

## 四、Intelligence 层 (factory-core/intelligence, 3,549 行)

- **决策链**: `DecisionIntelligence.analyze` (证据校验+因素聚合+置信度) → `evaluate_options` (逐选项评分) → `recommend` (四因素+风险) → 决策产物

## 六、单 Agent 执行引擎 (factory-exec/exec, 24,895 行 — 最重模块)

### 完整执行流水线 (T1-T5)
```
ExecutionRequest → ContextAssembler (上下文装配)
  → RankingEngine (文件排名/推荐, TopK 选择)
  → DeveloperAgent (Prompt 构建 + LLM 生成 patch/operations)
  → OperationEngine (结构化操作规划/校验)
  → Sandbox (git 沙箱副本: create/copy/apply_patch/diff/export_patch)
  → 测试命令验证 → Evaluator (五维评分)
  → Approval Gate (应用 patch 前必批) → 落库 + 经验提取
```

### 关键子模块
- `ContextAssembler` (778 行): 8 类上下文模型 + ranking 装配
- `RankingEngine`: 关键字/符号关系/依赖距离/测试关联/历史成功/经验匹配 六维评分
- `DeveloperAgent`: prompt 构建 + patch/operations 解析 (Anthropic/OpenAI 双 adapter)
- `Sandbox`: git 副本隔离, apply_patch/diff/export
- `Evaluator`: validation/patch_apply/scope/regression_risk/requirement_coverage 五维评分
- `BenchmarkRunner`: greenfield/features/bugs 三类 benchmark + 成本估算 + 五维报告
- Progressive/budget/multi-run: 多 Run 执行策略 (Feature Flag 默认关)

**注意**: 本模块最重但文档自述"生产闭环 0%" — 排名/沙箱/评估全部实现, 但真实 LLM 执行未在实际项目中验证。

## 九、核心代码逻辑精华 (值得学习的模式)

1. **Append-only 双层防改**: 应用层无写接口 + 数据库触发器物理拒绝 — 事件溯源的正确实现
2. **状态机受控转换**: `is_valid_transition` 集中定义, 非法转换一律 ValueError — 状态建模的规范做法
3. **目录信源 = 声明式注册**: 每实体一个 JSON 文件原子写 (临时文件+os.replace) — 简单可靠可审计
4. **分层解耦**: Workflow→(ExecutionRequest)→Runtime→Adapter, 每层只依赖下一层接口
5. **失败安全回退**: 新功能 (ranking/multi-run) 默认 Feature Flag 关, 异常回退旧路径 — 增量演进的稳健策略
6. **契约校验**: Adapter 返回结果须绑定本 request_id, 否则抛错 — 防串扰
7. **宽松解析**: 旧数据 (缺 state/enabled) → 默认值, 零破坏演进

## 十、发现的问题

1. **README 与代码脱节**: "8 只读 API/零写" vs 实际 59 路由/30 写接口; "34 事件" vs 实测 50
2. **双注册表并存**: 顶层 CLI `skill/workflow` (Core SkillRegistry/WorkflowEngine) 与 org `CapabilityRegistry` (六实体) 是两套, MCP 无 CLI 命令
3. **依赖声明不完整**: factory-exec 依赖 httpx、factory-runtime 依赖 platformdirs, 根 pyproject 未聚合
4. **exec 引擎未受真实检验**: 最重模块 (24,895 行) 生产闭环 0%, 无真实 LLM 交付案例
5. **无 CI/CD**: 7000+ 测试全靠本地
