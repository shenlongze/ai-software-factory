## 一、这是什么

**AI Software Factory (AI Factory)** — "AI 软件公司操作系统": 管理 AI 员工 (Agent)、组织软件生产流程、连接各种 Runtime/LLM, 让软件从想法到交付/运维全生命周期可管理、可观察、可验证、可审计。

- 对标 ERP/SAP 级企业系统 (愿景); 当前是技术底座 + 平台雏形
- **差异化: 内网私有化 + 本地 LLM (Ollama) + 审计治理 + 软件生产** — 云竞品进不了内网
- 四层架构: Core (冻结) → Extension → Intelligence → Human Console; 事件溯源 (append-only SQLite) 为唯一事实源

### 平台化蓝图 (长期定位, 2026-08-13 确认)

**AI Factory 未来不是"一个产品", 是一套 AI 基础设施平台。** 每个核心模块按"未来独立产品"设计 (接口/数据/测试独立), AI Factory 是它们的组合 (第一个客户)。

```
AI Factory Platform
├── Decision Router      (模型决策基础设施 — LLM世界的Kubernetes Scheduler)
├── Governance OS        (AI企业安全治理 — AI时代的 IAM+Compliance)
├── Agent OS             (Agent 生命周期)
├── Project Intelligence (项目级 RAG / AI 大脑)
└── Workforce Engine     (AI 员工系统)
```

**独立产品化机会排序 (商业价值):**
1. AI Workforce OS ★★★★★
2. AI Decision Router ★★★★★
3. AI Governance OS ★★★★★
4. AI Software Factory ★★★★★
5. Agent Lifecycle Platform ★★★★☆
6. Project Intelligence/RAG ★★★★★
7. Skill Marketplace ★★★★☆
8. Evaluation / Memory Engine ★★★★☆

**模块设计原则 (从现在起所有核心模块遵守):**
1. **独立生命周期** — 通过 Adapter 接, 不直接调 Factory 内部函数
2. **独立数据边界** — 逻辑隔离 (~/.llm-router/ ~/.ai-governance/ ...)
3. **独立测试** — 100% mock, 不依赖其他模块
4. **独立配置** — llm-router.yaml 脱离 Factory 可运行

**关键平衡 (野心 + 怀疑):**
- 野心: 平台化方向对, 每个模块能独立商业化
- 怀疑: 最大风险是"做太大" — 先找"楔子" (AI Software Factory) 打出第一个付费闭环, 模块内部长出, 以后再拆
- 类比: Amazon 卖书→AWS / Google 搜索→AI / Tesla 电动车→能源

## 五、关键决策

### 产品定位 (最终确认版)

**AI Software Factory = 创建和运营公司的操作系统**

- **当前产品 (认真做)**: 
  - v1 软件工厂: idea→成品 (验证: 一句话生成可运行台球计分App+测试通过+审计完整)
  - v2 自动运维: 自我运行
  - v3 RAG/记忆: 懂项目
- **愿景方向 (不展开, 仅留方向)**: 多行业数字公司 → CEO 超级助理 → 对标 ERP/SAP + 私人助理
- **边界**: 除了"线下办事", 任何行业线上能做的都能做
- **治理为底座** (所有版本的地基, 从 v1 起)
- **外部工具可选, 不必要** (exec 引擎必须最终点火, 不被外部工具绑架)
- **产品形态**: 用户用 AI Factory 创建公司 — 没有部门→创建, 没有专家→创建(agent/skill/mcp), 没有运营→创建, 没有生产线→创建并给落地方案
- **两条线**: 线1 企业向 (对标ERP/SAP, 现在能讲) / 线2 个人向 (私人超级助理, 愿景)

### 执行者决策模型 (闭环)
```
能力需求 → 任务级指定 → 项目级 → 工作区/全局 → 全局池权重评分
```
指定是硬规则, 评分是兜底; agent/skill 是全局池一份定义。
**现状: 评分只做了选LLM, 没做选执行者 → S10-016 缺口**

### 版本规划 (收敛版)
- **v1: idea→成品, 验证=一句话生成可运行台球计分App+测试通过+审计完整 (2个月)**
- **v2: 自动运维 / v3: RAG** — 当前产品线止于此, 认真做
- **v4+: 多行业/CEO助理/ERP-SAP — 愿景方向, 不展开不规划**
- 原则: 每个版本定义"怎么证明"而非"加什么功能"

### 移动端规划 (v1 闭环后)
- **原则: PC v1 真实执行闭环必做, 移动端闭环后做, 不分散核心**
- 移动端定位: CEO 遥控器 — 四能力:
  - **监控**: 看状态 (项目/AI员工/质量门/事件)
  - **审批**: 拍板 (review/批准/驳回)
  - **对话**: 指挥 (对 AI Factory 下指令/问状态/派活)
  - **通知**: 被提醒 (完成/阻塞/需审批 → 推送)
- 不做: 复杂配置/重型开发 (那是 PC 工作台)
- 技术选型: 倾向 Flutter (项目已有 MarkPad Flutter 储备; v1 台球计分App 若用 Flutter 则全栈统一)
- 架构: 复用 FastAPI 后端 + 轻量移动端 domain adapter, 不重写后端; 对话走已有 AI/LLM 通道
- 分期: v1闭环后 → 监控+审批 → 对话 → 通知 (通知需要推送服务, 最后做)

### LLM 策略 (v2 核心, 解决普通用户本地模型弱的问题)
**混合 LLM 策略** (本地为主 + 云端按需):
- 本地 Ollama (小模型): 简单任务/敏感数据 (快, 数据不出本机)
- 云端 API (Claude/DeepSeek): 复杂任务/质量优先 (强)
- 数据分级: 敏感 → 强制本地; 非敏感 → 可走云端
- 普通用户: 本地起步, 需要时按需上云, 可配置数据边界

**LLM 路由引擎** (CostAwareSelector 升级 — "效果/质量/成本"动态最优):
- 四信号: ①能力匹配 ②历史质量 ③成本 ④当前状态
- 动态权重: 按任务类型自动调 (写代码→质量高, 批处理→成本高, 简单→速度高)
- 用户约束: 质量优先/省钱模式/预算上限/只用本地 → 指定>推荐>兜底
- 历史回喂: Experience Loop 积累"哪个模型适合什么" → 越用越准 (自我提升落点)
- 冷启动: 无历史 → 能力匹配 + 用户指定; 用久 → 推荐越来越准
- 放在 v2 (LLM Center / Capability Center 核心), v1 用简单规则即可

### 成本控制 + 监控 (v2 核心功能, 不是附加)
**成本控制 — 五层机制 (三道闸: 事前路由/事中预警/事后核算):**
| 层 | 机制 | 解决 |
|:---|:---|:---|
| ① 预算帽 | 项目/任务/月 三级预算上限 | 防失控超支 |
| ② 成本核算 | 每次 LLM 调用记录 token+单价+成本 | 知道钱花哪 |
| ③ 成本路由 | LLM 路由引擎按成本权重选模型 | 便宜模型干简单活 |
| ④ 缓存复用 | 相似任务结果缓存, 不重复调用 | 砍重复开销 |
| ⑤ 预警 | 成本接近预算 → 预警/降级/暂停 | 提前刹车 |

**监控 — 三维度:**
| 维度 | 监控什么 | 价值 |
|:---|:---|:---|
| 成本监控 | 各模型/项目/任务 token 与费用/趋势 | 知道钱在哪烧 |
| 运行监控 | AI员工/任务进度/成败/阻塞 (升级 Runtime Monitor) | 知道工厂运转 |
| 质量监控 | 测试通过率/质量门/审批率 (配合 Quality Gate) | 知道交付可信 |

**落地分期:**
- v1: 不重点做 (单模型, 成本可控)
- v2: 成本控制核心 (预算帽+核算+成本路由) + 运行监控升级
- v3: 成本预警 + 缓存复用 + 质量监控闭环 (配合 RAG)

**商业意义: 成本控制+监控 = 卖点不是内功**
- 个人用户 (One Person Company): 最怕账单失控 → "看得见成本"
- 政企用户 (私有化): 最怕"AI跑了什么不清楚" → "成本纳入治理"
- 差异化: 竞品 (Copilot/Claude Code) 不给你看成本明细/控预算; AI Factory 把成本纳入治理底座

### 护城河战略 (重点关注的"墙")

**核心判断: 护城河不是技术, 是"积累" — 用得越久, 竞品越追不上。**

**该筑的墙 (靠积累, 抄不走):**
| 墙 | 版本 | 为什么抄不走 |
|:---|:---|:---|
| RAG 行业沉淀 | v3 | 越用越懂行业, 竞品从零开始 |
| **经验驱动智能路由** | v2 | **越用越懂"什么任务用什么模型最优" — 唯一入场券是真实执行数据** |
| 行业模板库 | v2+ | 覆盖行业越多越难追 |
| 治理合规认证 | v1后 | 政企合规流程绑定后, 替换成本极高 |
| 事件溯源/审计 | 已存在 | 架构级, 抄需重构底层 |

**别指望的墙 (会扩散, 当不了护城河):**
- 技术架构本身 (可以抄, 只是时间问题)
- 对话驱动 (大厂都在做, 太容易被抄)
- 纯技术 LLM 网关 (OpenRouter/LiteLLM 已成熟, 红海)

**关键: 力气花在"让 AI Factory 越用越强/越用越懂行业"上, 而不是"代码多难写"。**

### ⭐ 确定要做的方向: 智能 + 可配置 + 经验路由 (LLM 路由)

**定位判断 (已确认): 不做"技术网关", 做"经验驱动智能路由"。**
- 技术网关 (接多家模型+记成本): OpenRouter/LiteLLM 已成熟, 红海, 无优势
- 经验路由 (越用越懂"什么任务用什么模型最优"): 市场无精品, 蓝海, 有护城河
- 入场券: 真实执行数据 (v1 跑通后自然积累"任务/模型/结果"记录)

**三要素 (智能 + 可配置 + 经验):**
| 要素 | 含义 | 落地 |
|:---|:---|:---|
| **智能** | 系统按任务动态选最优模型 | 四信号 (能力/历史质量/成本/状态) + 动态权重 |
| **可配置** | 用户有控制权, 不是黑盒 | 三层控制 + 配置项 + 可解释可覆盖 |
| **经验** | 越用越懂, 自我提升 | usage+feedback → 路由历史 → 影响下次推荐 |

**三层控制 (可配置的核心, = 指定>推荐>兜底 扩展):**
```
第1层 完全指定: 用户 "这个任务用Claude" → 硬规则, 最可控
第2层 规则配置: 用户 "代码→豆包, 敏感→本地, 月预算500" → 半智能
第3层 智能推荐: 系统 "推荐豆包(历史好+便宜), 可换?" → 全智能, 可覆盖
```

**配置入口 (project.yaml 扩展):**
```
model_routing:
  default: deepseek-v4-flash
  by_task: {code: doubao-pro, analysis: gpt-4o, simple: local-ollama}
  sensitivity: {sensitive: local-ollama}
  budget: {monthly: 500, over_budget: downgrade}
# 单任务指定: factory task run --model claude-opus  (第1层)
```

**可解释 + 可覆盖 (用户敢用的前提):**
```
路由结果: 用了 豆包-pro
理由: 任务=写代码(质量权重高) / 豆包历史代码质量4.5/5 / 成本3元(便宜20倍)
可覆盖: [换Claude / 换本地]  → 路由决策可审计
```

| 风险分级+告警 | 🟡 v2 | AI 动作按风险分级 → 高危自动触发审批/告警 |
| 治理可视化 (普通人) | 🟡 v2+ | 面向非技术用户的时间线/摘要 |

**注意区分:** 内部治理缺口 (本段, 主线安全层) ≠ AI 治理独立产品 (战略支线, 卖给别人的产品)。内部补缺口是为了"敢用/能卖政企", 独立产品是"另一条线 v1 后再说"。

### 架构评估 (客观结论)

**工程质量 A 级, 产品适配度 B 级 — 优秀的工程底座, 但产品方向已跑在架构前面。**

- **优势**: 四层单向+事件溯源(双层防改)+状态机受控+目录信源 — 极少数人能写出的严谨
- **问题**: 双注册表并存 / exec 方向与"编排外部专家"定位错位 / 无对话入口层 / Core冻结边界需重划(通用原语冻结, 软件行业特化移Extension) / 文档脱节 / 无CI
- **伪优势**: "Core冻结"锁住了过去设计 / "测试多"覆盖的是稳定性不是AI生产能力 / "功能全"掩盖了执行未闭环
- **演进方向**: 补对话层(LLM理解意图→映射流程) + 行业模板层 + 重划Core边界 + 收敛双注册表 + exec转向"编排+验证"

### 相对 LangGraph 的定位 (为什么自己写)

- **优势**: 治理审计(LangGraph没有) / 对话驱动(它面向开发者) / 全行业流程 / 本地部署 / 完整生命周期
- **劣势**: 生态为零 / 编排轮子自己造 / 缺信任背书
- **结论**: 编排确实是自己造的轮子(LangGraph现成), 但已跑通, 换=重写已工作部分不划算; 力气花在它给不了的"治理+对话+行业层"
