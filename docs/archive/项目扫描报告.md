## 1. 项目定位

**AI Software Factory** — AI 驱动的软件生产系统（非代码生成器）。管理 AI 员工（Agent）、组织软件生产流程（Workflow）、连接 Agent Runtime 与 LLM Provider，让软件项目从 Idea 到交付/运维的全生命周期处于可管理、可观察、可验证、可积累的状态。

类比: Jira（任务）+ Jenkins（流程）+ K8s Dashboard（可观测）+ Confluence（知识）+ CI/CD（验证）的 AI 时代对应物。

当前版本 **v1.0.0-rc1**（功能冻结，只做文档与修复）。单贡献者（shenlongze，257 次提交），48+ 次阶段提交，主干 `main`。

## 2. 四层架构（依赖单向向下）

```
factory-console/   Human Console 人类审核台 (React 前端 + FastAPI 只读 API)
        │ 只读聚合 (零写 API)
intelligence/      决策/推荐/经验 (只读复用 events + product)
        │ 事件 + 只读复用
understanding/ product/ providers/ git/ change/ changeflow/  (Extension, 声明式注册)
        │ 只 import events
events/ tasks/ workflows/ agents/ execution/ runtime/ recovery/ validation/ metrics/
cli/ ...  (Core 冻结, 零领域依赖)
```

- **Core 冻结**: 8 项通用原语，冻结后不改行为，新能力一律走 Extension
- **Extension 隔离**: 依赖面仅 `events` + 区内，删除任一 Extension 不影响 Core（有测试断言）
- **事件溯源**: 事件是唯一事实源（append-only SQLite）
- **测试证明**: 删除 `product` 包后 `dashboard --view product` 仍 rc 0

## 6. 关键发现与建议

### 值得肯定
- 四层单向依赖架构清晰，Core 冻结 + Extension 隔离有测试背书
- 测试基线扎实（实测 7237 通过），文档体系远超一般项目
- 事件溯源 + 恢复/审计设计严谨

### 值得关注
1. **无 CI/CD 流水线** — `.github/workflows/` 不存在（只有 PR/Issue 模板）。单贡献者 + 本地全绿可以运转，但对发布候选版本这是明显缺口。
2. **依赖声明不完整** — `factory-exec` 用到 `httpx`、`factory-runtime` 用到 `platformdirs`，但根 `pyproject.toml` 未声明（本次测试暴露）。建议各子包独立声明依赖或用 workspace 统一管理。
3. **`factory-exec` 生产闭环 0%** — 文档自述 Exec 工程实现完整但生产使用率为 0%（模型瓶颈，见审计附录 H）。
4. **未实现项明确** — 组织-执行连接、多角色、工作台、多行业（路线图 Sprint 7/8/9/12）。
5. **`.venv` 提交路径敏感** — venv 的 shebang 指向宿主机绝对路径，换机器即失效（建议加入 gitignore 已含，但 demo 脚本依赖它）。

### 建议下一步（按优先级）
- 搭建 GitHub Actions: lint（ruff）+ pytest（3.12）+ vitest 三件套
- 补全子包依赖声明
- 为 RC1 打 tag 并发布 CHANGELOG 中的发布流程
