# AI Software Factory — 项目级 RAG 方案 v1.0

> 状态: 方案 (Design) | 日期: 2026-08-11 | 关联: S10 后续规划
> 一句话定位: 给 AI Factory 一个**不依赖模型、不超长、按需取用、可外挂**的项目记忆层。

---

## 1. 背景:我们要解决什么

### 1.1 三个核心问题

| # | 问题 | 根因 | 解决方向 |
|:-:|:-----|:-----|:---------|
| 1 | 换模型 = 失忆 | LLM 无状态, 记忆全在 prompt 里 | 知识存"模型外" |
| 2 | 超长上下文混乱 | 全量塞 prompt → 贵/乱/错 | 按需检索, 只带相关片段 |
| 3 | 影响控制 + 降出错 | AI 不了解项目真实情况就动手 | 项目知识 + 准确关联索引 |

**三者同一病根**: LLM 无状态且上下文有限, 而项目知识是长期、海量的。
**唯一治本之路**: 把项目知识从模型外存下来, 按需取用。

### 1.2 衍生问题(经排查确认必然存在)

| # | 问题 | 解法(已确认方向) |
|:-:|:-----|:-----|
| 4 | 知识新鲜度 | 内: 事件驱动自动同步; 外: 一键更新 + 自检 |
| 5 | 知识冲突(资料打架) | 自检提示 + 按事件时间最新优先 + 人裁决 |
| 6 | 知识规模 | 监控阈值 → 分层/归档 → 旧知识降级 |
| 7 | 权限隔离 | 复用 org 层 company 隔离 |
| 8 | 更新来源 | 内监控 + 外一键, 即 #4 机制本身 |

## 2. 总体架构:项目记忆层

```
                    ┌─────────────────────────────────────┐
                    │         AI Factory 控制平面          │
                    │   lifecycle / task / workflow / exec │
                    └───────────────┬─────────────────────┘
                                    │ 查询上下文 / 影响分析
                    ┌───────────────▼─────────────────────┐
                    │         知识层 (Project Memory)      │
                    │                                      │
                    │   KnowledgeStore 接口 (存储可替换)   │
                    │     ├─ SQLiteKnowledgeStore (默认)   │
                    │     ├─ PostgresKnowledgeStore (企业) │
                    │     └─ VectorStoreAdapter (外挂)     │
                    │                                      │
                    │   Retriever 接口 (检索可替换)        │
                    │     ├─ GraphFirst (图遍历, 主)       │
                    │     ├─ BM25 (词法兜底)               │
                    │     └─ VectorRetriever (语义外挂)    │
                    └───────────────┬─────────────────────┘
                                    │ 事件流驱动增量更新
                    ┌───────────────▼─────────────────────┐
                    │     事件溯源 (append-only SQLite)    │
                    │   artifacts/tasks/events/change/exp  │
                    └─────────────────────────────────────┘
```

**核心设计**: 知识层 = 一个接口 + 多个适配器 + 配置切换。
与 `providers/` 的 LLM 切换完全同构 —— 换存储不换业务代码, 只改配置。

## 3. 技术选型

### 3.1 选型原则

- **通用**: 成熟技术, 不追新
- **成熟**: 标准库/标准协议优先, 不引重型框架
- **可外挂**: 接口先行, 适配器后补

### 3.2 具体选型

| 层 | 默认实现 | 理由 | 外挂口 |
|:---|:---------|:-----|:-------|
| 存储 | SQLite(标准库) | 零安装, 全项目在用, 单项目级够用 | Postgres / 向量库适配器 |
| 图遍历 | SQLite 递归查询 | 影响分析主干, 零依赖 | 图数据库(百万级才需要) |
| 词法检索 | BM25 / TF-IDF(纯 Python) | 三十年级成熟算法, 离线可用 | rank-bm25 微型库 |
| 语义检索 | providers embeddings API | 复用现有 LLM 通道, 用户零安装 | OpenAI 兼容 /embeddings |
| 框架 | 不用 LangChain/LlamaIndex | 不成熟/黑盒/体积大, 与轻依赖哲学相悖 | 后期外挂层再评估 |

### 3.3 关键:外挂不是后期重构,是前期接口

```
factory config knowledge-store=sqlite    (默认)
factory config knowledge-store=postgres  (企业有 PG)
factory config knowledge-store=milvus    (海量数据)

企业要什么 → 加一个适配器 → AI Factory 核心不动
```

## 4. 详细设计

### 4.1 数据模型(SQLite)

```
nodes      (知识节点)
  id / type(file|class|func|api|task|artifact|doc|...) / name / content / meta / updated_at

edges      (关联边)
  from_id / to_id / rel(import|call|depends|references|supersedes|...) / confidence

event_sync (增量同步锚点)
  last_seq / last_commit / status

embeddings (语义层, 可选)
  node_id / model / vector BLOB / dims
```

- 节点 = 文件/类/函数/API/任务/产物/文档
- 边 = 依赖/引用/调用/决策链 source
- **影响分析 = 从变更节点沿边遍历**(图遍历, 精确)

### 4.2 增量更新(事件驱动)

```
内 (AI Factory 项目):
  事件流 (task完成/artifact创建/commit/审批/经验) → 增量加节点/边/更新失效/标记过期
  = 知识层是事件溯源的一个"物化视图"

外 (导入项目):
  一键更新 → 重扫代码库 diff → 增量重建
  自检 → 比对知识库与代码库差异 → 提示"过期知识"
```

### 4.3 影响分析(核心价值)

```
输入: 变更点 (改的需求 / API / 代码)
  ① 结构化图遍历 (主): 沿引用/依赖边扩散 → 精确影响面
  ② BM25 词法 (兜底): 覆盖"图里没显式链接但相关"
  ③ 语义检索 (增强): 补全"人没想到的关联"
输出: 影响范围 {涉及文件/API/测试/任务/文档} + 置信度 + 出处
```

**事实与推测分离**(信任关键):
- ① 输出标"代码事实"(确定性抽取)
- ②③ 输出标"推测, 请人工确认"
- 用户修正 → 写回知识库 → 推测变事实(纠错即知识)

### 4.4 老项目反向建库

```
老代码 + git 历史
  ① 代码结构索引 (AST/目录): 模块→文件→类/函数 → 节点
  ② 依赖图 (imports/调用): 谁依赖谁 → 边 (影响分析主干)
  ③ git 历史: commit→改过的文件→模块 (变更模式)
  ④ 已有文档/README/ADR → 词法层
  ⑤ understanding 报告 → 全局理解节点

导入即建库, 建库后与新项目无区别 (增量更新)。
诚实边界: 能推"代码级影响"(准), 推不出"需求级历史"(老项目没有)。
```

### 4.5 代码切块(检索质量的分水岭)⚠️ 现在必须定

代码不是散文, 不能按字数/固定长度切块——会把一个函数劈成两半, 检索即错。

**规则: 按 AST/语法结构切, 而不是按 token 切。**
- 最小单元 = 函数/类/方法(一个完整逻辑块)
- 一个文件内: 多个函数 → 多个块; 大文件 → 按结构分块
- 块保留完整上下文: 所在文件/类/依赖(import)作为块的元数据

**多语言处理**: Flutter/Dart + Python + 后端, 每种语言的 AST 切法不同,
需按语言选择解析器(标准库/轻量库, 不引重型框架)。

**为什么关键**: 切块质量直接决定检索质量。切碎了 → 检索到的语义残缺 →
影响分析漏报/误报。这是 RAG 里最容易被做砸、但看起来最不起眼的工程点。

### 4.6 查询时机(知识在哪个环节注入)⚠️ 现在必须定

知识不该只在"生成代码前"查一次, 而应在**每个环节按需查**:

| 环节 | 查什么 | 注入到哪 |
|:-----|:-------|:---------|
| PRD 生成 | 历史需求/决策/竞品分析 | 生成 prompt |
| 任务拆解 | 相似任务/依赖/已知坑 | 任务描述 |
| 写码前 | 相关模块代码/约定/经验 | 代码生成 prompt |
| 验收时 | 该项目应满足什么(PRD/测试) | 验收标准 |
| 需求变更 | 变更影响范围(图遍历) | 影响分析结果 |
| 用户问答 | 项目当前状态/历史 | 回答上下文 |

**要定义清楚**: 哪个环节、查什么、注入到哪、结果怎么用。
这决定"知识库"是增强所有环节, 还是只增强生成。

### 4.7 误报控制(防遗漏也要防误报)⚠️ 做前想清楚

我们一直强调"零遗漏", 但**误报同样致命**: 说影响了、实际没影响,
报错两次用户就不信了。

- 图遍历给"影响面" + 置信度分级: 直接依赖(高) / 间接依赖(中) / 语义相关(低)
- 输出按置信度排序, 用户可只看高置信度
- 评测集同时测"召回率(不遗漏)"和"精确率(不误报)", 两个指标都要

### 4.8 跨 API / 微服务

```
知识图加服务层:
  服务 → API 端点 → 调用方 / 数据模型 / 事件 topic

可靠度:
  契约级影响 (改API字段→谁消费)   ✅ 高 (有 OpenAPI/proto + 调用点)
  服务依赖图 (谁调谁)             ✅ 高 (服务发现/部署清单)
  同步调用链 (A→B→C)             🟡 中 (各服务都入库才准)
  异步链路 (消息驱动)             🟡 中偏难 (靠 topic schema + 事件溯源补)

前提: AI Factory 需要"系统/产品"层, 在项目之上聚合多个服务。
```

## 5. 安全与治理(不做就砸信任)

| # | 风险 | 机制 |
|:-:|:-----|:-----|
| 1 | **密钥泄漏** ⚠️最高 | 索引前剥离 API key/密码/.env/硬编码凭据; 检测+告警 |
| 2 | **注入攻击** ⚠️最高 | 检索内容当不可信数据处理, 与代码指令区分, 防知识库劫持 |
| 3 | 权限隔离 | 知识按 project 分库/命名空间, 查询强制 project 上下文 |
| 4 | 删除/改名跟踪 | git 感知的更新 (识别 rename/delete, 重连关联边) |
| 5 | 冷启动 | 大项目后台异步建索引, 先主干后细节, 进度可见 |
| 6 | 导出/合规 | 一键导出/清空项目知识 (数据主权) |
| 7 | 知识库自身生命周期 | 纳入 recovery/checkpoint, schema 升级可迁移 |

### 5.1 密钥剥离(最高优先级, 详细机制)

企业代码里到处是密钥, **代码进知识库 = 泄密, 不做企业不敢用。**

- **索引前扫描 + 剥离**: 识别并替换 API key / 密码 / token / 连接串 / 硬编码凭据
- **来源黑名单**: `.env`、配置文件、密钥文件、`secrets/` 目录 直接排除
- **模式识别**: 常见密钥格式 (sk-*, AKIA*, 私钥 PEM 头) 正则/规则匹配后脱敏
- **告警**: 检测到疑似密钥 → 告警 + 阻断入库, 而不是静默放过
- **双层**: 入库前剥离 + 检索结果再检查(防漏网)

### 5.2 注入防御(最高优先级, 详细机制)

**知识库里的内容会"教唆" AI。** 恶意内容可能藏在 README/注释/文档里,
诱导模型输出密钥或忽略规则。

- **检索结果当"不可信数据"处理**: 与代码/系统指令严格区分, 不直接作为指令执行
- **注入检测**: 检索结果中含指令性语言 ("忽略之前所有规则" 等) → 标注/隔离
- **权限边界**: 知识库内容不能触发工具调用, 只能作为上下文
- **审计**: 知识注入的每个环节留痕, 可追溯"哪段知识影响了什么输出"

**这两项不做, RAG 就是安全黑洞; 做了, 才是企业可采购的治理能力。**

## 6. 实施路线(先记忆, 后推理)

### 阶段一: 项目记忆基础(P0, 解决问题 1/2)
- KnowledgeStore 接口 + SQLite 实现
- 事件驱动增量索引
- 图遍历 + BM25 检索
- 密钥剥离 + 注入防御(起步就做)
- 验证: "AI 干活前按需查项目上下文", 换模型不失忆

### 阶段二: 影响分析(P1, 解决问题 3)
- 图遍历影响分析 + 置信度/出处
- 事实与推测分离 + 纠错即知识
- 评测集(拿真实变更当考题, 零遗漏可回归)
- 验证: 改需求 → 答出完整影响面

### 阶段三: 老项目 + 外挂(P2)
- 老项目反向建库(代码图)
- Postgres / 向量库适配器(企业)
- 微服务多仓支持(系统层)

### 阶段四: 增强(P3)
- 语义检索增强
- 执行上下文注入(反哺生成, 治"空实现")
- 团队共享/多机同步

## 7. 优先级清单(区分"必做"与"后补")

**现在必须定(不做返工):**
- 密钥剥离、注入防御、代码切块(AST 按结构切)、删除/改名跟踪、查询时机定义

**做之前想清楚(影响设计):**
- 误报控制(影响分析既防遗漏也防误报)、多人共享(决定存储选型)、知识库自身生命周期

**后期补(不影响起步):**
- 噪声过滤、非文本资产索引、重构风暴、冷启动优化、评测集、导出合规

## 8. 关键认知收束

1. **RAG 的本质**: 不是"检索系统", 是"项目记忆" —— 让 AI 先查项目资料再干活, 别瞎写
2. **三个问题的根**: LLM 无状态 + 上下文有限; 唯一治本 = 知识存模型外, 按需取用
3. **与现有架构同构**: 事件溯源提供增量与出处, providers 模式提供存储可替换, org 提供隔离, validation 文化提供评测
4. **不是加一个 RAG 模块, 是让现有架构长出记忆能力**
5. **护城河**: 纠错即知识 + 自我提升 —— 用得越多越准, 竞品没有

### 9.8 优先级汇总(速览)

**P0(起步必做, 不做返工):**
C1 密钥剥离 / C2 注入防御 / C3 代码切块 / U1 删除改名跟踪 / U2 事件驱动增量 /
U4 一键更新自检 / S1 权限隔离 / S2 注入检测 / X1 存储接口 / T1 查询时机

**P1(阶段二, 核心功能):**
C4 噪声过滤 / C6 多语言切块 / C7 测试代码 / U3 重构风暴 / Q1 影响分析 /
Q2 事实推测分离 / Q3 纠错即知识 / Q4 误报控制 / Q6 评测集 / Q8 冷启动 /
S3 导出清空 / S4 审计留痕 / S5 多租户 / X2 存储适配器 / X3 团队共享 /
X5 执行上下文注入 / L1 schema迁移 / L2 备份恢复

**P2(后期增强):**
C5 非文本资产 / C8 二进制 / U5 过期降级 / Q5 实体链接 / Q7 检索排序 /
X4 微服务系统层 / L3 性能监控

**核心洞察(补充):**
- RAG 的价值按 P0→P1→P2 递进, 但**安全项(P0)和正确性项(P1)是信任的上下限** —— 缺安全不能上线, 缺正确性没人信
- 最容易做砸的三个坑: **代码切块 / 实体链接 / 误报控制** —— 都"看起来简单, 做准极难"
- 最强的护城河组合: **事件驱动增量(新) + 纠错即知识(自我提升) + 审计留痕(治理)** —— 这三点叠加, 是竞品抄不走的
