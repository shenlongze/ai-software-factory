# 03 — CONVERSATION CASE REPLAY

对真实失败链逐轮: 用户想要什么 / 理想理解 / AF 实际理解 / 调用 /
已有信息 / 真缺 / 该不该调 / 该怎么答。

## 轮1 "现在项目是什么情况"
① 要项目概览 ② STATUS_QUERY(project 域) ③ project_status ④ project_status
⑤ - ⑥ - ⑦ 该调 ⑧ project_status/lifecycle ⑨ 一轮足够
⑩ 概述后自然等下一句。→ AF 应正确 (E1 后域路由) — 此轮无害。

## 轮2 "嗯，你查看了，结果呢？" ← 关键轮
① 用户要【综合结论】 — 上轮查完该给结果了
② 理想: 引用上轮工具结果 → 直接给结论 (0 新工具)
③ AF 曾实际: 又查 project_status/lifecycle/code 等 (重查)
④ 调用: 重新诊断工具组
⑤ 已有: 上轮全部 tool output (在历史)
⑥ 真缺: 无 — 足够回答
⑦ 不该调 (上轮事实可答)
⑧ - ⑨ 立即停
⑩ "上轮查到的状态: X/Y/Z → 结论: …"
为何 Hermes 更自然: 历史含上轮结果 → LLM 直接引用综合, 无重查冲动;
AF 无"上轮已查 → 直接综合"的执行约束 + 工具面引导继续查。

## 轮3 "什么情况"
① 用户困惑/催促 — 要解释 (可能"怎么没结论/乱了")
② 理想: 给清晰简短结论或承认混乱 → 重述要点
③ AF 曾实际: complaint → recovery 引导 (修后回主题) 或仍诊断
④ 调用: 视引导; 曾触发诊断组
⑤ 已有: 全历史 ⑥ 真缺: 无
⑦ 不该调 ⑧ - ⑨ 立即停
⑩ 承认 + 一句话要点 + 问是否继续某方向
Hermes: 判"催促/困惑" → 直接给最有用的简短总结。

## 轮4 "继续需求分析"
① 恢复需求分析工作 ② continue + active_work=需求分析
③ E3 后: resolver + 执行指令 ④ get/save_product_record
⑤ 已有 REQ (若有) ⑥ 真缺: 需求细节 (可基于已有信息推+标待确认)
⑦ 该调 (读已产出/写深化) ⑧ get_product_record → save record_id
⑨ 一轮产出后停 ⑩ 完成汇报
→ AF E3-E5 已基本对 (真产出 REQ, gate 防重复)。

## 轮5 "然后呢？"
① 要下一步/继续推进 (或要上轮结论的延续)
② 理想: 读取刚产出 → 判阶段 → 执行下一合法动作或给下一步
③ AF 应: continue → gate → ADVANCE/REFINE
④ get_product_record → save/execute
⑤ 已有: 刚建的 REQ ⑥ 真缺: 下一阶段 (PRD 内容 — AI 可起草)
⑦ 该调 (读/写) ⑧ get → save(prd) ⑨ 产出后停
⑩ 汇报新产出 + 下一步
→ AF gate 后能推进; 风险: 若 E3 判定落入"问用户"则空转。

## 总结: AF 三处系统性弱点
1. 轮2 型 (要结论) 无"上轮结果直接综合"约束 → 重查
2. 轮3 型 (催促/困惑) 靠分类恢复, 偶仍诊断
3. 上下文薄 → 已查事实重查/丢失
