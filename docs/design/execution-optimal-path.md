# AI Factory OS — 复杂任务执行:最优实施路径

> 状态: 方案 (Plan) | 日期: 2026-09-19 | 依据: 我方自评 + Codex 独立评审(读代码核实)
> 一句话: **先让执行链"跑得起来且不出静默故障", 再谈能力(审查员/隔离/MoA)。**

---

## 0. 为什么是这条路（两方评审的交集）

```
我方自评: 方向对, 但依据部分不实 + 做早了; 该先做执行能力(ct-1)。
Codex:    暂缓原设计; 先统一执行存储 + run --plan + Outcome/失败释放/文件冲突。
⇒ 交集（也是本方案）: 【地基 → 能跑 → 不静默出错 → 语义正确 → 资源真实】, 能力后置。
```

**关键否决(接受 Codex)**: 原设计把 `single/parallel/isolated/moa` 做成一个 enum = 错误维度。
`isolated`(上下文可见性) · `parallel`(并发度) · `moa`(模型多样性) **不是互斥的** ⇒ 应为**三个正交属性**。

---

## 1. 四刀方案（每刀 = 1 commit + 全量验证 + STOP）

### 第 0 刀 · 统一执行存储（地基）

| | |
|---|---|
| **现状(实测)** | 同一个 `RuntimeStore` 类被两条链用**两个路径**: pump→`root/runtime`（磁盘 0 个）· CLI→`root/runtimes`（1 个）; 另有 `ExecStore`→`root/exec`（6 个） |
| **目标** | **一个路径 + 一个权威 Store**（一数据一权威源 —— 与既有铁律同源） |
| **做法** | ① 定权威路径（建议 `<root>/exec`, 数据最多）② 另一个改为兼容读 ③ 迁移现存 `runtimes/` 1 个（先备份）|
| **验收** | pump 建的 execution 能被 CLI 查到（**互可见**）; 三条链只有一处写 |
| **风险** | 迁移真实数据 ⇒ **先备份**（`runtimes/` + `exec/`） |

**为什么必须第一刀**: `run --plan`（第 1 刀）要跑整棵树并**续跑** —— 若存储分裂, pump 与 CLI 各写各的, 续跑读不到状态。

### 第 1 刀 · `run --plan` + 三个"不静默"前提（必须一起做）

| | |
|---|---|
| **① run --plan** | 按 `depends_on` 拓扑序跑整棵树（现在只能 `run --task` 单个 ⇒ 13 任务 13 次调用）|
| **② claim 释放(cr-4)** | 现状: `_claim_and_run()` **只在抛异常时**释放 leaf; 返回 **FAILED 结果**时 leaf **保持 claimed** ⇒ **任务卡死永不重试**。修: FAILED ⇒ 释放 + 回写 + 落 checkpoint |
| **③ 文件冲突(cr-5)** | 现状: `decomposition.file_conflicts()` 要求"同层写同文件 ⇒ 降级串行", 但**没人调用** ⇒ 并行会**静默覆盖**。修: 并行前检测, 冲突降级串行 |
| **验收** | 13 个任务一条命令跑完; **故意让第 7 个失败 ⇒ 能续跑且前 6 个不重跑**; 两个写同文件的任务被串行 |
| **为什么三件一起** | ★ 只做 ① 会**更糟**: 跑起来就会遇到"失败即卡死"+"并行静默覆盖" —— 比现在人工逐个跑还危险 |

### 第 2 刀 · Outcome 接进完成语义（cr-3）

| | |
|---|---|
| **现状** | contract 明写 "execution success ≠ business completion, **必须 accepted Outcome**", 但 pump 见结果成功就写 `completed`; `has_accepted_outcome()` 也把 `completed/done` 当验收 |
| **目标** | "完成"必须经验收语义（不能"跑通即完成"）|
| **验收** | 无 accepted Outcome 的任务**不能**被标 `completed`; 与"acceptance 无消费方"一并解决 |

### 第 3 刀 · 让预算是真的（cr-6）

| | |
|---|---|
| **现状** | `SimpleLoad` 直接返回 `1e9` · `OrgResource.capability()` 返回 `None` ⇒ `cost_estimate` 实际为 **0** ⇒ 预算约束形同虚设（"超限该阻断就阻断"无数据支撑）|
| **目标** | load/capability 返回真实值（数据源: `providers/usage.json` 已存在）|
| **验收** | 预算能真实阻断（不是 1e9）; 超限时确实推迟/拒绝 |

## 2. 后置（明确不做, 及原因）

| 能力 | 为什么后置 |
|---|---|
| **角色外置(cr-2)** | ★ `RoleDefinition.prompt_template` **全仓无运行时消费者** ⇒ 先让 runtime 真读角色, 再谈外置; 否则"只加一个文件"只是多个目录 |
| **审查员插件(cc-2)** | 依赖上一条（角色得先被消费干净）; 且现在无人正在加审查员（"只问现在谁在用"）|
| **上游上下文传递(ct-6)** | 第 1/2 刀跑通后再做（那时才知道传什么）|
| **isolated / MoA** | 依赖第 3 刀（真实预算）; 且 MoA 需要模型选择+聚合契约, 成本高 |
| **"执行策略" enum** | ★ Codex 判定错误维度 ⇒ 改为三个正交属性（`context_visibility` / `concurrency` / `model_diversity`）, 且等有实现再定 |

---

## 3. 为什么这是最优（而不是"我原设计"或"Codex 的全盘"）

| 判据 | 本方案 |
|---|---|
| 顺序按依赖 | 地基(存储) → 能力(跑整棵树) → 语义(完成) → 资源(预算) ✓ |
| 守住"不静默"底线 | 第 1 刀强制三件一起（否则跑起来更糟）✓ |
| 不做没消费者的 | 角色外置/审查员后置（cr-2 证据: 没人读）✓ |
| 不做过早抽象 | "执行策略"改正交属性且后置 ✓ |
| 对齐 Founder 铁律 | 一数据一权威源(第0刀) · 只问现在谁在用(后置项) · 不给自己造活 ✓ |

## 4. 一句话

```
最优路径 = 【先修地基与安全网, 再让整棵树跑起来, 最后才谈智能】
  第 0 刀 统一执行存储   —— 否则续跑读不到状态
  第 1 刀 run --plan + claim 释放 + 文件冲突 —— 三件一起, 否则跑起来更糟
  第 2 刀 Outcome 接进完成语义
  第 3 刀 真实预算
  ⇒ 之后才有资格谈: 角色消费 → 上游传递 → isolated / MoA
```
