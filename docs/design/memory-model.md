# AI Software Factory — 记忆模型 (Memory Model)

> 角色: 首席架构师。把 Hermes + MarkPad 流程中实际跑通的记忆实践, 抽象为一套可复用的分层知识体系。
> 原则: 可落地、KISS、中文。抽象为方法论, 不绑定具体工具。

---

## 0. 一句话摘要

Agent 的记忆 = **声明性事实 (declarative facts) 的分层存储**, 不是指令集。事实按"稳定性"分层存放, 按生命周期 (写入→使用→过期→合并) 治理, 最终沉淀为四类 Knowledge Base; 失败记录不是垃圾, 是最贵的工程资产。

---

## 1. 核心定义: Memory 是"事实", 不是"指令"

实证中反复验证的第一条原则:

| 类型 | 含义 | 例子 | 存放位置 |
|------|------|------|----------|
| 声明性事实 (declarative) | 世界是什么样的 | 用户偏好、环境路径、上次会话结论 | Memory / Knowledge Base |
| 指令 (imperative) | 要做什么、怎么做 | "遇到 X 就执行 Y" | Skill / Prompt / 流程定义 |

**判定规则**: 写一条记忆前先问——这是"描述现状", 还是"规定动作"? 只有前者进 Memory。指令混入记忆的后果: 记忆膨胀、互相冲突、难以合并精简。

**第二原则: 事实必须有出处和时间**。没有来源、没有时间戳的事实, 三个月后就是谣言。

---

## 2. Memory 分层

按**稳定性** (变化速度) 分层, 稳定性越低, 离运行时越近, 越需要频繁更新。

### L0 — 用户画像 (User Profile)
- 内容: 沟通偏好 (中文、简洁、要图表)、质量偏好 (KISS、可落地)、工作风格 (先验证再汇报)、禁忌 (不要自说自话、不要伪造结果)。
- 存储: 长期, 几乎不失效。
- 更新频率: 仅当用户显式纠正时更新。
- 失效: 几乎不失效; 唯一更新信号是用户直接冲突。

### L1 — 环境事实 (Environment Facts)
- 内容: 平台/OS 版本、工作目录、工具链、网络限制、构建产物位置、CI 行为。
- 存储: 中期, 环境变更时失效。
- 更新频率: 每次环境变化 (升级、换机、迁移仓库) 时覆盖。
- 失效: 以"验证时发现不符"为失效信号, 立即覆盖并留痕。

### L2 — 经验教训 (Lessons Learned)
- 内容: 从成功/失败中提炼的可复用模式, 例如:
  - 截断续跑: 恢复时**读 session summary 确认落盘**, 不要直接 checkout 旧分支继续干;
  - Agent 可靠性模式: 分析型任务可靠 / 实现型任务范围清晰则可靠 / **debug 型任务首次不可靠, 必须验证**;
  - 不信任自报告: 任何"我完成了"都必须有独立验证 (测试输出、文件 diff、实际运行)。
- 存储: 长期, 但以"冲突案例"触发修订。
- 更新频率: 每次复盘后追加或修订。
- 失效: 当新案例证明旧教训不成立时, 用新证据覆盖, 保留旧版本在历史里。

### L3 — 项目知识 (Project Knowledge)
- 内容: 当前会话状态、停靠点 (checkpoint)、未决问题、进行中任务、最近变更。
- 存储: 短期, 会话级; 有价值的沉淀到 Knowledge Base (见 §4)。
- 更新频率: 每次里程碑/停靠点落盘一次。
- 失效: 会话结束即归档; 任务关闭即转移为 KB 条目。

### 分层总表

| 层 | 内容 | 稳定性 | 存储 | 失效信号 |
|----|------|--------|------|----------|
| L0 用户画像 | 偏好/禁忌 | 极高 | 长期记忆 | 用户显式纠正 |
| L1 环境事实 | 平台/路径/工具 | 高 | 长期记忆 | 验证不符 |
| L2 经验教训 | 可复用模式 | 中 | 记忆 + experiences/ | 新案例推翻 |
| L3 项目知识 | 会话状态/停靠点 | 低 | 会话文件 | 任务关闭/会话结束 |

## 3. Memory 生命周期

一条记忆经历四个阶段: **写入 → 使用 → 过期清理 → 合并精简**。

### 3.1 写入
- **时机**: 只写三类内容——用户明确表达的偏好; 验证过的环境事实; 复盘后的经验教训。**未经验证的自报告不写入** (见 §5.5)。
- **格式**: 一句话事实 + 出处 + 时间戳。例:`[2026-08] 用户要求所有交付物必须附真实运行输出 (来源: 会话复盘, 独立验证)`
- **去重**: 写入前先检索是否已有同义条目; 有则更新旧条目, 不新增。
- **写入即归档**: 关键结论同时落到会话停靠点 (docs/session/), 防止记忆丢失。

### 3.2 使用
- **注入时机**: 任务开始时注入 L0/L1 (画像+环境), 遇到相关场景注入 L2 (教训), 任务中持续读取 L3 (状态)。
- **命中原则**: 记忆是**提示性参考**, 不是权威。使用前要"怀疑它", 使用后要"验证它"——环境变了记忆就过期了。
- **检索成本控制**: 只带与当前任务相关的层, 不把全部记忆塞进上下文。

### 3.3 过期清理
- **触发条件**: 容量上限 (满了)、验证不符、任务/会话关闭。
- **清理动作**: 删除未引用、无时间戳、已被覆盖的条目; 可回溯的内容 (错误记录) 不删, 移入 KB 归档。
- **规则**: 清理是"降级"不是"删除"——从活动记忆降级到 Knowledge Base 存档, 只有确认无价值的才真正删除。

### 3.4 合并精简
- **触发**: 记忆满了 (实证: 满了就要合并精简, 这是既定操作, 不是异常)。
- **方法**:
  1. 按层统计, 找最膨胀的一层 (通常是 L2 或 L3);
  2. 同主题多条 → 合并为一条, 保留最新证据与最早出处;
  3. 冲突条目 → 用证据等级裁决 (见 §5.3), 高证据覆盖低证据;
  4. 合并结果写回, 并在变更记录中注明"合并了哪几条"。
- **验收**: 合并后语义不丢: 任取一条旧条目, 能从新条目 + 出处还原其结论。

## 4. Knowledge Base 设计

Memory 是**运行时快照**, Knowledge Base 是**持久化沉淀**。会话结束、记忆精简时, 有价值的内容沉淀为四类条目 (实证映射: docs/adr/ + docs/session/ + docs/bugs/ + dist/)。

### 4.1 四大类

#### ① decisions/ — 架构决策 (ADR)
- 内容: 背景、可选方案、决策、后果、状态 (proposed/accepted/deprecated)。
- 实证: 架构决策必须留档, 否则三个月后没人知道"为什么这么设计"。
- 条目模板:
  ```markdown
  # ADR-xxx: <决策标题>
  状态: accepted
  日期: YYYY-MM-DD
  背景: 为什么需要决策
  方案: 考虑了哪些选项, 为什么选这个
  后果: 带来了什么约束/收益
  ```

#### ② architecture/ — 架构事实
- 内容: 系统结构、模块边界、数据流、部署拓扑 (当前事实, 非决策过程)。
- 与 decisions 的关系: decisions 记"为什么", architecture 记"是什么"。架构文档过期时更新, 不改 decisions。

#### ③ bugs/ — 缺陷档案
- 内容: 症状、复现步骤、**根因 (必须带证据等级)**、修复、回归基线、预防措施。
- 实证: Bug 根因是最高价值的知识, 因为它是用真金白银 (调试时间) 换来的。
- 条目模板见 §5.2。

#### ④ experiences/ — 经验教训
- 内容: 从复盘提炼的模式, 含适用范围、失效条件、证据等级。
- 实证条目示例:
  - `debug 型任务首次不可靠 → 完成后必须独立验证` (证据: 多次会话实测);
  - `截断续跑: 读 summary 确认落盘, 不直接 checkout` (证据: 实测恢复流程);
  - `不信任自报告: 完成声明必须有测试/日志/diff 佐证` (证据: 多次被自报告误导)。

> 测试基线: 属于 ③ 的附属资产 (回归基线: 通过/失败集合), 用于快速判断"这次改动是否破坏了什么"。它本身不是独立类别, 挂在对应缺陷/模块条目下。

### 4.2 检索方式 (KISS)

1. **目录即索引**: `docs/{adr,architecture,bugs,experiences}/` 按主题分目录, 文件名即关键词 (如 `bugs/truncation-resume.md`)。
2. **元数据**: 每个条目头部 frontmatter: 类型/日期/证据等级/关联任务。元数据够支撑筛选即可, 不搞复杂 schema。
3. **全文检索**: 用仓库内文本搜索即可覆盖绝大多数场景, 不需要向量库起步。
4. **入口文件**: 每类一个 README/索引表, 记录条目清单与一句话摘要, 供 Agent 快速扫描。
5. **检索注入**: 新任务开工前, 按任务类型检索相关条目 (涉及调试→查 bugs/; 涉及架构→查 decisions/+architecture/), 检索结果作为参考注入, 不盲从。

### 4.3 Memory 与 KB 的关系

```
运行时 (Memory, 分层快照)         持久化 (Knowledge Base)
  L0 用户画像  ──长期──►  experiences/  (沉淀为经验)
  L1 环境事实  ──变更──►  architecture/ (沉淀为架构事实)
  L2 经验教训  ──复盘──►  experiences/  (沉淀为可复用模式)
  L3 项目知识  ──会话结束► bugs/ + decisions/ + session 归档
  (满了就合并精简, 精简掉的沉淀进 KB)
```

**双向通道**: 写入时"先查 KB 再写 Memory" (避免重复); 使用时不区分来源, 统一按证据等级信任。

## 5. 从错误中学习: 失败是工程资产

### 5.1 核心理念 (MarkPad 原则)

> **错误记录 = 工程资产, 不是污点。**

一次失败的调试, 产出了: 根因 (别人再花 5 小时也未必找得到)、修复方案、验证方法、防复发规则。这是回报率最高的知识。因此:
- 缺陷永不因"修好了"而删除, 只归档;
- 修复动作必须反向沉淀一条预防条目, 否则下次换个形式再犯。

### 5.2 缺陷档案模板

```markdown
# BUG-xxx: <一句话症状>
状态: fixed / open / won't-fix
日期: YYYY-MM-DD
症状: 观察到什么 (用户视角)
复现: 怎么稳定复现
根因: 深层原因, 不是表象
证据等级: A / B / C        <- 必须标
修复: 改了什么, 改了哪里
验证: 用什么独立手段确认修好 (测试/日志/diff)
回归基线: 修复前后通过/失败的用例集合
预防: 以后如何避免同类问题 (沉淀进 experiences/)
```

### 5.3 证据等级 (信任的标尺)

| 等级 | 含义 | 例子 | 使用规则 |
|------|------|------|----------|
| A | 独立验证/可复现 | 测试通过、真实运行输出、可复现步骤 | 可写入, 可指导决策 |
| B | 日志 + 推理 | 日志链吻合 + 代码推理 | 可写入, 标注为推断 |
| C | 推测/自报告 | "我认为大概是…"、Agent 口头汇报 | 不写入 KB, 只作线索 |

规则: **写入 KB 的最低门槛是 B; 指导架构决策必须 A; 自报告默认 C, 直到独立验证升级。**

### 5.4 Agent 可靠性模式 (实证沉淀)

| 任务类型 | 可靠性 | 应对策略 |
|----------|--------|----------|
| 分析型 (读代码/查资料/给结论) | 可靠 | 直接采用, 抽查引用 |
| 实现型 (写代码/改配置), 范围清晰 | 可靠 | 采用 + 跑真实验证 |
| 实现型, 范围模糊 | 中 | 先确认范围再动手, 每步落盘 |
| debug 型 (定位根因/修复诡异 bug) | **首次不可靠** | 完成后必须独立验证, 视首次结论为假设 |

**推论**: 任务分派与验收标准应按类型差异化——debug 型任务的"完成"必须附带独立验证证据, 不满足就视为未完成。

### 5.5 不信任自报告: 独立验证原则

实证中最贵的教训: **Agent 的"我完成了/我修好了/我已经验证过"不可直接采信。**

硬性规则:
1. 任何完成声明, 必须有可复核的产出物: 测试输出、构建产物、文件 diff、实际运行日志;
2. 验证动作与执行动作分离 (执行者不自证清白);
3. 截断续跑恢复时, 以**磁盘上的落盘内容** (summary/产物) 为准, 不信任内存里的记忆或口头描述;
4. 违反本原则的自报告, 其相关结论降级为 C, 重走验证。

## 6. 落地检查清单

- [ ] 每条记忆是"声明性事实"且带出处+时间戳?
- [ ] 四层 Memory 各有明确存储与失效信号?
- [ ] 记忆满了时走"合并精简", 且精简结果可回溯?
- [ ] KB 四类目录 (decisions/architecture/bugs/experiences) 已建立并各带索引?
- [ ] 缺陷档案必含"根因+证据等级+预防"?
- [ ] 所有"完成"声明都有独立验证佐证?
- [ ] 新任务开工前按类型检索过 KB?

> 记住: 记忆不是越多越好, 是**越准越好**; 错误不是越多越糟, 是**沉淀越深越好**。
