# AI Software Factory — 迁移方案 (Phase 1-3)

> 角色: 首席架构师。从当前可观测性痛点出发, 把 Hermes + MarkPad 流程逐步演进为 AI Software Factory。
> 原则: **不推翻现有体系**, 三步渐进, 每阶段独立可交付、可回退; KISS; 不绑定具体工具。

---

## 0. 摘要

现状: 体系已能干活 (多 Agent、会话、记忆、归档), 但**看不见、断得痛、信不过、记不牢**。本方案用三个阶段补齐:

- **Phase 1 观察层** (只读不改): 先让系统"看得见"——事件日志、仪表盘、指标。
- **Phase 2 管理层** (形式化): 再让系统"管得住"——任务、Agent、Skill 登记造册。
- **Phase 3 自动层** (自学习): 最后让系统"自己学"——工作流编排完整化、知识自动沉淀。

每阶段不依赖下一阶段, 随时可以停在任意阶段并长期受益。

---

## 1. 现状与痛点 (出发点)

来自实证的四个痛点, 按严重度排序:

| # | 痛点 | 现象 | 代价 |
|---|------|------|------|
| P1 | **可观测性缺失** | 会话进行中不知道 Agent 在做什么、做到哪、成败如何; 只能事后翻聊天记录 | 无法管理、无法审计、无法定位问题 |
| P2 | **截断续跑风险** | 长任务被打断后, 恢复依赖会话 summary; summary 没落盘就白干 | 重复劳动、上下文丢失 |
| P3 | **自报告不可信** | Agent 说"完成了/修好了", 但没有独立证据; 多次被误导 | 假完成、假修复、返工 |
| P4 | **记忆无治理** | 记忆满了不会自动合并; 经验教训散落在会话里, 没有沉淀机制 | 知识流失、重复踩坑 |

**迁移优先级判定**: P1 是一切管理的前提 (看不见就没法管); P2/P3 是直接经济损失; P4 是长期资产损失。因此顺序是: 先观察 (P1), 再管理 (P2+P3), 后自动 (P4)。

---

## 2. 三阶段总览

```
现状 (能干活, 看不见)
  │
  ▼ Phase 1 观察层 (只读不改行为)
  看得见: 事件日志 + 仪表盘 + 指标收集
  │
  ▼ Phase 2 管理层 (行为不改, 结构形式化)
  管得住: Task Manager + Agent Registry + Skill Registry
  │
  ▼ Phase 3 自动层 (行为增强, 可回退)
  自己学: Workflow Engine 完整化 + Knowledge Base 自动沉淀
```

---

## 3. Phase 1 — 观察层: 先看得见

> 本阶段唯一铁律: **只读, 不改任何现有行为**。加"记录"不加"干预"。

### 目标
1. 任何时刻都能回答: "系统现在在做什么? 做过什么? 结果如何?"
2. 为 Phase 2/3 提供数据基础 (没有事件数据, 后面全是空谈)。

### 增加模块

| 模块 | 作用 | 落地要点 (KISS) |
|------|------|------------------|
| **Event Logger** | 记录关键事件流 | 只记六类事件: 任务开始/结束/失败、工具调用、错误发生、停靠点落盘、会话结束。每条 = 时间戳 + 事件类型 + 关联任务 + 一句话摘要 + 证据指针 (日志/产物路径)。追加式写入, 不修改、不删除。 |
| **Dashboard** | 一眼看清状态 | 三块: 进行中的任务 (做什么、多久了)、最近事件流 (倒序)、失败/错误计数。一张表即可, 不搞可视化重活。 |
| **指标收集** | 量化健康度 | 每个任务: 耗时、成功/失败、重试次数、验证是否通过。按天/按会话聚合。 |

### 风险与对策
- **日志噪音**: 只记六类事件, 拒绝"记录一切"; 噪音超了先砍事件类型, 不加过滤规则。
- **存储膨胀**: 事件日志按会话轮转归档, 原始日志可删, 但指标聚合结果保留。
- **性能影响**: 事件写入必须异步、非阻塞; 若影响主流程, 直接降级为采样记录。

### 验收标准 (全部满足才算 Phase 1 完成)
- [ ] 任何会话中途, 能答出"当前在做什么任务、已耗时多久、做过哪些步骤"
- [ ] 任一失败任务, 能回溯到失败前的完整事件链
- [ ] 连续 3 个会话的指标 (成功率/耗时/重试) 可对比
- [ ] 全程未改变任何 Agent 行为 (对照行为基线)

---

## 4. Phase 2 — 管理层: 再管得住

> 行为仍然不改, 但把"谁、什么、怎么"形式化登记, 让恢复与分派有据可依。

### 目标
1. 截断续跑可可靠恢复 (P2): 任务状态是磁盘事实, 不靠会话记忆。
2. 自报告有对照物 (P3): Agent 声称的能力与可靠性, 有登记与评级可核。

### 增加模块

| 模块 | 作用 | 落地要点 (KISS) |
|------|------|------------------|
| **Task Manager** | 任务状态机 + 停靠点 | 状态: `pending → running → done/failed`, 加 `paused` (截断时显式落盘)。每条任务: 目标、当前进度、下一步动作、产物路径。**恢复协议**: 断点续跑只认 Task Manager 落盘的状态 + 产物, 不信任口头 summary; 恢复时先核对产物存在, 不存在则从最近停靠点重做。 |
| **Agent Registry** | 登记 Agent 能力与可靠性 | 每个 Agent 一条: 负责的任务类型、已知强项、已知弱点、可靠性评级。评级来自实证模式 (见 memory-model §5.4): 分析型/实现型(范围清晰)/debug型(首次不可靠→需验证)。评级只升不降需两次独立验证。 |
| **Skill Registry** | 把流程与经验形式化 | 已有 Skill 登记造册: 触发条件、适用任务类型、已知坑。新经验教训 (如"debug 必须验证") 落为 Skill 或 experiences/ 条目, 而不是散在会话里。 |

### 风险与对策
- **过度形式化**: Task/Agent/Skill 三份登记表就够了, 不加第 4 张表; 字段以"恢复和分派用得到"为准, 其他不记。
- **登记表腐化**: 每任务结束顺手更新对应 Agent 评级与 Task 状态; 登记表连续 3 个会话没更新视为腐化, 触发清理。
- **恢复误判**: 恢复协议硬性要求"核对产物存在性", 宁可重做也不信口供。

### 验收标准
- [ ] 模拟截断 3 次, 恢复后均从最近真实停靠点继续, 无重复劳动
- [ ] 每个 Agent 有评级, 且 debug 型任务分派时自动附加"必须独立验证"要求
- [ ] 新会话开工, 能从 Skill Registry 检索到相关流程与已知坑
- [ ] 登记表随每次任务结束自动更新, 无手工维护负担

---

## 5. Phase 3 — 自动层: 最后自己学

> 行为增强开始, 但每个自动化点都可一键关闭 (回退到 Phase 2 状态)。

### 目标
1. Workflow Engine 完整化: 多步任务自动编排、自动检查点、按失败模式自动重试。
2. Knowledge Base 自动沉淀: 错误自动建档、经验自动提炼, 新会话自动带出相关知识。

### 形成内容

| 模块 | 作用 | 落地要点 (KISS) |
|------|------|------------------|
| **Workflow Engine 完整化** | 多 Agent 编排有显式流程 | 流程定义 (步骤、依赖、检查点) + 执行记录 (每步状态/耗时/产物) + 失败策略 (按失败类型: 重试/降级/上报)。检查点沿用 Phase 2 的 Task Manager 状态, 不另起炉灶。 |
| **Knowledge Base 自动沉淀** | 错误与经验自动入库 | 失败任务自动生成缺陷草稿 (事件链→症状→根因线索, 证据等级标 C), 人工/复核确认后升 B/A。经验提炼: 同类失败出现 2 次, 自动提示"这可能是模式, 是否沉淀为经验?"。 |
| **自动检索注入** | 新任务自动带知识 | 开工时按任务类型自动检索 KB 相关条目注入参考。注入内容标注证据等级, 低等级条目只作线索。 |

### 风险与对策
- **自动化误判**: 所有自动生成的 KB 条目默认 C 级, 必须有人复核才升档; 宁可少自动, 不可自动错。
- **失控感**: 每个自动化点独立开关; 上线顺序 = 最无害的先上 (自动检索 → 自动建档 → 自动提炼)。
- **编排死锁**: 工作流必须带超时与手动中断入口; 卡死超过阈值自动降级为人工接管。

### 验收标准
- [ ] 5 步以上的多 Agent 任务可全程自动编排, 任一步失败按策略处理且事件链完整
- [ ] 一次真实失败的调试, 自动生成缺陷草稿, 复核后其根因在后续类似任务中被成功引用
- [ ] 新会话开工自动带出 ≥1 条相关 KB 参考, 且参考不干扰任务 (可忽略性验证)
- [ ] 任意自动化点可一键关闭, 关闭后系统行为退回 Phase 2 且无残留异常

---

## 6. 迁移优先级: 痛点 → 阶段 → 模块

| 优先级 | 痛点 | 解决阶段 | 对应模块 | 见效信号 |
|--------|------|----------|----------|----------|
| 1 | P1 可观测性缺失 | Phase 1 | Event Logger + Dashboard | 中途能答出"在做什么" |
| 2 | P2 截断续跑 | Phase 2 | Task Manager + 恢复协议 | 截断 3 次零重复劳动 |
| 3 | P3 自报告不可信 | Phase 2 | Agent Registry (评级) + 验证要求 | debug 任务完成必带证据 |
| 4 | P4 记忆无治理 | Phase 3 | KB 自动沉淀 + 检索注入 | 同类坑不再踩第二次 |

> 顺序理由: P1 提供数据, P2 需要数据才建得准, P3 需要 P2 的登记与 P1 的事件证据才可核。P4 放在最后, 因为它依赖前两阶段的产物, 且它本身就是"长期收益", 不急在一时。

---

## 7. 落地节奏与退出标准

| 阶段 | 建议周期 | 做完整件事 | 可回退点 |
|------|----------|------------|----------|
| Phase 1 | 1 个迭代 | 六类事件全量可查, 指标可对比 | 停掉 Logger, 系统原样 |
| Phase 2 | 1-2 个迭代 | 三张登记表 + 恢复协议实测通过 | 登记表作废, 回到 Phase 1 行为 |
| Phase 3 | 持续 | 自动沉淀稳定运行 2 周无误判 | 逐个关自动化开关 |

**全局退出标准**: 连续 4 个真实会话满足——可观测 (随时能答状态)、可恢复 (截断零丢失)、可信 (完成声明全部有证据)、可复用 (新坑不再重复)。

---

## 8. 附录: 最小事件集 (Event Logger 的六类事件)

```
task.start     {task_id, 类型, 目标, 开始时间}
task.end       {task_id, 结果(done/failed), 耗时, 产物指针}
task.fail      {task_id, 失败阶段, 错误摘要, 证据指针}
tool.call      {task_id, 工具, 参数摘要, 结果摘要, 耗时}
checkpoint     {task_id, 停靠点描述, 落盘产物清单}   ← 截断续跑的生命线
session.close  {session_id, 事件数, 任务数, 成败统计}
```

每条事件追加写入, 永不修改。**指标 = 事件聚合, 不单独记录**, 避免双写不一致。
