# AI Software Factory — 产品需求文档 (PRD)

> 版本: v0.1 (MVP 草案) | 日期: 2026-08-05 | 状态: 评审中
> 关联文档: [roadmap.md](./roadmap.md) · [phase1-plan.md](./phase1-plan.md) · [design/migration-plan.md](./design/migration-plan.md)

## 1. 背景与痛点

AI 编程已从"单次对话"演进到"多 Agent 协作生产"。实践中暴露四个真实痛点 (按严重度):

| # | 痛点 | 现象 | 代价 |
|---|------|------|------|
| P1 | **可观测性缺失** | 会话进行中不知道 Agent 在做什么、做到哪、成败如何;只能事后翻聊天记录 | 无法管理、无法审计、无法定位问题 |
| P2 | **截断续跑风险** | 长任务被打断后恢复依赖会话记忆,记忆没落盘就白干 | 重复劳动、上下文丢失 |
| P3 | **自报告不可信** | Agent 说"完成了",但没有独立证据;多次被误导 | 假完成、假修复、返工 |
| P4 | **记忆无治理** | 经验教训散落在会话里,没有沉淀机制 | 知识流失、重复踩坑 |

现有工具 (Jira / Jenkins / K8s Dashboard / Confluence) 各自解决一块,但没有一个系统把它们串起来,且都不面向"Agent 员工"这个新生产主体。

---

## 2. 产品愿景与定位

**一句话**: AI Software Factory 是 AI 时代的软件生产操作系统 —— 管理 AI 员工、组织软件生产流程、连接各种 Agent Runtime 的平台。

**它不是**:

- ❌ 不是聊天机器人 (用户不是来对话的,是来交付软件的)
- ❌ 不是单个 Agent (它是管理 Agent 的系统,不是 Agent 本身)
- ❌ 不是代码生成工具 (生成代码只是工作流中的一个环节)

**它的对照**:

```
传统软件体系                     AI Software Factory
-----------                     -------------------
Jira           →  Task Management
Jenkins        →  Workflow Engine
K8s Dashboard  →  Agent Management + Dashboard
Confluence     →  Knowledge System
CI/CD          →  Validation System
```

**核心承诺**: 任何时刻都能回答"系统在做什么、做过什么、结果如何、下一步是什么";任何任务中断后都能从真实断点恢复;任何"完成"声明都有独立验证证据;任何错误都沉淀为工程资产。

---

## 3. 核心原则

1. **不绑定单一模型 / Agent 框架** — Hermes / Claude Code / LangGraph / CrewAI / OpenHands 只是 Runtime 执行器,Factory 通过 Adapter 连接,可插拔。
2. **一切状态必须可观察** — Event Logger 是唯一事实来源 (Single Source of Truth)。
3. **所有执行必须产生 Event** — 没有事件 = 没有发生。
4. **所有完成必须经过 Validation** — Agent 自报告 ≠ 完成。
5. **所有知识必须可沉淀** — 错误 = 工程资产。
6. **支持未来多项目** — MarkPad / Java / Flutter / SaaS / 企业软件,项目是顶层隔离单位。

## 4. 用户画像

| 角色 | 身份 | 核心诉求 | 主要入口 | 常用功能 |
|------|------|----------|:--------:|----------|
| **工程师** | 一线开发者,委派 Agent 干活、验收产物 | 少操心:任务下去能跑,中断能续,失败有原因 | CLI (P0) | 建任务、跑工作流、看日志、查事件链、续跑 |
| **技术负责人** | Orchestrator 角色,拆解目标、分派任务、把控质量 | 看得见:多项目并行时一眼看清谁在干什么、卡在哪 | Dashboard (P1) | 项目总览、任务看板、Agent 面板、质量指标 |
| **管理层** | PO / 决策者,最终验收人 | 信得过:进度、质量、风险有数据支撑,关键决策有闸口 | Dashboard (P1) | 里程碑进度、质量指标、挡板审批 |

优先级:**工程师 (P0) > 技术负责人 (P1) > 管理层 (P1 复用)**。第一版先把工程师的闭环跑通。

## 5. 产品范围:九大模块

| 模块 | 职责 | 对应痛点 |
|------|------|:--------:|
| M1 Orchestrator | 决策中枢:目标拆解、任务审批、结果验收;不写代码 | — |
| M2 Task Manager | 任务状态机 + 断点续传 | P2 |
| M3 Agent Registry | Agent 注册/实例化/统计 (可靠性评级) | P3 |
| M4 Skill Registry | Skill 版本化管理、按角色装配 | P4 |
| M5 Workflow Engine | 可配置流程:决策门、验证门、三挡板、资源锁 | P2/P3 |
| M6 Knowledge Base | 决策/缺陷/经验自动沉淀 | P4 |
| M7 Validation Engine | 独立验证 Agent 产物,产出证据链 | P3 |
| M8 Event Logger | 事件总线,唯一事实来源 | P1 |
| M9 Dashboard | 只读投影,回答"在做什么/卡在哪/下一步" | P1 |

**架构纪律**: 所有模块只通过两条通道交互 —— ① 直接调用 (控制流,上游→下游);② Event Logger (信息流,一切状态变化以事件发布)。模块之间不互读状态,状态一律从事件流投影。

## 6. 核心功能需求

### 6.1 CLI 入口 (P0,工程师主入口)

| 编号 | 功能 | 需求描述 |
|:----:|------|----------|
| F-01 | `factory init` | 初始化项目:创建目录结构、默认配置、初始化事件存储 |
| F-02 | `factory task create` | 创建任务:标题、角色、验收标准、文件范围 (Allowed/Forbidden) |
| F-03 | `factory task list` | 列出任务与状态 (派生自事件流) |
| F-04 | `factory task resume` | 断点续跑:从最近 checkpoint 恢复,核对产物存在性 |
| F-05 | `factory workflow run` | 运行声明式工作流 (feature / bug / release) |
| F-06 | `factory logs` | 查看事件流:按 task / type / 时间过滤,失败可回放完整事件链 |
| F-07 | `factory status` | 当前状态:进行中任务、耗时、最近事件、指标 |

### 6.2 Dashboard 入口 (P1,观察层)

| 编号 | 功能 | 需求描述 |
|:----:|------|----------|
| F-08 | 项目总览 | Active/Blocked 任务数、运行中 Agent 数、里程碑进度、质量指标、最近 10 条事件 |
| F-09 | 任务列表 | 每任务一行:状态/角色/进度/当前动作/上次事件/风险标记 (截断≥阈值、验证失败≥2、越权>0) |
| F-10 | Agent 面板 | 每个 Agent:当前任务、当前动作、工具调用数/上限、历史指标 (first_attempt_success) |
| F-11 | 时间线回放 | 按事件序号回放,可跳转任意 checkpoint 查看当时快照 |
| F-12 | 指标视图 | first_attempt_success / path_errors / human_intervention / 截断率,按天/会话聚合 |

Dashboard 形态第一版为 **Rich CLI 仪表盘 / Markdown 报告**,不做 Web 前端。

### 6.3 API 入口 (P2,未来)

| 编号 | 功能 | 需求描述 |
|:----:|------|----------|
| F-13 | REST API | GitHub Issue → Factory API → 任务 → 工作流 的自动化触发链 (FastAPI) |
| F-14 | 事件订阅 | 外部系统可订阅事件流 (Webhook / SSE),进入后续版本 |

**P2 只做接口预留,不做实现。**

### 6.4 通用能力 (贯穿所有入口)

| 编号 | 功能 | 需求描述 |
|:----:|------|----------|
| F-15 | 事件记录 | 六类最小事件 (task.start / task.end / task.fail / tool.call / checkpoint / session.close),append-only,永不修改删除 |
| F-16 | 指标聚合 | 指标从事件聚合得出,不单独建统计表 (避免双写不一致) |
| F-17 | 验证证据链 | 每次验证产出结论 + 证据指针 (命令输出/diff/测试报告),可回溯 |
| F-18 | 断点恢复 | 恢复只认落盘状态 + 产物存在性核对,不信任口头 summary |

## 7. 非功能需求

| 类别 | 需求 | 验收口径 |
|------|------|----------|
| **可观测** | 任何时刻能答出"当前在做什么、做过什么、结果如何";失败可回放完整事件链 | 中途查询 5 分钟内返回准确状态 |
| **可恢复** | 任意时刻中断,可从最近真实断点恢复,零重复劳动 | 模拟截断 3 次,恢复均从真实停靠点继续 |
| **可扩展** | 新角色/Skill/工作流 = 新增一份声明式文件,零代码改动 | 新增一个角色 ≤ 10 分钟,不改核心代码 |
| **不绑定工具** | Agent 框架/模型可插拔,通过 Runtime Adapter 连接 | 同一任务可切换两种 Runtime 执行 |
| **性能** | 事件写入异步、非阻塞,不影响主流程 | 事件写入对任务执行无感知延迟;压力超限降级为采样 |
| **存储** | 事件日志按会话轮转归档;指标聚合结果长期保留 | 原始日志可删,聚合结果不丢 |
| **安全** | 文件写入范围校验 (越权即拦截并记录) | 越权写入 0 次放行 (由 Validation Engine 保证) |

## 8. MVP 范围

### 8.1 MVP 包含 (Phase 1-2)

1. **Event Logger (核心)**: 六类事件、SQLite append-only 存储、查询/回放、指标聚合。
2. **CLI**: `factory init / logs / status`(以及 task/workflow 的命令骨架)。
3. **Dashboard**: Rich 仪表盘 — 进行中任务、最近事件流、失败计数、指标对比。

> MVP = "先看得见"。**不做任何行为干预**:只记录,不改变 Agent 行为。

### 8.2 MVP 不做 (明确排除)

| 不做 | 原因 |
|------|------|
| Task Manager / Agent Registry / Skill Registry | Phase 3 管理层的活,依赖事件数据先成型 |
| Workflow Engine 完整编排 | Phase 4 |
| Knowledge Base 自动沉淀 | Phase 4,且"人工沉淀"流程可先行 |
| Web 前端 / 微服务 / K8s | 复杂度与价值不匹配,Rich/Markdown 足够 |
| 多项目并行管理 | 数据结构预留 project_id,但第一版只跑单项目 |
| 自研 Agent 框架 / 模型接入 | 只做 Adapter,不绑定任何 Runtime |

### 8.3 技术栈 (第一版)

Python 3.12+ / Pydantic / SQLite / Typer / Rich / FastAPI (仅 P2)。不做微服务、不做复杂前端。

## 9. 成功指标

### 9.1 北极星指标

**任务交付可信率** = 有独立验证证据的完成任务 / 完成任务总数。目标: MVP 结束时 ≥ 90%。

### 9.2 过程指标 (对应四个痛点)

| 指标 | 计算方式 | MVP 目标 |
|------|----------|:--------:|
| 状态可查询率 | 中途能准确答出当前任务状态的比例 | 100% |
| 断点恢复成功率 | 截断后从真实停靠点恢复、零重复劳动 | 3/3 次 |
| 假完成率 | 无证据完成任务 / 完成任务 | ≤ 10% |
| 经验复用率 | 沉淀知识被后续任务引用次数 | ≥ 1 次/周 |

### 9.3 系统指标 (Event Logger 聚合产出)

- `first_attempt_success`: 任务在无失败验证情况下首次完成的比例
- `path_errors`: 越权文件操作计数
- `human_intervention`: 人工介入事件计数 (挡板频率)
- `task_truncation_rate`: 截断事件 / 任务数

### 9.4 里程碑

| 里程碑 | 时间 | 判定 |
|--------|------|------|
| MVP (Phase 1-2 完成) | T+2 迭代 | 六类事件全量可查,指标可对比,CLI + Dashboard 可用 |
| 管理闭环 (Phase 3 完成) | T+4 迭代 | 截断 3 次零重复劳动,Agent 有评级,登记表自动更新 |
| 自学习 (Phase 4 完成) | T+持续 | 自动沉淀稳定运行 2 周无误判 |

## 10. 风险与对策

| 风险 | 对策 |
|------|------|
| 日志噪音膨胀 | 只记六类事件,拒绝"记录一切";噪音超了先砍事件类型,不加过滤规则 |
| 存储膨胀 | 按会话轮转归档;原始日志可删,聚合指标保留 |
| 事件写入拖慢主流程 | 写入异步非阻塞;影响主流程则降级为采样记录 |
| 过度形式化 (Phase 3) | Task/Agent/Skill 三张登记表就够,不加第 4 张;字段以"恢复和分派用得到"为准 |
| 自动化误判 (Phase 4) | 自动生成的 KB 条目默认 C 级,人工复核才升档;每个自动化点独立开关 |
