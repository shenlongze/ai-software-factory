## 1. 流程（Founder 定的四步 + 用户视图）

```
 需求进来
   │
   ├─→ ① 定位    归属（公司/部门/项目）+ 类型（新项目/改现有/问答/一次性）+ 承接（谁提的/谁做）
   ├─→ ② 理解    结构化事实: IDEA / REQ / CONSTRAINT / DECISION …（+ 产品理解快照）
   ├─→ ③ 分析    见 §2（含需求分析 / 需求拆解 / UX 设计 / 架构设计）
   ├─→ ④ 拆解    任务树: 任务 → 子任务 → 子子任务（每叶带承接 / 验收 / 依赖 / 改哪些文件）
   ├─→ ⑤ 用户视图 见 §4（两种呈现: 功能链路图 · 层级待办清单）
   └─→ ⑥ 确认/修改 用户看 → 改 → 确认（★ 不确认很可能做错）
 执行 ⇒ 本次范围之外
```

**为什么"定位"必须在最前**（Founder 明确: "需求进来先定位"）:

```
 · 归属决定: 记忆存哪（全局/项目/部门）· 权限谁能看（跨公司默认拒绝）· 上下文带哪些
 · 类型决定: 走哪条链（要 PRD? 要架构? 还是直接答）
 · 承接决定: ★ 用哪个角色 + **拆到多深**（一个 agent 一次能做多少 ⇒ 决定叶子粒度）
 ⇒ 没有定位, 后面每一步都"不知道站在哪"; 尤其④拆解的粒度**依赖承接信息**。
 ★ 现状差距: 归属靠 `conversation new --project` 手动传（隐式）; 类型/承接**完全没有**。
```

## 3. 两层拆解（Founder: "两层" —— 业务层 vs 执行层）

```
 第一层: 需求拆解（在③分析里）
   · 视角: 业务 —— "这个需求由哪些模块/功能组成"
   · 承接人: 架构师/产品 → 产出业务结构与技术结构

 第二层: 任务拆解（④）
   · 视角: 执行 —— "这些模块/功能要做哪些活、谁做、怎么验收"
   · 产出: 任务树（任务→子任务→子子任务）
   · ★ 输入: PRD + 需求拆解结果 + UX + 架构 + **①的承接信息**（决定粒度）

 ★ 为什么必须分两层: 普通人看不懂"需求拆解"和"架构设计"（Founder 明确）
   ⇒ 所以内部用专业表达, 给用户的是【翻译后的人话表达】（见 §4）。
```

## 4. 用户视图（★ Founder: "还有一个设计, 你没有体现到, 就是用户视图"）

### 4.1 两种呈现, **说的是同一件事**（Founder 强调）

```
 ┌──────────────┬────────────────────────────┬────────────────────────────────────┐
 │ 面向         │ 回答什么问题                │ 形态（能说明白即可）                 │
 ├──────────────┼────────────────────────────┼────────────────────────────────────┤
 │ ① 功能链路图 │ "这个需求包含什么、         │ 脑图 / 流程图 / 表格 —— 只要能把      │
 │   （看关系） │  它们怎么串起来"            │ 【功能 + 关系】说清楚                │
 ├──────────────┼────────────────────────────┼────────────────────────────────────┤
 │ ② 层级待办  │ "具体要做哪些活、           │ 层级清单: 可勾 / 带状态与进度 / 有层级 │
 │   （看进度） │  谁做、做到哪了"            │ （Todo Tree 形态）                   │
 └──────────────┴────────────────────────────┴────────────────────────────────────┘
 ★★ 两者是【同一件事的两种看法】—— 链路图里的"商品管理"点,
    就是清单里的"商品管理"块 ⇒ 必须能互相点过去、互相对得上。
```

### 4.2 由此定下的硬要求

```
 ① 数据源只有一份（专业层）—— 两个呈现是它的两个**投影**, 不是两份数据
 ② 两视图必须能【互相对上】: 链路图的节点 ⇄ 清单的任务块可互相定位
 ③ 改任一处 ⇒ 写回同一份数据 ⇒ **两个投影同时更新**（不需要"回译"）
 ④ 专业层（title 等）与用户视图（display_name）是【翻译关系】:
    专业层是源; 人话层是给用户看的表达; 两处都可改, 改的都是同一份字段
```

### 4.3 呈现形式（Founder 认可: 形式不强求）

```
 · 功能链路图: 现阶段用**表格 / mermaid 流程图**（CLI 可渲染）, 将来 Web 换脑图
 · 层级待办清单: 层级清单（缩进 + 状态图标 + 百分比）
 ★ 关键: 生成规则固定 ⇒ 换载体不改数据, 也不会让两个视图不一致
```

## 5. 同一份数据（任务节点）—— 只加 3 个字段

```
 ┌──────────────┬──────────┬────────────────────────────────────────────────┐
 │ 字段          │ 现状      │ 说明                                            │
 ├──────────────┼──────────┼────────────────────────────────────────────────┤
 │ id            │ ✅ 有     │ 节点标识                                        │
 │ kind          │ ✅ 有     │ project / domain / task                         │
 │ parent_id     │ ✅ 有     │ ★ 层级: 任务→子任务→子子任务靠它                  │
 │ title         │ ✅ 有     │ 专业名（"实现分类树、SPU/SKU 查询与详情…"）       │
 │ ★ display_name│ ✗ 缺     │ ★ 人话名（"商品管理"）—— 用户视图就靠它           │
 │ depends_on    │ ✅ 有     │ 依赖 ⇒ 链路图的**边**就靠它画                     │
 │ acceptance    │ ✅ 有     │ 验收标准 ⇒ ★ "能不能一句话写出来"决定该不该再拆     │
 │ required_caps │ ✅ 有     │ 需要什么能力（= 谁能做）                         │
 │ ★ assignee    │ ✗ 缺     │ ★ 明确"谁在做"（现只有"需要什么能力"）             │
 │ status        │ ✅ 有     │ 状态（待办/进行中/完成）                        │
 │ progress      │ ✗ 缺     │ ★ **派生值, 不落字段** —— 完成度完全由子节点的 status 决定 ⇒
│ (派生)       │          │   若存成字段会出现"存的值"与"算的值"不一致（一数据一权威源）│
 │ expected_files│ ✅ 有     │ 要改哪些文件（执行用, 用户视图不显示）            │
 │ scope         │ ✅ 有     │ 描述                                            │
 └──────────────┴──────────┴────────────────────────────────────────────────┘
 ★ 只补 2 个字段（display_name / assignee）+ 1 个派生值（progress）⇒ 不推翻现有任务树。
```

## 6. 两个投影的生成规则（都只读 §5, 不再加字段）

```
 功能链路图:
   · 节点 = kind=domain 的节点 → 显示 display_name
   · 边   = depends_on（读成"前置关系"）
   · 分层 = parent_id（可折叠）
   · 主次 = 被依赖次数（被多人依赖 ⇒ 核心）

 层级待办清单:
   · 行   = kind=task 的叶 → 显示 display_name, 缩进体现 parent_id
   · 勾选 = status（☐ 待办 / 🚧 进行中 / ✅ 完成）
   · 百分比 = progress（父节点由子节点聚合）
   · 谁做 = assignee（无 ⇒ 显示"待派"）
```

## 7. 改动写回（三种改法）

```
 ┌────┬────────────────────────┬──────────────────────┬──────────────────────┐
 │ #  │ 用户在哪改              │ 写回字段              │ 举例                  │
 ├────┼────────────────────────┼──────────────────────┼──────────────────────┤
 │ ①  │ 清单里改【人话名】       │ display_name          │ "商品管理"→"商品与分类" │
 │ ②  │ 清单里改【做不做/怎么做】 │ title / acceptance /  │ "建商品表"→"导入已有表" │
 │    │ （语义改动）             │ parent_id（拆分/合并） │                      │
 │ ③  │ 链路图里改【功能关系】    │ depends_on            │ 让"支付"不再依赖"库存" │
 └────┴────────────────────────┴──────────────────────┴──────────────────────┘
 ⇒ 任一处写回 ⇒ 两个投影同时更新（同一份数据）✓
```
