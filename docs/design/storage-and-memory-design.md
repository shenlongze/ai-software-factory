# AI Factory OS — 存储与记忆设计

> 状态: 设计 (Design) | 日期: 2026-09-19 | 决策人: Founder | 落地状态: 见 §6 分期
> 一句话: **不可派生的才「记」, 可派生的只「算」; 每个数据只有一个权威源。**

---

## 0. 总纲: 一条原则推出全部设计

```
数据按【能否从别的数据重建】分为两类:

  ① 不可重建的 ⇒ 必须【记】（丢了就永远没有）
       例: 决策与理由 · 任务意图依赖 · 运行事实(执行顺序) · 人的产物文档
  ② 可重建的   ⇒ 只【算】（每次现算, 或建可丢弃的索引加速）
       例: 调用关系 · 依赖图 · 模块结构 · 测试映射 · 检索索引

由这条原则推出的三条纪律:
  D1  每个数据只有一个【权威源】—— 冲突时以它为准, 其余都是派生
  D2  可派生的**禁止记成账本** —— 代码改了账本没改 ⇒ 两套账 ⇒ 比不记更糟
  D3  并发只发生在权威源上 —— 派生视图可以随便重建, 不需要并发保护
```

**这条原则同时回答了三个先前的问题**: 存哪(§1) · 记什么(§2) · 怎么改全(§3)。

## 1. 三个真相源(存储分层)

| 真相源 | 管什么 | 为什么是它 | 现状 |
|---|---|---|---|
| **git** | ① 人的产物**内容**(代码/文档/PRD/报告)<br>② **决策与理由**(commit message) | 天然带: 版本 · 回溯 · diff · 可审计 · 人可读 | ⚠ 本仓有 1,935 提交;<br>★ **项目的 workspace 无 git** ⇒ 产物历史丢失 |
| **SQLite** | **运行时状态**(任务树/调度/执行/会话元数据/事件) | 高频改写 + 多 agent 并发 + 要查 ⇒ 只有它扛得住<br>实测: WAL 下 4 写入方 × 300 零丢失 | `factory.db`(WAL ✓, 9,203 事件)<br>`search.db`(**delete ✗**, 应改 WAL) |
| **文件** | **配置**(org / 项目配置 / 工作区) | 人要手改 · 要 git 管 · 是"设定"不是"事实" | 1,677 个 JSON |

### 1.1 三层结构(权威 → 派生)

```
   ┌─ 真相层 ──────────────────────────────────────────────┐
   │ git(内容+决策)   ·   SQLite(状态)   ·   文件(配置)      │
   └───────────────────────┬──────────────────────────────┘
                           │ 派生(可丢弃 · 可重建 · 不保护并发)
   ┌───────────────────────▼──────────────────────────────┐
   │ ① 索引: search.db / FTS5（已有 10,176 篇）             │
   │ ② 图谱: repo_intelligence 7 层（现算, 不落库）         │
   │ ③ 视图: 人的可读导出（报告 / HTML / 摘要）             │
   └──────────────────────────────────────────────────────┘
```

### 1.2 判据(给每一份新数据用)

```
问 3 个问题:
  Q1 它能不能从别的数据重算?     能 ⇒ 派生(不记)
  Q2 它会被高频改写 / 并发写吗?   会 ⇒ SQLite
  Q3 人要手改 / 要 git diff 吗?   要 ⇒ 文件(内容/配置)

判定表:
  可重算                              ⇒ 派生：现算或建可丢弃索引
  不可重算 + 高频/并发/要查            ⇒ SQLite 表
  不可重算 + 是内容(文档/代码)         ⇒ git 管文件
  不可重算 + 是人要改的设定            ⇒ 文件（非 git 内容）
```

### 1.3 ★ 反例: 为什么不能"按判据分流了事"

```
曾经想过: nodes/artifacts/workflows 放 SQLite, PRD/配置放文件 ⇒ 完事。
错在哪: 它只回答了"放哪", 没回答【谁说了算】——
        同一个 artifact 有"文件"和"库里的登记"两份, 改了文件没改登记 ⇒ 谁对?

⇒ 正确做法: 内容与登记**天然分家**, 各有一个权威
   · artifact 的【内容】(PRD 正文/代码)  → git 管文件  = 权威
   · artifact 的【登记】(id/归属/时间/路径/sha) → SQLite = 权威
   · 二者用 sha256 绑定 ⇒ 内容改了能发现登记过期（不是"两套账", 是"两件事"）
```

## 2. 记忆设计(项目级记忆)

### 2.1 不记全量代码(为什么)

```
· 代码在磁盘 + git 里, 随时可读可 grep ⇒ 重复保存毫无价值
· 500 万行项目实测: 全量索引库 49MB / 查询毫秒级 ⇒ 存得下, 但**没必要**
· 真问题不是"记不住代码", 而是"记不住【关于代码的知识】"
```

### 2.2 记什么(四类, 按不可重建性排序)

| 类别 | 内容 | 权威源 |
|---|---|---|
| **决策与理由** | 为什么这么分层/为什么否掉 B 方案 | ★ git commit + 关键决策落 SQLite |
| **任务链** | 意图依赖（谁必须先做） | SQLite（已有 `depends_on`）|
| **运行事实** | 执行顺序 / 谁在何时做了什么 / 结果 | SQLite（已有 events, append-only）|
| **知识文档** | README / PRD / 设计文档 / 经验教训 / CHANGELOG | git 管文件 + **派生**检索索引 |

### 2.3 索引规则(现在缺的就是这个)

```
现状: `.factory_rag` 已建(29,463 片段 / 10MB / 695 文件), 但:
  ✗ 噪音混入: package-lock.json(641 片段) · acl-manifests(510) · desktop-schema(505)
  ✗ 过期:     仍索引 factory-exec(2,934) / factory-console(560) —— 老区已删
  ✗ 无消费:   knowledge_store 只有 re-export, 没有真调用方（检索了没人读）

规则:
  R1【白名单】只索引: README · CHANGELOG · PRD · 设计/架构文档 · 决策记录(ADR) ·
                      经验/教训/最佳实践 · 项目说明
  R2【排除】不索引: `*-lock.json` · `*manifest*` · `*schema*` · 生成物 · 构建产物 ·
                    二进制 · 依赖目录(node_modules/site-packages)
  R3【新鲜度】索引前校验来源仍存在; 增量按 mtime, 删掉的源要清片段
  R4【分档即优先级】检索排序 knowledge > summary > raw; 单文件片段设上限
                    (现状"一个方案书占 2,720 片段"会挤满结果)
  R5【必须被消费】接进 ContextResolver 的 retrieval 步 ⇒ agent 干活时真拿到
```

### 2.4 记忆的读取路径(这才叫"不忘")

```
开工时三样拼出项目全貌:
  ① git log --oneline        → 做过什么 + 为什么      （决策记忆）
  ② SQLite 状态表 + 事件      → 现在到哪 / 谁在做什么   （现状记忆）
  ③ FTS5 检索(按 §2.3 规则)  → 相关细节               （细节记忆）
⇒ 完全不依赖 LLM 上下文窗口 ⇒ 时间再长也不忘
```

### 2.5 作用域(已实现, 见清单第 9 组)

```
归属: 全局 < 公司 < 部门 < 项目（线性四级, 每事实只存一份）
可见: 同公司横向可达; 跨公司 Default Deny
继承: 自下而上 + 同槽下层顶替 + provenance 可解释
⇒ scoped_facts 已落地并通过实测（市场部读到 IT 部门事实 ✓ / 跨公司无泄露 ✓）
```

## 3. 影响面设计(「改全」怎么保证)

### 3.1 前提: "改全"没有 100% 保证

```
动态语言里存在静态看不见的引用(字符串/反射/运行时注入/外部消费者)。
⇒ 设计目标不是"保证不漏", 而是:
   ① 用四通道把覆盖率最大化
   ② 让"漏了会暴露"(编译/测试)
   ③ ★ 把【可能漏了什么】显式写出来 —— 从"隐形风险"变成"可见清单"
```

### 3.2 四通道

| 通道 | 手段 | 抓什么 | 现状 |
|---|---|---|---|
| **① 静态精确** | AST / 调用图（符号全名 = 模块.类.方法） | 真调用边 / 继承 / 导入 | ⚠ `repo_intelligence` 是**正则级** ⇒ 实测把被调用者当调用者(假阳性) |
| **② 文本兜底** | 全仓 grep + 排除同名异物 | 字符串 / 配置 / YAML 路由 / 文档 / 注释 | 有工具(`code_search`) |
| **③ 行为契约** | 签名 diff + 测试覆盖 | 返回值/副作用/异常语义变了影响谁 | ✗ 无 |
| **④ 非代码引用** | 检索知识索引 | 文档 / PRD / 决策记录 | 有索引(待按 §2.3 清) |
| **⑤ 验证** | 编译 / 测试 / 验收判据 | 唯一能证明"改全"的 | ⚠ `plan.acceptance` 无消费方 |

### 3.3 精度升级(唯一必须做的技术改动)

```
正则级 → AST 级:
  · Python 用标准库 `ast` ⇒ **仍是零依赖**（与现有"零第三方静态分析库"的纪律一致）
  · 产出: 定义(全名) / 调用边(from→to, 带文件行号) / 继承边 / 导入边
  · 验收: 对同一个符号, AST 结果与"人工核对"一致; 正则级的已知假阳性消失
```

### 3.4 交付物: `factory change plan <符号>`

```
factory change plan conversation.upsert_fact     ← 只分析, 不改动
输出:
  [定位] conversation.upsert_fact（全名）—— ★ 与 scoped_facts.upsert_fact 区分
  [静态] 调用方 5 处（proposal.py ×5）· 继承 0 · 导出 0
  [文本] 字符串/配置命中 0 · 文档引用 3 处
  [行为] 签名未变 ⇒ 影响面 = 调用方 5 处
  [测试] 覆盖 0 处 ⇒ ⚠ 无测试保护
  [建议] 改后验证: scripts/verify.sh + 端到端 conv 用例
  [风险] 无测试覆盖 ⇒ 需人工核对这 5 处

⇒ 然后才 factory change apply（按清单逐处改 + 验证）
⇒ ★ 影响面清单落进 commit / 事件 ⇒ 下次"为什么改了这些"有据可查
```

## 4. 链的归属表(记 vs 算, 一张表定死)

| 链 | 可派生? | 归属 | 现状 |
|---|---|---|---|
| 功能模块结构 | ✓ 目录/包 | **算**（L2） | 已有 |
| 调用关系 | ✓ AST | **算**（L5） | 已有(正则级, 升 AST) |
| 依赖图 | ✓ import | **算**（L3） | 已有 |
| 测试映射 | ✓ 命名/import | **算**（L6） | 已有 |
| 架构上下文 | ✓ 启发式 | **算**（L7） | 已有 |
| **任务链** | ✗ 是意图 | ★ **记**（SQLite） | 已有 `depends_on` |
| **执行顺序/阶段** | ✗ 运行时才有 | ★ **记**（events） | 已有 |
| **决策与理由** | ✗ 人的判断 | ★ **记**（git + SQLite） | ⚠ 只靠 commit message |
| **数据链** | 拆开 | **意图记**（PRD→设计→任务→产物）· **实际流算**（L3 + `artifact_refs`） | 部分 |

## 5. 设计的自我约束(边界)

```
· 不用 PgSQL（单机场景过重, 实测 500 万行索引仅 49MB ⇒ SQLite 足够）
· 不引入第三方静态分析库（ast 是标准库）
· 不搞事件溯源的重型投影（Phase 2 再考虑; 现在 state 用表 + events 记账足够）
· 不记可派生的东西（D2）—— 这是本设计最容易违反、也最致命的一条
```

## 6. 落地分期

### 阶段 1（解决真实风险, 优先级最高）

| # | 动作 | 验收标准 |
|---|---|---|
| 1 | `search.db` 改 WAL | `pragma journal_mode` = wal |
| 2 | 事件源分层: "查看类"事件(console.viewed 6,685 条)不入真相层 | 真相层里无查看类噪音 |
| 3 | 项目产物纳入 git（`projects/*/workspace`） | `git -C workspace log` 有历史 |
| 4 | 知识索引按 §2.3 R1–R4 重建 | 噪音 0 · 过期 0; 检索命中质量人工抽检通过 |
| 5 | 知识检索接进 ContextResolver（R5） | agent 一次任务中真用到检索结果（事件可见）|

### 阶段 2（把"改全"做实）

| # | 动作 | 验收标准 |
|---|---|---|
| 6 | `repo_intelligence` 升 AST 级 | 已知假阳性消失; 与人工核对一致 |
| 7 | `factory change plan` 上线 | 对一个真符号输出完整影响面清单 |
| 8 | `plan.acceptance` 接消费方 | 验收判据真被读、真能判"完成" |

### 阶段 3（等规模来）

```
· 运行时状态(nodes/artifacts 登记/workflows)迁 SQLite（现在 1,677 个 JSON 尚可承受）
· 状态表升级为 events 的投影（reducer + 快照）—— 那时"回放/重建"才有价值
· facts 规模过几百条后, 启用 FTS5 检索层（清单 tsc-4/刀3b）
```

## 7. 一句话总览

```
记的:   决策与理由 · 任务链 · 运行事实 · 人的产物与知识文档
算的:   调用关系 · 依赖 · 模块结构 · 测试映射 · 各种索引
权威:   git(内容+决策) · SQLite(状态) · 文件(配置) —— 各管一摊, 互不越界
不改全的唯一解: 现算(AST) + 兜底(grep) + 验证(测试) + ★ 显式列风险
```
