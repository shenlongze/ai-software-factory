> 一句话: **事件是唯一真相; 状态、索引、记忆、影响面、文件全都是它的投影。**

## 0. 【已作废·2026-09-19】先收敛, 再设计

> ★ **本节被实测推翻, 保留作教训记录。** 原内容主张"store 类从 24 收敛到 ≤3"。
>
> **为什么作废（Founder 连问四次"这么做的是对的么 / 这回对么"逼出来的）**:
> 「24 个 store / 5 套机制 / 8 处多写入方」这些数字是**我数出来的, 不是 Founder 的痛点**;
> 我从"数字不好看"推出"该收敛", 再花四轮纠结"怎么收敛" —— 这是**给自己造活**,
> 违反 Founder 定的两条铁律: 「只问现在谁在用」「'将来可能用'不是保留理由」。
>
> **实测反证（决定性）**:
> · 所谓"9 组同名异物"里, 6 组是**不同数据空间**各自的实现（符合域隔离 R3）⇒ 合并会破坏边界
> · 所谓"8 处多写入方": `approvals.json` 在 exec/ 与 org/ **都不存在**（根本没用过）;
>   `artifacts.json` 3 处在**不同路径**、格式一致 `{"artifacts": ...}` ⇒ 无覆盖、无不一致
> · ⇒ **无任何实际症状**
>
> **正确做法（替代原"收敛目标"）**:
> · **不设数量目标**（store 类多不等于有问题）
> · 只在出现**实际症状**时动手: 同一份数据被覆盖 / 格式不一致 / 读出错
> · 判据必须**可靠**: 静态扫描（grep 文件名）会误判 —— 实测出两类假阳性
>   （异常类的错误消息被当"写入方"、把"读"当"写"), 且同根也只能到"疑似"（写动作可能在基类）
> ⇒ 真要判, 需**运行时证据**（在唯一落盘点记录"谁写了哪个文件"）, 而不是 grep。



```
★ 本设计不是"再设计一套存储", 而是"让存储只有一个地方定义"。

【实测的病（2026-09-19）】
  · Store/Index/Memory 类: ★ 24 个（散落 infrastructure/services/plugins）
  · 数据落地:               ★ 8 处
      projects/*/conversations(110) · knowledge(0, 空) · .factory_rag(11M) ·
      search.db(26M) · factory.db(4.1M) · org(676K) · memory(652K) · ops(10M)
  · 同名异物: KnowledgeStore ★ 两个不同实现
      (infrastructure/retrieval/knowledge_store.py:378 与 services/organization/store.py:260)
      + KnowledgeItem 是第三个概念
  · "记忆/知识/事实"机制: 五套彼此不通
      (会话 facts · scoped_facts · .factory_rag · search.db FTS5 · org 知识条目)

【结论】病灶是"做好几套"。所以本设计的第一动作是**收敛**, 不是新增。

【三件 + 一张表 + 一条纪律】
  ① 事件源 = 唯一真相（append-only · WAL · 已有 factory.db）
  ② 投影层 = 所有视图（状态/索引/记忆/影响面）—— ★ 一个机制, 不是 24 个 store
  ③ 配置   = 唯一例外（设定 ≠ 事实 · 文件 + git）

  ★ 一张表: 什么数据在哪 / 谁权威 / 怎么改 —— **全系统只有这一张**, 不是每处各设计一次

  ★ 一条纪律: 新增任何存储前, 先问「能不能用【事件 + 投影】表达?」
       能 ⇒ **不许新增 store**; 不能 ⇒ 才允许, 并写进那张表

【收敛的验收标准（可量化）】
  Store/Index/Memory 类:  24 → ≤ 3
  数据落地处:              8 → 3
  同名 KnowledgeStore:     2 → 1（合并或明确分工）
  "记忆/知识"机制:         5 套不通 → 1 套

【收敛方式】不做"大迁移"（那会造出新的一套）:
  新增走新机制 + 旧的自然淘汰; 每淘汰一个, 上面四个数字减一。
```

## 0.1 总纲: 一个概念, 一条纪律, 一个例外

```
【一个概念】事件（append-only）
【一条纪律】谁都不许直接改写状态; 只能追加事件, 状态由投影产生
【一个例外】配置 —— 它是"设定"而不是"事实", 留在文件 + git
```

**为什么这是最本质的**: 前面几轮设计("三个真相源 + 记/算判据 + 四条索引规则 + 四通道")
的复杂度是**永久的** —— 每新增一种数据都要再判一次"放哪 / 谁权威 / 要不要索引";
而"一个真相 + 投影"的复杂度是**一次性的** —— 追加事件, 需要哪个视图就投影哪个。

**AIF 已经具备全部基础设施**(实测):

| 能力 | 现状 | 位置 |
|---|---|---|
| append-only 事件存储 | ✅ **双层保证**: 应用层只暴露 append/query_*(**无 update/delete 方法**)<br>+ 数据库层 **BEFORE UPDATE/DELETE 触发器物理拒绝** | `infrastructure/events/store.py` |
| 回放锚点 | ✅ `seq` 单调递增, 自述即"回放锚点" | 同上 |
| 回放 | ✅ `replay(events) → ReplayedState` | `services/execution/recovery/replay.py:70` |
| 并发 | ✅ WAL + 单连接 RLock | 同上 |
| 派生索引 | ✅ FTS5 索引 event 8,995 / trace 1,030 … | `search.db`(10,176 篇) |
| 规模 | 9,203 条事件 · 4 MB | `factory.db` |

**唯一缺的**: 状态还不是事件的投影（各个模块各写各的: 文件 / 表 / 双写)。

## 1. 一个真相 + 投影

```
                    ┌──────────────────────────────┐
                    │  事件流（唯一真相）            │
                    │  append-only · WAL · 双层保证  │
                    │  factory.db: events (9,203)   │
                    └───────────────┬──────────────┘
                                    │ 投影（可重建 · 可丢弃 · 不保护并发）
      ┌──────────────┬──────────────┼──────────────┬──────────────┐
      ▼              ▼              ▼              ▼              ▼
   状态视图       检索索引        记忆视图       影响面视图      文件视图
 (物化表)      (FTS5, 已有)   (知识/决策)    (代码 + AST)   (人可读导出)
  落库·增量      落库·增量       落库·增量       ★现算不落库     导出·非权威
```

### 1.1 投影的两类(这是"记 vs 算"的真正表述)

```
落库型投影（值得缓存, 因为重算贵或要查询）
   · 状态视图:   任务树 / 调度 / 执行状态 / 会话元数据
   · 检索索引:   FTS5（已有）
   · 记忆视图:   知识文档 + 决策 + 任务链（以事件形式入库）

现算型投影（重算便宜, 落库反而会过期）
   · 影响面/调用图/依赖/模块结构/测试映射 —— 自述"零数据库 · 确定性 · 现算"
   · ★ 落库它们 = 必然过期 ⇒ 两套账（D2）
```

### 1.2 状态视图怎么建(投影器)

```
每个视图一个 reducer:  events → 状态
  · 从 seq 单调推进; 记 last_applied_seq
  · 幂等: 同 seq 重放不改变结果
  · 可重建: 删掉视图表, 从 seq=0 重放到当前 ⇒ 一致
  · 快照: 事件多了以后按 seq 存快照, 重放从最近快照起（现在 9,203 条, 不需要）
验收: 重建后的视图与重建前**逐字节一致**
```

### 1.3 并发: 从"解决"变成"不存在"

```
只追加 ⇒ 没有"两个写者改同一行" ⇒ 竞争从设计上消失
实测(WAL, 同机): 2 写者零等待 · 4 写者零等待 · 8 写者 1600/1600 零丢失 ·
                 4 写者 + timeout=0.05s 仍零错误
⇒ 引擎层已足够; 不需要更强的引擎(那会解决我们还没有的问题, 并违背"单机"边界)
将来真需要更大并发: 按作用域分库(每公司/项目一库), 每库仍是单写者 ⇒ 线性扩展
```

### 1.4 唯一例外: 配置

```
配置是"设定"不是"事实": org 结构 / 项目配置 / 工作区设定
  · 人要手改 · 要 git diff · 不是"发生了什么"
⇒ 留文件 + git; 变更时发一次事件（为了审计轨迹）, 但文件是权威
```

### 1.5 ★ 修掉已存在的违规(自查)

```
违规 1: facts 有两个写入方 —— ① 会话文件(understanding.upsert_fact) ② scoped_facts(同步双写)
  定案: 事实变更 = 一条事件; **scoped_facts 是 facts 的投影视图**(不是第二个权威)、
        会话内的 facts 也是投影; 两者都由事件重建
违规 2: scoped_facts.upsert_fact 现在是 `read_layer → kept.append → write_text(全量)`
  ⇒ 与"JSON 并发丢 59%(实测)"同一个病
  修法: 改为"追加事实变更事件 + 投影"（或至少真加锁 + 唯一临时名）
违规 3: 状态散落在 1,677 个 JSON（nodes 553 / artifacts 408 / workflows 391 …）
  ⇒ 逐步改为投影视图（不是一次全搬: 见 §6 分期）
```

## 2. 记忆设计

### 2.1 记什么: 事件本身

```
"记忆"= 事件流里那部分【不可从别处重建】的东西:
   · 决策与理由   → 一条 decision 事件（为什么这么定 / 否掉了什么）
   · 任务链       → 事件的因果: 谁产生了谁（depends_on 是它的投影）
   · 运行事实     → 执行顺序/结果（已有 org.execution.* / org.stage.*）
   · 知识文档     → 文档入库事件（README/PRD/设计/经验/CHANGELOG）
不记:
   · 代码本身     → 在磁盘 + git, 随时可读可 grep（500 万行实测: 全量索引 49MB 但没必要）
   · 可派生的关系 → 调用/依赖/模块/测试映射（现算）
```

### 2.2 索引规则(投影实现细节)

```
现状: `.factory_rag` 已建(29,463 片段 / 10MB / 695 文件), 但:
  ✗ 噪音: package-lock.json(641) · acl-manifests(510) · desktop-schema(505)
  ✗ 过期: 仍索引 factory-exec(2,934) / factory-console(560) —— 老区已删
  ✗ 无消费: knowledge_store 只有 re-export, 没真调用方

规则:
  R1 白名单: README · CHANGELOG · PRD · 设计/架构 · 决策(ADR) · 经验/教训 · 项目说明
  R2 排除:   *-lock.json · *manifest* · *schema* · 生成物 · 构建产物 · 二进制 · 依赖目录
  R3 新鲜度: 索引前校验来源仍存在; 按 mtime 增量; 源删了要清片段
  R4 分档即优先级: knowledge > summary > raw; 单文件片段上限
  R5 必须被消费: 接进 ContextResolver 的 retrieval 步（否则建了没人读）
```

### 2.3 读取路径(这才叫"不忘")

```
开工时三样拼出项目全貌:
  ① 事件流回放/查询  → 做过什么 + 为什么      （决策记忆）
  ② 状态视图         → 现在到哪 / 谁在做什么   （现状记忆）
  ③ FTS5 检索        → 相关细节               （细节记忆）
⇒ 不依赖 LLM 上下文窗口 ⇒ 时间再长也不忘
```

### 2.4 作用域(已实现)

```
归属: 全局 < 公司 < 部门 < 项目（线性四级 · 每事实只存一份）
可见: 同公司横向可达; 跨公司 Default Deny
继承: 自下而上 + 同槽下层顶替 + provenance 可解释
现状: scoped_facts 已落地实测（市场部读到 IT 部门事实 ✓ / 跨公司无泄露 ✓）
      —— 按 §1.5 它要改为投影视图, 语义不变
```

## 3. 影响面(「改全」怎么保证)

### 3.1 前提

```
动态语言里存在静态看不见的引用（字符串/反射/运行时注入/外部消费者）
⇒ 目标不是"保证不漏", 而是:
   ① 四通道把覆盖率最大化  ② 让"漏了会暴露"(编译/测试)
   ③ ★ 把「可能漏了什么」显式列出 —— 从隐形风险变成可见清单
```

### 3.2 四通道

| 通道 | 手段 | 抓什么 | 现状 |
|---|---|---|---|
| ① 静态精确 | AST（符号全名 = 模块.类.方法） | 真调用边 / 继承 / 导入 | ⚠ 正则级 ⇒ 实测把被调用者当调用者 |
| ② 文本兜底 | 全仓 grep + 排除同名异物 | 字符串 / 配置 / 路由 / 文档 / 注释 | 有工具 |
| ③ 行为契约 | 签名 diff + 测试覆盖 | 返回值/副作用/异常语义变了影响谁 | ✗ 无 |
| ④ 非代码引用 | 检索知识索引 | 文档 / PRD / 决策 | 有索引（待按 §2.2 清）|
| ⑤ 验证 | 编译 / 测试 / 验收判据 | 唯一能证明"改全"的 | ⚠ `plan.acceptance` 无消费方 |

### 3.3 唯一技术改动: 正则级 → AST 级

```
Python 标准库 `ast` ⇒ 仍零依赖（与"零第三方静态分析库"的纪律一致）
产出: 定义(全名) / 调用边(from→to, 带文件行号) / 继承边 / 导入边
验收: 同一符号 AST 结果与人工核对一致; 已知假阳性消失
```

### 3.4 交付物: `factory change plan <符号>`

```
factory change plan conversation.upsert_fact        ← 只分析, 不改
  [定位] conversation.upsert_fact（全名）—— ★ 与 scoped_facts.upsert_fact 区分
  [静态] 调用方 5 处 · 继承 0 · 导出 0
  [文本] 字符串/配置 0 · 文档引用 3 处
  [行为] 签名未变 ⇒ 影响面 = 调用方 5 处
  [测试] 覆盖 0 处 ⇒ ⚠ 无测试保护
  [建议] 改后验证: scripts/verify.sh + 端到端 conv 用例
  [风险] 无测试覆盖 ⇒ 需人工核对这 5 处
⇒ 之后才 factory change apply; ★ 影响面清单作为事件入库 ⇒ 下次"为什么改了这些"有据可查
```

## 4. 设计的自我约束

```
· 不用 PgSQL（单机过重; 实测 500 万行索引仅 49MB ⇒ SQLite 足够）
· 不引入第三方静态分析库（ast 是标准库）
· ★ 不把可派生的东西落库（现算; 落库必然过期 ⇒ 两套账）
· 不做"多规则"设计（规则要人维护 ⇒ 永久成本）; 宁可一个概念 + 投影
· 配置是唯一例外（设定 ≠ 事实）
```

## 5. 一套规则解决四个问题

| 问题 | 在这个设计里的答案 |
|---|---|
| **存哪** (文件 / SQLite) | 事件进 SQLite; 文件是导出（非权威）; 配置留文件 |
| **记什么** (时间长了会忘) | 事件流里的不可重建部分（决策/任务链/运行事实/知识）|
| **怎么改全** | 影响面 = 代码事件投影 + AST 现算; 显式列风险 |
| **要不要记各种链** | 全是投影 —— 落库型(状态/索引/记忆) 或 现算型(代码关系) |

## 7. 一句话总览

```
真相:   事件（append-only · WAL · 双层保证 —— 全是 AIF 已有的）
派生:   状态 / 索引 / 记忆 / 影响面 / 文件 —— 全是事件+代码的投影
纪律:   只追加, 不改写状态
例外:   配置（设定不是事实）
收益:   并发/一致性/权威之争 三个问题一起消失; 新增数据不用再决策
```
