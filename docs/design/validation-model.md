# Validation 模型 (validation-model)

> 通用 AI Software Factory 的验证体系:双验证机制、门禁、自动化指标与质量基线。
> 核心公理来自实证:**Agent 的自报不等于事实**;自动化命令的通过也不等于功能完成。
> 本模型从 Hermes + MarkPad 实践归纳,与具体工具无关。

---

## 1. 核心公理

1. **自报 ≠ 事实**:Agent 可能声称"文件已创建""测试通过"而实际相反(实证高频事故:
   文件写到临时目录、测试未运行、自验通过的是无关用例)。
2. **CLI PASS ≠ 功能完成**:静态检查/自动测试全绿,不代表真实运行可用(实证:759 个测试
   全过、0 编译错误,但 12 个新方法在真实使用中全部静默失效;6 个渲染缺陷全过自动测试)。
3. **验证必须独立**:执行者不得自我验证自己的产出;验证结论必须可复现、有证据。
4. **验证要有证据链**:每个"通过"都要可回查(命令输出、文件存在性、符号匹配、用户实测记录)。

---

## 2. 双验证机制(形式化)

每个委派任务的验证由两个独立环节组成,**两者都通过才算完成**:

```
Agent 自报(Self-Report) ──┐
                          ├──→ 一致性判定 → 通过 → 记录归档
协调器独立验证(Independent) ─┘                 └→ 不通过 → 打回(1 修复 / 2 换法 / 3 上报)
```

### 环节 A:Agent 自报(输入)

按 agent-model §5.1 格式提交:完成项 / 文件变更 / 已运行的验证与输出 / 未完成项。
自报是**验证的输入**,不是结论。

### 环节 B:协调器独立验证(判定)

协调器必须**亲自重跑**,不得引用 Agent 输出作为证据:

| 验证级别 | 内容 | 判定方式 |
|:--------:|:-----|:---------|
| **L1 静态** | 文件存在于预期绝对路径;符号存在/消失;静态检查命令通过 | `ls` 预期路径、精确匹配(grep/命令退出码)、重跑静态检查 |
| **L2 构建/测试** | 构建命令成功;测试套件结果与基线对比 | 独立执行构建与测试,解析真实输出 |
| **L3 用户实测** | 真实运行的应用上按验收场景操作 | 用户(或受控操作)实测,禁止 Agent 代报视觉通过 |

**独立验证的取证纪律**:
- 文件存在性:在**预期绝对路径**检查(防止"创建了但没在项目里")。
- 内容断言:用精确匹配(grep / 命令退出码),**禁止**用带行号前缀的格式化阅读视图做判定
  (实证:14/29 个合法断言因此误判失败)。
- 多修复验证:Agent 声称修了 N 处,必须**逐条**取 grep 证据(新增符号出现、删除符号消失),
  把自报当清单核对,而不是只看"检查通过"(实证:报 7 处修复实际 1 处未写、1 文件被误还原)。
- 中断任务:Agent 未运行的验证按"未验证"处理,由协调器补验,不许采信"应该没问题"。

### 环节 C:记录(输出)

验证结果写入事件日志,至少含:任务 ID、验证级别、证据摘要、结论 PASS/FAIL、
失败分类(见 §4)。事件日志同时是指标与审计的数据源。

## 3. Gate 机制

门禁是流程中"不满足条件不允许前进"的强制检查点。两类门:

### 3.1 Decision Gate(决策门)

**位置**:专业调查之后、开发之前(workflow-model §4 Bug 流程第 5 步;主干流程"架构"阶段出口)。

**规则**:**无决策记录,不进入开发。**

```markdown
## 决策记录
Problem:    <问题>
Evidence:   <调查证据>
Root Cause: <已确认根因(经交叉验证)>
Scope:      <影响文件/模块>
Decision:   <最终方案与理由>
Owner:      <执行角色>
Next:       <后续动作>
```

**触发决策门的情形**:
- Bug 流程的修复方案选择;
- 架构变更(挡板 G2);
- 产品方向冲突(挡板 G1);
- Scope 扩展(挡板 G3)。

### 3.2 验收 Gate(验收门)

**位置**:流程末端(构建之后、以及每次对外交付前)。

**规则**:
1. **自动测试通过 ≠ 功能完成**。验收标准必须是**可操作的用户场景**(如"能作为日常编辑器
   持续输入 10 分钟无崩溃"),而不是"功能开关能切换""构建通过"。
2. **必须用户实测**:用户在真实运行的调试/发布构建上按验收清单操作;Agent/协调器
   不得替用户宣布"视觉通过"(实证:Agent 无法看到屏幕,其"渲染正确"报告是编造的)。
3. **逐条核对**:验收清单每条独立判定,不通过项单独走 Bug 流程,不"整体放行"。

**验收证据**记录:验收清单 + 每项结果(通过/失败/说明)+ 测试会话信息。

## 4. 自动化指标

三个核心指标,全部由事件日志自动统计,用于衡量工厂可靠性。**趋势比绝对值重要**:
可靠性跌破历史基线时必须停下调查,不得带病继续。

### 4.1 指标定义

| 指标 | 定义 | 计算 |
|:-----|:-----|:-----|
| **first_attempt_success(首试成功率)** | 委派任务一次通过双验证的比例 | `首试通过任务数 ÷ 总任务数`(重试/打回/换法均不算首试) |
| **path_errors(路径错误数)** | 因路径问题失败的任务数:文件未写入预期路径、在错误目录执行 | 事件日志中分类为 `path_error` 的事件计数 |
| **human_intervention(人工介入次数)** | 流程需要人类介入的次数:命中三挡板、第 3 次失败上报、发布授权、外部阻塞 | 事件日志中"暂停待人工"类事件计数 |

### 4.2 失败分类(统计与改进的切面)

每次 FAILED 事件必须归入一类,分类决定处置路径:

| 分类 | 判定 | 典型处置 |
|:-----|:-----|:---------|
| `api_error` | 基础设施故障(超时/服务不可用/额度不足) | 指数退避重试 ≤3 次,仍败转阻塞;**额度类不重试**,直接上报 |
| `env_error` | 环境问题(依赖缺失/权限/命令不存在) | 修环境后重试 |
| `path_error` | 文件不在预期路径 | 补路径约束(绝对路径注入)后重派 |
| `context_error` | Agent 行为偏离任务目标(做错功能) | 补上下文/换法重派 |
| `code_error` | 产出有缺陷(静态检查/测试失败) | 走两次失败上限:1 修复 → 2 换法 → 3 上报 |

### 4.3 收集方式

- 每个委派事件(创建/完成/失败/重试/阻塞)写一行事件日志:时间、任务 ID、状态、分类、证据。
- 指标按任务粒度聚合,按 Sprint/周期汇报。
- **实证基线参考**(抽象自 MarkPad 系列 Sprint):路径约束缺失时 path_errors 占失败一半;
  注入绝对路径后 path_errors 归零、first_attempt_success 从 ~50% 提升至稳定 100% 级别、
  多轮 Sprint 连续 0 人工介入。工厂应在自身实践中建立并维护自己的基线表。

## 5. 质量体系

### 5.1 测试基线管理

基线 = 一组"已知失败集合",是判断回归的参照系。

```
建立基线:在改动前运行全量测试,记录 失败数 × 按文件分组(如:26 fails / 5 files)
回归判定:改动后重跑,对比——
  新的失败文件出现                 → 回归,必须调查
  既有文件失败数增加               → 回归,必须调查
  失败数持平或减少、文件集合不变   → 非回归,可放行(但既有失败另行排期治理)
```

**纪律**:
- 只对比**失败集合**,不对比总数(总数持平可能掩盖"旧失败消失、新失败出现"的置换)。
- 不接受"没有新增回归"的头条结论,必须出示分组对比证据。
- 常见假回归:测试自身时序问题(如未推进异步计时器导致 "Timer is still pending")——
  先判是测试问题还是产品问题,修错对象会引入真回归。

### 5.2 回归区分(新回归 vs 既有)

| 类型 | 判定 | 处置 |
|:-----|:-----|:-----|
| 新回归 | 失败文件/数量超出基线 | 阻塞当前交付,优先修复 |
| 既有失败 | 与基线一致(非本次改动引入) | 记录、排期治理,不阻塞本次交付,但不得隐瞒 |

### 5.3 构建验证

| 构建类型 | 用途 | 授权要求 | 验证内容 |
|:---------|:-----|:---------|:---------|
| **调试构建** | 开发/测试/质量稳定期验证 | 无需授权 | 构建成功 + 安装可启动(用户实测用) |
| **发布构建** | 对外交付 | **必须显式授权** | 全量测试 0 失败 + 静态检查 0 错误 + 打包 + 安装验证 |

**规则**:
- 发布构建/发布产物(安装包、安装器)未授权前禁止产生;授权只针对发布动作,
  调试构建可自由执行,两者不得混淆。
- 打包后的产物必须做安装验证(挂载/安装/启动),产物内资源需抽查(实证:缓存导致
  打包产物缺失新资源、大小写不敏感文件系统导致安装包内嵌套旧应用)。
- 架构迁移后增加**体验实测**维度:自动测试覆盖不到的光标/选区/快捷键/渲染,
  由用户在实际构建上操作验证(见 workflow-model §5.4 质量稳定期)。

### 5.4 双验证落地检查清单

- [ ] 每个委派都有自报(结构化)
- [ ] 每个完成声明都有协调器独立重跑的证据(级别 ≥ L1,涉 UI 至少 L3)
- [ ] 每个 FAILED 事件都有失败分类
- [ ] 每次全量测试前后都有基线对比(分组级)
- [ ] 每次对外交付都有验收 Gate:用户实测记录 + 验收清单逐条结果
