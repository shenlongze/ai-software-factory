# AI 工作流编排（AI Workflow Orchestration）— 可立项产品规格

> 版本: 0.1 (可立项) | 日期: 2026-08-24 | 状态: 内核已实现（M2/M3）
> 来源: AI Factory 方案书 §4 多 Agent 编排 · M2 员工内核 · M3 执行链 · §2.9.1（P1, 对标 LangGraph）

---

## 1. 产品概述

**一句话**: 多 Agent 协作编排引擎——自有 Node Runtime + 递归原子拆解 + 关键路径 + 并行调度 + 质量门控，让复杂任务被"可验证地"完成。

**给谁**: 开发者 / ISV / AI 平台团队

**解决什么**:
- 复杂任务 Agent 做不完（拆解粗/上下文爆炸/一失败全崩）
- 多 Agent 协作无编排（谁先谁后/谁等谁/谁干哪块）
- 编排框架（LangGraph）无治理无证据（跑得起来但不敢信）

**价值主张**: "LangGraph 编排工作流，AI Factory 编排**可信**的工作流——每步有证据、有审批、可回滚"。

## 2. 背景与机会

- **痛点**: LangGraph/CrewAI 等编排框架解决了"怎么连"，但没解决"怎么可信"（无证据/审批/审计/回滚）
- **机会**: 编排是 AI 应用的地基，但企业要的是"可信编排"——这是 AI Factory 的差异化
- **竞品对照**:
  - LangGraph: 有状态图 + checkpoint（编排强, 治理无）→ 我们借鉴, 但自有 Runtime 不外包核心
  - CrewAI: 角色 Agent 快速搭建（浅, 无深度执行链）
  - 本产品差异 = **编排 + 执行链（拆解/调度/质量门控）+ 治理（证据/审批）三位一体**
- **战略地位**: P1——平台内核，可独立开源 + 云托管（对标 LangGraph + LangSmith）

## 3. 目标用户与场景

| 用户 | 场景 | 价值 |
|---|---|---|
| 开发者 | "让 AI 完成一个复杂重构任务" | 拆解→调度→执行→证据 全自动 |
| ISV | 构建垂直 Agent 应用 | 复用编排内核 + 治理底座 |
| AI 平台团队 | 多 Agent 协作的可信执行 | 每步可验证可审计 |

## 5. 端到端用户流程

```
1. 开发者提交复杂任务（"重构用户模块"）
2. 引擎: 递归拆解 → 原子叶子（复杂度诚实标注）→ 质量评分（adopt/adjust/reject）
3. 引擎: 依赖推断 → 关键路径 → 调度轮次
4. 执行: 每轮就绪叶子 → AgentMatcher 分配 → ExecutionLoop 执行 → 证据
5. 治理: 高风险操作审批 · 每步证据 + 审计
6. 交付: 全部完成 → 汇总报告（耗时/成本/证据/审批）
```

## 6. 技术架构（自有 Runtime，不外包核心）

```
AI 工作流编排（自有 Runtime）
  ├─ AgentEntity/ExpertFactory（M2 ✅）
  ├─ HandoffBus（交接/血缘 ✅）
  ├─ DecomposeEngine（原子拆解 M3a ✅）
  ├─ CriticalPathEngine（关键路径 M3b ✅）
  ├─ TaskScheduler（调度 M3c ✅）
  ├─ DecompositionEvaluator（质量门控 M3d ✅）
  ├─ ExecutionLoop（执行循环 ✅）
  ├─ AgentMatcher（动态分配, M3e 接入中）
  └─ 外部框架 = Adapter（LangGraph/Claude SDK 可插拔, P2）
统一契约: agt- 前缀 · TaskEntity schema · 审计事件 · E4xx
```

## 7. 验收标准（可立项门槛）

```
1. 一个复杂任务 → 拆解→评分→关键路径→调度→真实执行→证据（全链）
2. 质量门控: 差拆解 reject 回退确定性（不伪造）
3. 单任务失败不中断整链（M3e 验收）
4. 每步证据 + 审计 + 高风险审批
5. 全量回归 0 新增 + git clean
```

```
GTM: 开发者社区（开源 → 云）；P0 三件套客户可升级（治理/证据链 = 编排的增值层）
包装: "可信的工作流编排——LangGraph 的能力 + AI Factory 的治理"
```
