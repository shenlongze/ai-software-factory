# 存量代码清理服务（积压清道夫）— 可立项产品规格

> 版本: 0.1 (可立项) | 日期: 2026-08-24 | 状态: MVP 内核已实现（M1b, 818 行）
> 来源: AI Factory 方案书 §2.9.1（P0 首个 wedge）· M1b BacklogSweeper

---

## 1. 产品概述

**一句话**: 自动分诊并清理企业存量 issue 队列的 AI 服务——分诊 → 修复 → 证据 → 审批 → 报告，全程可审计。

**给谁**: 企业研发团队（有历史 issue 积压、修复速度跟不上、想量化 AI 修复价值）

**解决什么**:
- 存量 issue 积压无人清理（技术债）
- 人工分诊耗时（哪些该修/怎么修/风险多大）
- AI 修复不可信（黑盒改代码不敢批）

**价值主张**: "让 AI 像资深工程师一样清积压，每单修复附证据包，看完证据再批准"。

## 2. 背景与机会

- **痛点**: 企业 issue 积压是普遍现象，人工清理 ROI 低，AI 直接改代码又不可信
- **机会**: 这是"AI 修代码"里**最可量化、最可演示**的场景（每单=issue 一条，产出=修复+证据）
- **竞品对照**: 通用 coding agent（Cursor/Devin）改代码不产生"可审计证据包"；本产品差异 = **证据 + 审批 + 报告闭环**（企业敢签字）
- **战略地位**: AI Factory 首个可独立交付的 wedge（P0）——先卖它验证商业闭环，再带治理/审计产品

## 3. 目标用户与场景

| 用户 | 场景 | 价值 |
|---|---|---|
| 研发负责人 | 月底清积压（200 条 issue） | 批量分诊 + 自动修复 + 报告 |
| 一线工程师 | 收到"该修的依赖 bug + 证据包" | 看完证据就批，不用自己查 |
| 合规/审计 | 查询"这单谁修的/怎么修的/花多少钱" | 全链路审计 |

## 4. 功能范围

### MVP（内核已实现 ✅）
- [x] **分诊**（triage）: bug/feature/dependency → 修复策略（可解释）
- [x] **执行**（repair）: dependency 确定性真实修复（非 fake）
- [x] **证据包**（evidence）: 每单 diff+测试+日志+决策+变更文件（复用 evidence.py）
- [x] **审批**（approval）: 每单自动请求分级审批（复用 ApprovalGate，默认不自动应用 patch）
- [x] **报告**（report）: sweep-<ts>.json 运行报告

### P1（待做）
- [ ] 真实 issue 源接入（GitHub Issues / Jira / GitLab）
- [ ] 修复应用（审批后自动 apply + PR 创建）
- [ ] issue 去重/依赖排序（同类 issue 批量）
- [ ] 失败重试 + 分类汇总

### P2（远期）
- [ ] 多仓库批量清扫
- [ ] 修复质量回评（引用率/返工率）
- [ ] 订阅制 SaaS 形态

### 明确不做
- 不做通用编码 agent（只清积压）
- 不做未经审批的自动应用（Human 决定权保留）

## 5. 端到端用户流程

```
1. 导入 issue 队列（MVP: 本地文件/CLI 传入; P1: GitHub/Jira 接入）
2. 一键启动: factory backlog-sweep --input issues.json
3. 系统: 分诊（每单: 类型/策略/风险）→ 修复 → 证据包
4. 系统: 每单请求审批（factory approval list 查看）
5. 用户: 看证据包（diff+测试）→ approve/reject
6. 系统: 批准单自动应用（P1: +PR）· 拒绝单记录原因
7. 报告: 清扫汇总（分诊数/修复数/批准数/成本/耗时）
```

## 6. 技术架构（复用 AI Factory，不重造）

```
BacklogSweeper (818 行, ✅)
  ├─ triage → 修复策略
  ├─ repair → 确定性真实修复（dependency）
  ├─ evidence → EvidenceBundle（diff+test+决策+日志）✅ 复用 evidence.py
  ├─ approval → ApprovalGate（分级审批, 默认不自动应用）✅ 复用 exec.approval
  └─ report → sweep-<ts>.json
接入点: CLI（factory backlog-sweep）· API（backlog/sweep 待补）
统一契约: agt- 前缀 · E4xx 错误码 · 审计事件（§2.11）
```

## 7. 验收标准（可立项门槛）

```
1. 一条真实 issue（依赖 bug）→ 分诊正确 + 确定性修复 + 证据包完整
2. 每单证据含 diff+测试（可断言）· 审批 pending 记录
3. 未经审批绝不应用 patch（铁律）
4. 运行报告落盘（sweep-<ts>.json）+ 审计事件
5. 全量回归 0 新增 + git clean
```

## 8. 商业模式与 Go-to-market

```
定价: 按件（每单修复 X 元）或订阅（月清扫量套餐）
GTM: 先 1 个客户（有积压的研发团队）跑通 5 单 → 收集反馈 → 定价验证
包装: "AI 积压清道夫" — 演示 = 导入你的 issue → 看证据 → 批准 → 报告
```

## 10. 风险与依赖

| 风险 | 缓解 |
|---|---|
| 修复不可信（改错代码） | 证据包 + 分级审批 + 默认不自动应用（已设计） |
| 只修 dependency 太窄 | P1 扩展 bug/feature 修复策略 |
| issue 源接入成本 | P1 先 GitHub（API 成熟） |
| 依赖 | 审批/证据/审计内核（已实现 ✅） |
