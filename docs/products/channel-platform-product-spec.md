# AI 员工渠道平台（AI Worker Channel Platform）— 可立项产品规格

> 版本: 0.1 (可立项) | 日期: 2026-08-24 | 状态: 设计完整（§9.5）, 实现 0（P2 产品）
> 来源: AI Factory 方案书 §9.5 消息平台与社区集成 · §2.9.1（P2）

---

## 1. 产品概述

**一句话**: AI 员工出现在用户日常渠道（WhatsApp/Telegram/Slack/Discord/微信 50+）——渠道内派活、看进度、一键审批、收证据。

**给谁**: 运营 / 客服 / 销售 / 日常使用 AI 的员工

**解决什么**:
- AI 只在 CLI/网页里，日常渠道用不上（"在微信里让 AI 干活"）
- 审批要切系统（高风险操作在聊天里一键批）
- 社区/客服需要 AI 值守（FAQ 自动回复/舆情监控）

**价值主张**: "用户在哪，AI 员工就在哪——渠道是入口，不是系统"。

## 2. 背景与机会

- **痛点**: AI 能力封装在开发者工具里，业务人员（运营/客服/销售）接触不到
- **机会**: 消息渠道是企业 AI 普及的最大入口（微信/飞书/钉钉/Slack 是日常工作地）
- **竞品对照**: 客服机器人（单场景问答）· AI 助手 App（独立安装）· 本产品差异 = **完整任务闭环**（渠道内派活→Agent 干活→证据推送→渠道审批），不只是问答
- **战略地位**: P2——入口扩展层（先有内核/治理/证据，再铺渠道）

## 3. 目标用户与场景

| 用户 | 场景 | 价值 |
|---|---|---|
| 运营 | "在飞书群里让 AI 生成周报" | 渠道内派活 |
| 客服 | "客户问常见问题，AI 自动回" | FAQ 值守 + 知识回流 |
| 全员 | "让 AI 改个 bug，审批直接在 Slack 点" | 任务 + 审批闭环 |

## 4. 功能范围

### MVP（设计 ✅, 待实现）
- [ ] **P0 5 渠道**: WhatsApp / Telegram / Slack / Discord / 微信（§9.5.6）
- [ ] **入站派活**: 消息 → 归一化 → 意图解析 → Agent 路由
- [ ] **出站推送**: 任务结果 + 证据包推送到渠道
- [ ] **渠道审批**: 高风险动作 → 渠道内 ReviewGate（approve/reject）

### P1（待做）
- [ ] +20 渠道（Teams/飞书/钉钉/邮件/Line/Reddit/Discourse...）
- [ ] 定时能力（日报/巡检/提醒）
- [ ] 社区运营（发帖/回复/舆情监控/FAQ 知识回流）

### P2（远期）
- [ ] 50+ 长尾（插件化批量接入, 复用热插拔 + MCP）
- [ ] 语音/电话（Twilio）

### 明确不做
- 不做聊天机器人框架（只做 AI 任务闭环入口）
- 渠道是**增强入口**，不是必要条件（核心走 CLI/API, §9.5.5）

## 5. 端到端用户流程

```
1. 用户在微信/Telegram 发消息: "帮我看看登录报错"
2. 平台: 消息归一化（ChannelMessage{platform, conversation, sender, text}）
   → 意图解析 → Agent 路由（§四）
3. Agent 干活 → 结果 + 证据包 → 推送回渠道
4. 高风险操作 → 渠道内审批卡（approve/reject, 一键）
5. 所有消息 + 触发任务落审计（TOOL_CALL 等）
```

## 6. 技术架构（复用 AI Factory，不重造）

```
AI 员工渠道平台
  ├─ MessageChannel 协议（统一消息抽象, §9.5.3）
  ├─ Channel Adapter（每平台一插件, 热插拔 §二）
  ├─ 消息总线（§2.3.4）→ 意图解析 → Agent 路由（§四）
  ├─ ReviewGate 多渠道化（审批卡）✅ 复用
  ├─ 证据推送（evidence.py）✅ 复用
  └─ 安全铁律: 凭证加密 · 权限白名单 · 审计 · 不依赖（§9.5.5）
统一契约: ChannelMessage schema · 事件注册表 · E4xx
```

## 7. 验收标准（可立项门槛）

```
1. P0 1 个渠道（如 Telegram）跑通: 入站派活 → Agent 干活 → 证据推送 → 渠道审批
2. 凭证不落明文（加密存储断言）
3. 消息触发的敏感动作必须走审批（铁律断言）
4. 每条入站/出站消息落审计
5. 全量回归 0 新增 + git clean
```

## 8. 商业模式与 Go-to-market

```
定价: 按渠道数/消息量订阅
GTM: 从 P0 5 渠道开始（WhatsApp/Telegram/Slack/Discord/微信）
   — 先做 1 个渠道（如 Telegram）跑通闭环，再铺
包装: "AI 员工在你工作的地方干活——渠道内派活/审批/收证据"
```

## 10. 风险与依赖

| 风险 | 缓解 |
|---|---|
| 渠道 API 碎片化 | 统一 MessageChannel 协议 + Adapter 插件化 |
| 凭证安全 | 加密存储 + 权限白名单（§9.5.5 铁律） |
| 渠道内误触高风险操作 | 敏感动作必须走审批（铁律） |
| 依赖 | 内核/治理/证据已实现 ✅（渠道只做入口） |

