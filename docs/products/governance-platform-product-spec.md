# AI 治理平台（AI Governance Platform）— 可立项产品规格

> 版本: 0.1 (可立项) | 日期: 2026-08-24 | 状态: 核心已实现（审批/预算/审计）
> 来源: AI Factory 方案书 §6 治理与合规 · §6.7 独立产品边界 · §2.9.1（P0 信任层）

---

## 1. 产品概述

**一句话**: 管理组织里**所有 AI**（不论 Claude/Codex/自建 Agent）的治理平台——审批、预算、审计、合规四件事，让企业"敢让 AI 进生产"。

**给谁**: 企业 CTO / 合规 / 审计 / AI 平台团队

**解决什么**:
- AI 遍地开花但没人管（谁在调模型？花多少钱？谁批准的？）
- 高风险操作无审批（AI 直接删库/改生产）
- 出事无证据（黑盒 AI 不敢追责）

**价值主张**: "AI 的执行权交给 AI，审核权交给治理平台——执行权 != 审核权"。

## 2. 背景与机会

- **痛点**: 企业 AI 应用（Claude Code/Codex/自建 Agent）**能跑但不能管**——审批/预算/审计全裸奔
- **机会**: 这是 AI 时代的"安全合规层"——AI 越普及，治理越刚需（对标 SAP 的治理在 ERP 时代的地位）
- **竞品对照**: LangChain/LangGraph 等框架**无治理层**（开发者自己搭）；企业级 AI 平台（如 Azure AI）治理弱；本产品差异 = **独立于任何 AI 提供方**（管所有 AI）
- **战略地位**: P0 信任层——与积压清道夫（wedge）互补：清道夫验证"AI 能干活"，治理平台解决"敢不敢用"

## 3. 目标用户与场景

| 用户 | 场景 | 价值 |
|---|---|---|
| CTO | "全公司 AI 都在干什么/花多少" | 治理全景 + 成本水位 |
| 合规/审计 | "上个月的 AI 变更全流程可查吗" | 审计链 + 报告 |
| 工程师 | 提交高风险 AI 操作 | 分级审批（不裸奔） |

## 4. 功能范围

### MVP（内核已实现 ✅）
- [x] **分级审批门**（ApprovalGate）: low/medium/high → developer/tech_lead/compliance（爆炸半径分级）
- [x] **审批工作流**（review_gate）: request/approve/reject + 决策记录
- [x] **成本治理**（budget）: 四级预算 + 熔断 + 告警
- [x] **审计链**（audit）: 52 事件 + hash 防篡改 + 血缘
- [x] **证据包关联**（evidence）: 审批时看 diff+test+决策

### P1（待做）
- [ ] **多 AI 接入**（外部 Claude/Codex 经统一契约挂进来，§6.7）
- [ ] 审批 API 对外（approvals API 已有部分, 补全）
- [ ] RBAC 角色表（Owner/Admin/Operator/Viewer/Auditor）
- [ ] 审计报告（§5.9: factory audit report, 定时周报）

### P2（远期）
- [ ] 多租户 / SSO
- [ ] 合规认证（SOC2/等保 对接）
- [ ] 治理规则自动建议（AI 辅助策略）

### 明确不做
- **不执行任务**（执行权 != 审核权铁律）——只做决策与护栏
- 不做模型调用（只管治理）

## 5. 端到端用户流程

```
1. AI 发起高风险操作 → 平台捕获（事件回调/API）
2. 平台: 爆炸半径分级（low/medium/high）→ 匹配审批人
3. 审批人: 收到审批请求 → 看证据包（diff+测试+决策）→ approve/reject
4. 通过 → AI 执行 → 执行结果回报 + 证据归档
5. 预算: 每操作扣预算 → 超限告警/熔断
6. 审计: 全程事件链（谁/何时/哪个模型/多少钱）+ hash 防篡改
7. 报告: 月度治理报告（操作量/成本/审批率/风险分布）
```

## 6. 技术架构（复用 AI Factory，不重造）

```
AI 治理平台
  ├─ ApprovalGate（exec/approval.py, 分级审批 ✅）
  ├─ ReviewGate（session/review_gate.py ✅）
  ├─ BudgetEnforcer（exec/budget.py, 四级+熔断 ✅）
  ├─ 审计链（audit/audit_event.py, 52 事件+hash ✅）
  ├─ 证据包（evidence.py, 审批时看证据 ✅）
  └─ 统一契约: /api/v1/approvals|budget|audit + 事件回调（§6.7）
接入: 外部 AI 经统一契约挂入（不侵入内部）
边界铁律: 只做决策与护栏, 不执行任务
```

## 7. 验收标准（可立项门槛）

```
1. 一条高风险 AI 操作 → 分级 → 审批请求 → 证据可看 → 决策落审计
2. 未经审批绝不执行（铁律断言）
3. 预算超限 → 告警/熔断（断言）
4. 审计链 hash 校验通过（防篡改）
5. 全量回归 0 新增 + git clean
```

## 8. 商业模式与 Go-to-market

```
定价: 订阅（按组织规模/月活 AI 操作量）
GTM: 跟随积压清道夫（客户已信任 AI 能干活 → 升级治理）
包装: "AI 治理平台 — 管你所有 AI 的审批/预算/审计"
竞品定位: 独立于 AI 提供方（Claude/Codex/自建都能管）
```

## 10. 风险与依赖

| 风险 | 缓解 |
|---|---|
| 外部 AI 不愿接入 | 统一契约 + 事件回调（零侵入）+ 先服务自家 AI 客户 |
| 审批变瓶颈 | 分级（低风险自动/高风险必批）+ 异步审批（§9.5） |
| RBAC/多租户复杂度 | P1 先单租户 RBAC, 多租户 P2 |
| 依赖 | 审批/预算/审计/证据内核（已实现 ✅） |

## 11. 团队需求

```
1 后端（复用内核 + 多 AI 接入适配）· 0.5 前端（审批界面/治理面板）
1 产品/合规（RBAC/审计报告需求 + GTM）—— 内核已存在, 主要工作量 = 多 AI 接入 + 对外 API
```

**结论**: AI 治理平台 = **内核已实现（审批/预算/审计/证据）+ 边界清晰（执行权≠审核权）** 的可立项产品。
最大增量是 M1（多 AI 接入 + RBAC + 对外 API + 审计报告）——**2-3 周可到"可卖"状态**。
与积压清道夫形成组合: 清道夫证明"AI 能干活", 治理平台解决"敢不敢用"。
