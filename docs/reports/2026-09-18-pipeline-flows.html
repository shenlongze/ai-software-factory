3调用链路（一条命令背后经过哪些层）

颜色分层：CLI 层 → 服务层 → Agent / LLM → 存储（每行 = 一条命令的完整穿透路径）
① 会话conversation say
apps/cli/main.py _dispatch_conversation→ services/conversation/understanding append_message→ projects/<P>/conversations/*.json
② 需求conversation understand
_understand apps/cli/domains/conversation.py→ interpreter.llm_semantic_interpreter _llm_fn()→ infrastructure/llm/complete_text gateway.complete→ proposal.apply_operations 唯一写路径→ 事实层（理解版本 +1）
③ 分析conversation prd
_prd→ conversation/formalization 产品认知→PRD→ projects/<P>/product_truth/prds.json
④ 架构设计product develop / ux / arch design
cmd_product_develop main.py→ PMAgent.develop plugins/agents/pm.py→ _prod_provider kernel ProviderRegistry→ ProjectStore.save_artifact→ org/artifacts.json
⑤ 任务拆解tasktree decompose
_dispatch_tasktree main.py→ services/work/decomposition decompose_from_design→ 边界检查 depth/leaves/cycle→ projects/<P>/tasks/PLAN-*.json
⑥ 执行run --project <dir>
cmd_run→ execution/kernel agent_runtime→ kernel/sandbox 仓库副本→ LLM 生成 patch→ validation syntax + test-cmd→ exec/patches/*.patch
⑦ 监控metrics / kanban
_print_metrics→ metrics/calculators 从事件聚合→ metrics/control_tower 注入式投影
⑧ 运维backup / recover
_dispatch_operations→ operations/backup tar.gz 归档→ operations/rollback_service 回滚
LLM 出口只有一处：② 与 ④ 的模型调用最终都走 infrastructure/llm/gateway.complete() —— 它是唯一汇聚点（成本估算 + traces/llm.jsonl 留痕都在那一次调用里完成）。这一刀正是本轮新补的（complete_text.py，组装自 gateway + control_plane，不再借老区 llm_raw）。

4跨环依赖（谁挡住谁）

这一层决定"改一环会不会牵动别环"。
环依赖谁被谁依赖断链风险
① 会话—②（消息是理解输入）低
② 需求① · LLM 口③（事实→PRD）中（LLM 口断则降级 CLARIFY）
③ 分析②—低
④ 架构③ 的 PRD 语义 · LLM ×3 · org 存储⑤（design.task_breakdown 是种子）高（双输入缺失则无法生成）
⑤ 拆解④ 的 design 产物⑥（叶任务 + 拓扑序）高（无 design 则拒绝）
⑥ 执行⑤ 的任务 · 真实仓库 · LLM⑦⑧（执行记录是数据源）中（缺仓库则报错, 不静默）
⑦ 监控⑥ 的执行记录 + 事件—低（无数据则显示 0, 诚实标注）
⑧ 运维数据根—低
