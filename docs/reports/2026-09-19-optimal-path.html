1. 四刀方案（每刀 = 1 commit + 全量验证 + STOP）

第 0 刀 · 统一执行存储（地基）
现状(实测)同一个 RuntimeStore 类被两条链用两个路径: pump→root/runtime（磁盘 0 个）· CLI→root/runtimes（1 个）; 另有 ExecStore→root/exec（6 个）
目标一个路径 + 一个权威 Store（一数据一权威源 —— 与既有铁律同源）
做法① 定权威路径（建议 <root>/exec, 数据最多）② 另一个改为兼容读 ③ 迁移现存 runtimes/ 1 个（先备份）
验收pump 建的 execution 能被 CLI 查到（互可见）; 三条链只有一处写
风险迁移真实数据 ⇒ 先备份（runtimes/ + exec/）

为什么必须第一刀: run --plan（第 1 刀）要跑整棵树并续跑 —— 若存储分裂, pump 与 CLI 各写各的, 续跑读不到状态。

第 1 刀 · run --plan + 三个"不静默"前提（必须一起做）
① run --plan按 depends_on 拓扑序跑整棵树（现在只能 run --task 单个 ⇒ 13 任务 13 次调用）
② claim 释放(cr-4)现状: _claim_and_run() 只在抛异常时释放 leaf; 返回 FAILED 结果时 leaf 保持 claimed ⇒ 任务卡死永不重试。修: FAILED ⇒ 释放 + 回写 + 落 checkpoint
③ 文件冲突(cr-5)现状: decomposition.file_conflicts() 要求"同层写同文件 ⇒ 降级串行", 但没人调用 ⇒ 并行会静默覆盖。修: 并行前检测, 冲突降级串行
验收13 个任务一条命令跑完; 故意让第 7 个失败 ⇒ 能续跑且前 6 个不重跑; 两个写同文件的任务被串行
为什么三件一起★ 只做 ① 会更糟: 跑起来就会遇到"失败即卡死"+"并行静默覆盖" —— 比现在人工逐个跑还危险

第 2 刀 · Outcome 接进完成语义（cr-3）
现状contract 明写 "execution success ≠ business completion, 必须 accepted Outcome", 但 pump 见结果成功就写 completed; has_accepted_outcome() 也把 completed/done 当验收
目标"完成"必须经验收语义（不能"跑通即完成"）
验收无 accepted Outcome 的任务不能被标 completed; 与"acceptance 无消费方"一并解决

第 3 刀 · 让预算是真的（cr-6）
现状SimpleLoad 直接返回 1e9 · OrgResource.capability() 返回 None ⇒ cost_estimate 实际为 0 ⇒ 预算约束形同虚设（"超限该阻断就阻断"无数据支撑）
目标load/capability 返回真实值（数据源: providers/usage.json 已存在）
验收预算能真实阻断（不是 1e9）; 超限时确实推迟/拒绝
