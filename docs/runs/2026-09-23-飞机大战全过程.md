## 6. 那次损坏的完整闭环（本轮最有价值的收获 ✓）

**症状** → **取证** → **根因** → **修复** → **反例证明** → **数据恢复** → **守卫**（每一步都有实物 ✓）

| 步 | 内容 |
|---|---|
| 症状 | `--parallel 3` 时：`检查点写入失败: CorruptRuntimeStoreError: runtimes.json: Extra data: line 1107 column 5 (char 99803)` ✗ |
| 取证 | 99,811 字符；尾部实录 `…}\n  }\n      }\n    }\n  }\n` ⇒ **两段写交错** ✗ |
| 根因 | `RuntimeStore._write_all` 临时名 `.{filename}.{os.getpid()}.tmp` ✗ —— **同进程并发线程 PID 相同** ⇒ 共写同一临时文件 ⇒ 交错。该文件注释本就写着「单进程本地使用, **不做文件锁**」✗ |
| 修复 | ① `tempfile.mkstemp` 唯一临时名 ② 写后**回读校验**（坏了当场报 ✗）③ 读-改-写加**线程锁 + flock**（缺任一个都丢更新 ✗） |
| 反例 | 老写法 6 线程 × 20 条 = 120 ⇒ 实测**只剩 20 条** ✗（并且报 FileNotFound）⇒ 说明新守卫**真能抓住**这个 bug ✓（不是摆设） |
| 数据恢复 | 你真实根被写坏的 `runtimes.json`：**先备份**（`~/.factory-backups/runtime-store-before-repair-20260924-025458/` ✓）→ 截到**合法前缀**（`runtimes 1 · executions 33 · results 21` ✓）→ 原子替换 ⇒ 平台恢复 ✓；尾部残缺的第二次写**无法拼回** ✗（如实说明） |
| 守卫 | 新增「并发写不丢更新」4 线程 × 15 条 ⇒ JSON 合法 + 记录一条不少 ✓ |
| 提交 | `fccb8425` · v1.3.33（守卫 65 → **66** · pytest 76 → **77**） |
