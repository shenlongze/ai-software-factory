## 一、敢不敢演示？——结论：**敢演"骨架"，不敢让懂行的人看"产出内容"**

先把事实钉死（都是代码，不是推测）：

| 关键事实 | 证据 | 含义 |
|---|---|---|
| 生产路径 `llm_fn=None`，从未接 LLM | `actions.py:3095` `ProductPipeline(context.workspace, slug)` 不传 `llm_fn` | 7 专家**从不真调 LLM** |
| 兜底是规则模板 | `expert_factory.py:359-382`，输出含 `规则占位` / `（待补充）` | 专家"产出"是填字模板 |
| 交接只传 ID 不传内容 | `pipeline_runner.py:117-134`，`_produce` 只拿到 `parent_artifact_id` 字符串；`handoff_bus.py:259` `produce(agent, prev_artifact_id, product)` | 后一个 Agent **看不到**前一产出的正文 |
| LLM prompt 里也只嵌 ID | `pipeline_runner.py:126` `f"上一资产: {parent_artifact_id or '(根, 无)'}\n"` | 即便接了 LLM，也喂不进去上一产出内容 |
| 7 专家产出是死胡同 | `actions.py:500-503`：`prepare_project` 用 `ProductDocument.from_product_intent` **规则重生成 PRD**，不读 HandoffBus 的 `prd` 资产 | 下游工程绕过 7 专家 |
| 7 专家不落盘 | `expert_factory.py:323-337` assemble 不 `registry.add`；测试注释 `test_m2_agent_core.py:213` 明说"assemble 不自动落盘" | 跑完 pipeline，`~/.factory/agents/` 里**没有**这 7 个 `agt-*` |

**"我要做CRM → 7 专家 → 资产链"这条路径走不走得通？** 走得通，且离线确定、不翻车（`TestProductPipelineAction` 实测 `sess._dispatch("让PM分析")` → "产品管线完成 · 7 个资产" + 血缘 + `created_by=agt-*` 全过）。所以**"演示骨架"敢**：id 契约、parent_artifact 血缘、冲突→ReviewGate 挂起、`created_by=agent_id` 审计，这四样是真实的、可现场跑的。

**哪里会翻车（3 个现场必被追问的点）：**

1. **"市场分析为什么是空的/待补充？"** —— 因为 market/competitive 的确定性兜底只从 `ProductIntent` 里取用户已填的字段，没有真实调研，也没有 LLM 补足。
2. **"UX 专家读了 PM 的产出吗？"** —— 没有。它只收到上一资产的 ID 字符串（`product-v1-xxx`），正文从没进过任何角色。
3. **"这份 PRD 是 7 专家链产出的吗？"** —— 不是。你 `准备开发` 时系统用规则又生成了一份 `PRD.md`，7 专家的 `prd` 资产躺在那没人消费。

**与 M1 拼起来**：M1 的"证据+审批+apply"闭环是**独立真实**的，但和 M2 是**并联不是串联**——M2 的 7 专家资产不喂给 M1 的工程执行。所以"完整 demo 路径"能串起来演（create → 让PM分析 → 准备开发 → 开始开发 → 验收），但中间那步"7 专家分析"是**装饰性的**，抽掉它 demo 结果不变。

## 三、真实差距清单（员工内核 → "AI 软件公司"）

1. **专家不干活**：生产路径 `llm_fn=None`，7 专家 = 规则模板。`ReasoningProvider._default_llm_fn()`（`reasoning.py:443`，能真装配 providers.json 的 provider）**存在但没接进 pipeline**。
2. **交接不消费**：`route` 只传 `prev_artifact_id` 字符串，正文从未进入任何角色的 prompt/上下文。这是"互引"不是"协作"。
3. **产出是死胡同**：`prepare_project` 规则重生成 PRD/plan，绕过 7 专家资产——M2 与 M1 工程域**没接通**。
4. **专家不落盘**：`build_team` 不 `registry.add`，`查看团队` 看不到这 7 个 `agt-*`。
5. **能力全是占位面**：`tools=[]`（MCP 真连后置）、`knowledge_ref` 只校验目录字符串、`memory_ref/evaluation_ref` 空、`profile` 恒 0（无回流）。
6. **唯一真实可演示的是"治理壳"**：id 契约、血缘、冲突审批——这些是对的，但它们管的是"空的资产"。

## 四、下一 Sprint 裁决

**裁定：#6（让专家真实消费上一产出）为主线，但必须与 #4 的最小切片（接真实 LLM 进 `_produce`）打包成一个 Sprint。** 二者缺一不可——没有 LLM，"消费上一产出"消费的也是空壳；没有消费，LLM 各自为战。

理由（Head of Product 视角）：

- 其余所有候选都**默认"7 专家真干活"这个前提成立**。`expert build` CLI 造出的专家现在不干活；M3 拆解的 plan 现在是规则生成的、与专家无关；记忆回流回流的是"规则占位"的经验。**在假地基上继续盖楼，只会把空心结构复利放大。**
- 这个改动的成本极小、风险可控：接 `ReasoningProvider()._default_llm_fn()` 到 `product_pipeline` action 是 ~3 行；`route` 把上一资产 `content_ref` 读出来传进 `produce` 也是小改。契约测试已有注入点（`ProductPipeline(llm_fn=...)`、`bus.route(produce=...)`）。
- 它把"敢演示"从**演示骨架**升级为**演示分析**——这是产品叙事（"AI 软件公司"）当前唯一缺的那口气。

**完整定序（Founder 候选 1–6）：**

1. **#6 + #4-min**（专家真干活：消费上一产出 + 接 LLM）—— 唯一让 demo 诚实的杠杆。
2. **#2 审批→PR 链路** —— M1 最后一公里，独立用户价值（真实 issue 源），审批门已在 M1 闭环，成本低、价值实。**这是"收尾纪律"的第二名。**
3. **#1 expert build CLI** —— 在专家真干活之后才有意义；现在 build 出的只是空壳。
4. **#3 记忆回流最小切片** —— M4 锚点，但依赖"真干活"才能回流出真经验。
5. **#4-full / MCP 工具** —— 多 LLM 路由的三层（planner/executor/reviewer）和真 MCP，是 #4-min 之后的放大，非当前瓶颈。
6. **#5 M3 前奏** —— 下一个大里程碑，但必须先打通"7 专家 PRD → 工程计划"的消费链路，否则 M3 拆解的是与专家无关的规则 plan。

## 五、对 M3 的建议

1. **M3 的输入必须先变真**：当前 M3 要拆的"原子任务"，其上游 plan/PRD 是 `prepare_project` 规则生成的，与 7 专家链无血缘。进入 M3 前，把 `prepare_project` 改成**消费 HandoffBus 的 `prd` 资产**（或至少消费 LLM 真产出的 plan），否则递归拆解做得再漂亮，拆的也不是专家的东西。
2. **"递归原子拆解"可以独立于 LLM 先行**——它本质是确定性算法，不需要等 A6 多路由。但**拆解器可以先行，拆解对象不能是假的**。建议 M3 内部分两拍：先接通真 PRD 消费，再上递归拆解。
3. **补一条 M2 未兑现的验收**：§1.7.3 把 M2 写成"7 专家**真实产出**"，当前交付的是"7 专家**规则占位产出**"。建议 M3 前把 M2 的"真实产出"拆成可量化断言（如：market 资产必须包含 ≥1 条来自 LLM 的市场数据，而非"（待补充）"），否则"真实"二字会一路带病进入 M3 的验收链。

**总判**：M2 是**工程质量扎实、产品价值未兑现**的交付。地基是对的，但"AI 软件公司"目前只有"公司"（治理/血缘/审批），没有"AI 软件"（专家真的分析、真的消费上游）。下一刀该砍向"让专家真干活"，而不是继续往空心结构上盖 CLI 或 M3。
