【AI Factory Sprint 规格 — 产品发现 LLM 深度介入】

## 角色
Hermes = CTO + 架构委员会。产出可执行 Sprint 规格，不写实现代码。

## 背景（Founder 实测暴露的深层需求）
Founder 测试产品发现发现"太模板化"：
- 现状: 用户描述 → 规则状态机逐字段收集（problem/user/core_features）→ 模板追问 → 模板命名
- 问题: LLM 没有真正**理解**用户意图，只是"填字段"
- 已修复: 命名接线（bcc1b14, 验收通过: deterministic 'markdown编辑器要' → LLM '墨写/码上记/简执笔'）
- 本 Sprint: **字段收集本身升级为 LLM 理解 + 规则兜底**

## Sprint 目标
**产品发现 = LLM 理解主路径 + 规则状态机兜底**：

```
现在:  用户描述 → 规则状态机提取字段 → 模板追问 → 模板命名
目标:  用户描述 → LLM 理解意图 → 智能提取结构化产品定义
       → 缺失字段智能追问（理解为什么缺, 不是机械列问题）
       → LLM 主动分析（用户没说但该问的: 平台/竞品/范围）
       → LLM 命名（已通）
无 LLM → 规则状态机兜底（现有行为, 诚实降级, 不伪造）
```

## 必须包含（参考既有 Conversation State Machine 优先级）
1. **LLM 意图理解**: 用户输入是产品描述 / 控制指令（取消/整理/查询）/ 字段回答？——复用
   S10-082 意图判断优先级（控制指令 > 查询 > 字段回答）
2. **LLM 结构化提取**: 一次理解产出 {problem, user, core_features, name?, platform?}，
   替代逐字段追问（用户一次说清就不该再逐个问）
3. **智能追问**: 缺失字段时 LLM 理解"为什么缺"→ 针对性追问（不是机械列全部问题）
4. **主动分析**: LLM 补足用户没说但该有的（platform/竞品/范围）→ 确认时展示"我们理解你的产品是..."
5. **规则兜底**: 无 LLM/key → 现有状态机完全不变（向后兼容, 诚实降级）
6. **确认门增强**: 确认前展示 LLM 理解摘要（"我理解你要做 X, 给 Y 用, 核心是 A/B/C, 对吗"）

## 规格必须包含（8 项）
1. 发现流程新架构（LLM 主路径 vs 规则兜底 vs 混合）
2. LLM 提取/理解接口（prompt 设计: 输入=对话历史+当前输入, 输出=结构化字段+追问理由）
3. 与 ConversationManager 状态机集成点（最小改动, 状态机保留为兜底/控制流）
4. 智能追问 vs 机械追问的判定（什么时候 LLM 追问, 什么时候规则追问）
5. 确认门增强（LLM 理解摘要展示）
6. 契约测试要点: 自然描述一次产出 / 控制指令不被当字段 / 无LLM回退 / 确认摘要 / 向后兼容
7. Codex 写 scope
8. 边界: 不做 product_pipeline 深度分析（那是"让PM分析"已有）· 不做多语言

## 验收标准（Codex 完成后，你独立验证）
- 自然描述（如"我想做个 markdown 编辑器, 要 typora 和 notepad++ 的优点, 适配手机"）
  → LLM 一次产出结构化定义（problem/user/core_features）非逐字段问
- 控制指令（"取消"/"整理一下"）→ 不被当字段（优先级保持）
- 无 LLM → 现有状态机零变化
- 确认门: 展示 LLM 理解摘要（"我理解你要做..."）
- 全量回归 0 新增 + git clean
- 版本: 本 Sprint 完成后 bump v1.1.16
