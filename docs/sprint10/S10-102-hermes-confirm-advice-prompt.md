## 角色
Hermes = CTO + 架构委员会。产出可执行 Sprint 规格，不写实现代码。

## 背景（Founder 实测 v1.1.22 暴露 2 个 bug）
Founder 实测 "做一个记账app" 全流程:
1. **确认阶段输入分流错误（严重）**: 用户输入 "可以，先出prd文档 功能说明，或者html"
   → 系统把整句话当**产品新名称**（"产品: 可以，先出prd文档功能说明，或者html"）→ 重新确认
   → 用户输入 "？" → 也被当名称（"产品: ？"）
   根因: handle_product_confirm 非 y/取消词 → 一律当"改名"（S10-081 简单逻辑, 无智能分流）
   - "可以"（确认词）+ "出prd"（下一步意图）混合句未识别
   - 问号/请求/非名称输入 全被当改名
2. **求助词变体未全覆盖**: 用户说 "没 想法"（带空格）→ 被填进 core_features="想法"
   （S10-101 求助响应只覆盖部分变体, "没 想法"/"没想法" 等漏网 → field_answer 机械填入）

## Sprint 目标（2 项）
1. **确认阶段 LLM 智能分流**: 确认时输入 = 确认 + 下一步意图（出prd/html/文档）混合句
   → 识别"确认 + 下一步"（执行创建 + 触发下一步）; 非 y/N 且明显非名称（问号/请求）→
   智能处理（澄清/建议）而非一律改名
2. **求助词全覆盖**: "没想法/没 想法/没有想法/随便/你定/给个建议/给些意见/你看吧" 等
   → 求助响应（提供建议）, 不填字段; 规则关键词 + LLM 分类双覆盖

## 必须包含（6 项）
1. **确认输入分流模型**: y/确认词(可以/好/行/是/确认) / 确认+下一步混合(可以,先出prd)
   / 改名(明确新名称) / 问号或请求(澄清/建议) / 取消 — 分类器
2. **确认+下一步**: 识别后 → 确认创建 + 返回"下一步意图"（generate_prd/出html）给宿主执行
3. **非名称输入处理**: 问号/含糊 → 不改名, 请求澄清（"是想修改产品名, 还是确认创建?"）
4. **求助词规则表**: 补全变体（含空格/口语）→ 求助响应不填字段
5. **LLM 分类**: 确认输入 LLM 理解（confirm_intent: approve+next / approve / rename /
   clarify / cancel）; 规则兜底（关键词表）
6. **向后兼容**: 明确改名（"改名叫X"/"产品名X"）仍走改名; 纯 y/N 行为不变

## 规格必须包含（8 项）
1. 确认输入分类器设计（类别 + 判定规则 + LLM 注入）
2. "确认+下一步" 语义（返回结构: approved + next_action?）
3. 非名称输入的澄清话术
4. 求助词全覆盖规则表（含空格/口语变体）
5. conversation.py + discovery.py 集成（两路径同步）
6. 契约测试要点: 确认+下一步/问号不改名/明确改名仍走/求助词不填字段/无LLM回退/向后兼容
7. Codex 写 scope
8. 边界: 不改命名/主动分析/进度提示（已有）

## 验收标准（Codex 完成后，你独立验证）
- "可以，先出prd文档" → 确认创建 + 触发下一步（PRD）; 产品名不被覆盖
- "？" / "随便" 在确认阶段 → 不改名, 智能澄清
- "没 想法" / "没有想法" → 求助建议, core_features 不被填"想法"
- 明确改名（"改名叫X"）→ 仍走改名
- 无 LLM → 规则兜底（关键词表, 行为不劣化）
- 全量回归 0 新增 + git clean
- 版本: 本 Sprint 完成后 bump v1.1.23
