# 会话系统整体设计 v3（重新评估）

> 日期: 2026-08-27 | 前置: v1.1.215（Agent 循环 v2 + IntentCore + 话题账本 + 意图解析重构全落地）
> 类型: **设计评审 → 已采纳**（Founder: "重新评估设计，会话" → "那就推翻，采用最有效的解决方案"）
> 目标: 从全局审视会话架构，找出体制性问题，给目标架构 + 迁移路径，不再打补丁
> 状态: **① 范式转变已落地 (v1.1.216)** — AgentLoop v3 (agentic 自主 + Reflection 自评, 意图门降级软参考); ②③④⑤ 待排期

---

## 0. 结论先行

**会话能力单点已大幅改善（意图/上下文/工具/路由），但架构有 3 个体制性债务，导致"问题多、修不完"：**

1. **双轨制** — 项目级走 agent 循环、其他/降级走旧路由 query_engine，两套意图解析、两套工具调度、两套输出
2. **路由表** — 意图→固定工具仍是映射表，新增能力要改多处；capability_router 存在但没接进会话
3. **不可观测** — 意图识别率/工具成功率/回答质量无指标落监控，问题靠用户发现

**目标：单轨化 + 三层架构（理解→路由→执行）+ 上下文统一 + 证据强制 + 可观测。**

## 2. 体制性债务（详细）

### 2.1 双轨制（最严重）
- 项目级会话 → `run_agent`（LLM+原生 FC，模型自主选工具）
- 公司级/全局/agent 不可用 → `parse_intent_llm` → 20 意图各绑一个工具
- **同一个用户消息，两条路径行为不同、输出格式不同、质量不同**
- 维护 = 双倍：修 bug 要改两处；新增能力要同步两套意图表+工具表+dispatch
- 用户感知："同样的问法，时好时坏" / "刚修好的问题换个入口又出现"

### 2.2 路由表而非能力路由
- query_engine：意图→固定工具（project_scan/code_scan/project_structure...）
- agent 循环：模型 FC 从 15+ 工具里裸选（无候选约束，选错靠碰）
- capability_router（能力匹配）+ external router（历史加权）**都没有接进会话工具选择**
- 新增能力 = intent 表 + LLM prompt + 工具 schema + dispatch 四处改动

### 2.3 上下文分层混乱
- 4 个来源堆进 messages：意图摘要 + 历史(4轮) + 话题视图 + 锚定任务
- 无统一"预算/优先级"管理（哪个重要、超长怎么办、冲突以谁为准）
- 跨会话记忆（K-7f）、项目知识（RAG）完全没接进主链路

### 2.4 可观测缺失
- 每轮 intent/route/tool/耗时 无落审计
- 无"意图识别准确率/工具成功率/回答质量"指标
- 问题靠用户发现 → 用户就是 QA（Founder 已经当了很多次 QA）

### 2.5 证据不强制
- challenge 有自查；普通查询"是否带证据"靠模型自觉
- 无"查询/分析类必须带工具证据，否则不输出结论"的硬约束

## 3. 目标架构（单轨三层）

```
用户消息 (任何 scope: 项目/公司/全局)
  ↓
┌─────────────────────────────────────────────┐
│ ① 理解层 IntentCore v2 (唯一入口)             │
│    LLM 结构化: intent × target × need ×      │
│    emotion × summary                         │
│    规则只做无-LLM 兜底 (降级保护)              │
└─────────────────────────────────────────────┘
  ↓
┌─────────────────────────────────────────────┐
│ ② 路由层 Router (统一)                       │
│    按意图 → 专业能力线:                       │
│    - 查询   → 数据工具 (capability 匹配)      │
│    - 分析/质疑 → deep_analyze (多工具+证据)   │
│    - 开发/操作 → 动作链 (计划→审批→执行)       │
│    - 外部专业 → external route (已有)         │
│    - 聊天   → 自然对话 (话题上下文)            │
└─────────────────────────────────────────────┘
  ↓
┌─────────────────────────────────────────────┐
│ ③ 执行层 Executor (agent 循环)               │
│    原生 FC + 硬收敛 + 证据链                  │
│    上下文 = 话题账本(唯一历史源) + 记忆(跨会话) │
│              + 项目事实(实时)                 │
│    query_engine → 纯降级兜底 (LLM 不可用)      │
└─────────────────────────────────────────────┘
```

**关键设计决策：**

| # | 决策 | 理由 |
|---|---|---|
| D1 | **单轨化**：所有 scope 走同一条链路；query_engine 退居"LLM 不可用时的降级"，不再并行 | 消除双轨，行为一致，维护减半 |
| D2 | **Router 复用** capability_router + external router：意图 + 能力匹配 → 候选工具集（模型在候选中选，缩小选择面） | 选工具从"碰"变"匹配"，新增能力只加资源注册 |
| D3 | **上下文统一**：topic_ledger 为唯一历史源（替换固定 4/8 轮）；记忆层挂载点（跨会话摘要/常问事实） | 一份上下文，预算可管理 |
| D4 | **证据强制**：查询/分析类"无工具证据不输出结论"（硬约束，先查再说）；challenge 已有自查 | "数据真不真"的体制保障 |
| D5 | **可观测**：每轮 intent/route/tool/耗时/准确率落 audit → 监控页会话指标 | 不再靠用户当 QA |

## 3.5 范式转变（已落地 v1.1.216）

采纳前沿 agentic 范式：**推翻"意图门硬路由"，采用"模型自主循环 + Reflection 自评"**。

- 意图门 (IntentCore) → 软参考：不再拦截/锁定，意图只作 system 提示（"仅供参考，以对话语义为准"）
- 循环：模型自主决策（调工具/直接答/追问）→ 工具回喂 → Reflection 自评（够→答案带证据；不够→继续查；需澄清→提问）→ 主动收敛
- 硬收敛保留为最后兜底（上限 + 强制收敛轮 + 3-loop 追问）
- 测试: 44 passed（agentic 自主 / reflection 注入 / 软参考措辞 / 硬收敛）

## 4. 迁移路径（不推翻重来，每步可独立交付）

### Step 1 — 单轨化（最高优先）
- 公司级/全局会话也接入 agent 循环（统一入口）
- query_engine 改为"agent 不可用时降级"（不再并行服务）
- 验收：同一消息在项目/公司/全局三处行为一致；回归 215+ 不倒退

### Step 2 — Router 统一（能力匹配）
- 会话工具选择接入 capability_router：意图 + 能力 → 候选工具集
- 新增能力 = 注册资源（CapabilityResource），不再改四处
- 验收：工具选错率下降（可观测指标支撑）

### Step 3 — 上下文 + 记忆 + 可观测
- 话题账本作为唯一历史源（移除固定 4/8 轮逻辑）
- 挂接跨会话记忆（K-7f：新会话"继续上次"）
- 每轮落审计：intent/route/tool/耗时 → 监控页会话指标
- 验收：会话指标页可看意图识别率/工具成功率趋势

## 6. 不做什么（边界）

- 不推翻 agent 循环（方向已验证对）
- 不引入重型框架（保持轻量，标准库 + LLM + 少量 JSON）
- 不做"全自动无确认"（敏感动作保留审批）
- 不做向量库检索（RAG 已记录为独立需求，先不阻塞单轨化）
