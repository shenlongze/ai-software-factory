# Workflow 模型 (workflow-model)

> 状态: DESIGN ONLY (蓝图, 未实现或部分实现: 任务级 WorkflowEngine 已实现, 组织级/业务流程未实现 — 见 ./audit/architecture-reality-audit.md)

> 通用 AI Software Factory 的流程定义。Workflow 把"一系列委派 + 门禁"组织成可自动推进、
> 可暂停的生产流水线。本模型从 Hermes + MarkPad 的生产实践(通用生产流程、Bug 固定流程、
> Sprint 管理)归纳而来,与具体工具无关。

---

## 1. 核心概念

- **阶段(Phase)**:流程中的一个大步骤(如"开发")。
- **步骤(Step)**:阶段内的可执行单元,通常对应一次角色委派。
- **门(Gate)**:步骤/阶段间的检查点,不通过不前进。
- **自动推进**:阶段完成即进入下一阶段,不等待人工确认 —— 除非命中暂停挡板。
- **三挡板**:仅三类情况允许暂停流程等待人类决策(见 §3.3)。

```
Workflow = 阶段序列 + 步骤依赖图 + 门 + 自动推进规则 + 暂停挡板
```

---

## 2. 通用软件生产流程抽象

任何软件交付任务(功能/缺陷修复/发布)都映射到同一主干流程。六个阶段,每阶段定义
输入、执行角色、产出、出口条件:

```
需求 → 架构 → 开发 → 测试 → 构建 → 验收
```

| 阶段 | 执行角色 | 产出 | 出口条件(通过才前进) |
|:-----|:---------|:-----|:---------------------|
| **需求** | 产品经理 | 需求描述、验收标准 | 验收标准可判定(用户场景级,而非"界面能切换") |
| **架构** | 架构师 | 方案分析、设计决策、影响范围 | 决策记录落盘(无决策记录不进入开发) |
| **开发** | 开发工程师 | 实现代码、变更清单 | 文件范围合规 + 静态检查通过(见 validation-model L1) |
| **测试** | 测试工程师 | 测试用例、验证结果、回归状态 | 新回归为 0;与基线对比无恶化 |
| **构建** | 发布验证 | 构建产物(调试/发布) | 构建成功 + 安装可启动(调试构建无需授权,发布构建需授权) |
| **验收** | 用户(最终) | 验收结论 | 用户在真实运行的应用上实测通过(CLI/自动测试通过 ≠ 功能完成) |

**两条主干变体**:
- **功能任务**:需求 → 架构 → 开发 → 测试 → 构建(调试)→ 验收。
- **缺陷任务**:走 §4 的 Bug 专用流程(调查先行)。
- **发布任务**:构建(发布,需授权)→ 安装验证 → 验收,前置要求全量测试 0 失败。

## 3. Workflow 引擎

引擎负责"按依赖调度委派、验证后自动推进、命中挡板即暂停"。

### 3.1 步骤定义 Schema

```yaml
step:
  id: T-001                 # 全局唯一
  phase: 开发
  role: development         # 执行角色(agent-model 注册表)
  depends_on: [T-000]       # 前置步骤(可为空)
  parallel: true            # 是否可与同级步骤并行(默认 false)
  files:                    # 文件范围(allowed/forbidden/expected)
  validation:               # 验证要求(validation-model)
  acceptance:               # 本步出口条件(可判定)
```

### 3.2 依赖与并行约束

- **依赖**:`depends_on` 未全部完成的步骤为 BLOCKED,不得委派。
- **并行**:仅当满足**全部**条件才允许并行委派 ——
  1. 无依赖关系;
  2. 文件范围不重叠(实证:同一文件即使"不同分支"并行也会互相破坏编译与标记);
  3. 均为只读调查型任务(审计/根因追踪)或独立文件集。
- **串行纪律**:核心集成步骤(核心逻辑合并进 UI、架构迁移)必须一个接一个串行执行:
  架构 → 开发 → 测试,禁止并行 —— 并行 Agent 可能污染已正确的核心代码。

### 3.3 自动推进与三挡板

**自动推进规则**:任何阶段完成后立即检查挡板 → 无挡板 → 自动进入下一阶段。
禁止在无阻塞时询问"下一步做什么";也禁止把"自动推进"误解为"跳过授权"。

**暂停挡板(仅三类,命中即停并输出状态报告,由人类裁决)**:

| 挡板 | 触发条件 | 处置 |
|:----:|:---------|:-----|
| **G1 产品方向冲突** | 架构方案与产品方向不一致 | 停,输出决策记录,等人类拍板 |
| **G2 架构变更** | 修复/开发暴露出需要架构级重构(超出本任务范围) | 停,拆为独立任务走完整流程,禁止混合 |
| **G3 Scope 扩展** | 任务范围扩大(新增需求/新功能混入) | 停,重新规划拆分,禁止吞并 |

另有一个**授权门(非暂停挡板)**:发布构建/发布产物必须有人类显式授权;
调试构建用于验证,无需授权。授权 ≠ 每次构建都要问,而是"发布动作必须授权"。

**快速修复 vs 架构重构分离(实证强制规则)**:同一问题同时有用户可见症状与深层架构缺陷时,
拆成两个阶段、两个决策记录 —— Phase 1 最小改动关闭症状(不做架构改动),Phase 2 单独排期做
重构。**禁止混在一次交付里。**

## 4. Bug 调试流程通用化

任何缺陷从报告到关闭走固定流程,步骤顺序不可跳:

```
归档 → 根因调查 → 架构评估 → 交叉验证 → Decision → 修复 → 测试 → 构建 → 用户实测
```

| 步骤 | 执行角色 | 产出 | 规则 |
|:-----|:---------|:-----|:-----|
| **归档** | 协调器 | 结构化缺陷报告(复现步骤/期望/实际/严重度) | 证据优先,禁止凭报告猜 |
| **根因调查** | 调试工程师 | 事件链追踪、根因结论 | 与架构评估**并行**(相互独立) |
| **架构评估** | 架构师 | 影响范围、修复方案约束 | 与根因调查并行 |
| **交叉验证** | 协调器 | 一致性判定 | 两者结论一致才前进;不一致则补查后重审 |
| **Decision** | 协调器 | 决策记录(问题/证据/根因/范围/决策/执行者) | **无决策记录不进入修复**(决策门) |
| **修复** | 开发工程师 | 代码修改 | 不得改变架构方案;快速修复与重构分离 |
| **测试** | 测试工程师 | 验证结果、回归状态 | 独立验证,禁止开发者自验(见 validation-model) |
| **构建** | 发布验证 | 调试构建产物 | 构建成功 |
| **用户实测** | 用户 | 验收结论 | 真实操作验证;自动测试通过 ≠ 已修复 |

**流程规则**:
- 根因调查与架构评估必须并行启动(各自独立,互不等待)。
- 交叉验证不一致时,重新派发一方或双方,直到结论一致,不允许"取平均"或跳过。
- 产品经理介入条件:修复改变用户可见行为(导航/布局/交互/功能);纯技术缺陷(编译错误、
  测试失败、性能)可跳过。拿不准时**宁可多派**,成本低且能拦截隐藏假设。
- 缺陷严重度分级:P0 崩溃/数据丢失 / P1 功能损坏 / P2 功能缺陷 / P3 体验问题。

## 5. Sprint 管理抽象

Sprint 是批量交付单元:一批任务(步骤)按依赖图组织,由引擎在一个周期内调度执行并统一验收。

### 5.1 Sprint 类型(实证强制分离)

| 类型 | 内容 | 禁止 |
|:-----|:-----|:-----|
| **Bug Fix Sprint** | 回归、损坏功能、体验缺陷 | 不得混入新功能任务 |
| **Feature Sprint** | 新能力、新界面 | 不得把 backlog 的纯修复任务带进来 |
| **RC/发布 Sprint** | 稳定性、全量测试清零、打包、文档 | 不得开新功能 |

混合类型 Sprint 一旦发现,立即拆分为两个独立计划。

### 5.2 Sprint 生命周期

```
规划 → 校验 → 调度 → 执行(循环:READY→RUNNING→VERIFYING→DONE/FAILED/BLOCKED)
     → 验收报告 → 回顾沉淀
```

| 环节 | 内容 |
|:-----|:-----|
| **规划** | 产出计划文档:任务清单,每任务含步骤 Schema 全字段(goal/文件范围/依赖/验证命令/验收标准) |
| **校验** | 计划通过 Schema 校验(引用 ID 存在、依赖可解析、验证命令合法)才允许执行 |
| **调度** | 引擎按依赖解析 READY 任务;迭代 1 派发无依赖任务,后续迭代派发依赖就绪任务 |
| **执行** | 每任务:委派 → 独立验证 → 通过标记 DONE / 失败按两次失败上限处理 / 阻塞上报 |
| **验收** | 逐条核对任务验收标准,产出验收报告 |
| **回顾** | 记录指标(first_attempt_success 等,见 validation-model)、沉淀新 pitfall、修补 Skill |

### 5.3 任务状态机

```
READY → RUNNING → VERIFYING → DONE
   │        │          └→ FAILED →(重试1)→ RUNNING
   │        └→ BLOCKED ←───────────────(第3次/挡板)
   └→ BLOCKED(依赖未就绪)
```

### 5.4 阶段衔接(跨 Sprint)

- **架构迁移/核心重构之后必须进入质量稳定期**:暂停下一个功能 Sprint,由用户在调试构建上
  实际操作(如 5–10 分钟)发现回归(光标/选区/剪贴板/快捷键等自动测试看不到的体验问题),
  修复循环,直到连续若干轮 0 新问题才恢复功能开发。
- **会话中断恢复**:按"状态恢复检查 → 确认事实 → 从中间态继续"恢复,禁止整任务重跑
  (见 agent-model 生命周期 Waiting 状态)。

## 6. 流程规则总表(KISS 收束)

| 规则 | 内容 |
|:-----|:-----|
| R1 | 任何任务映射到主干流程,专业阶段必须由注册角色执行 |
| R2 | 阶段完成自动推进;只有三挡板(G1/G2/G3)与发布授权可暂停 |
| R3 | 依赖未就绪不委派;文件范围重叠不并行;核心集成串行 |
| R4 | Bug 走固定九步流程;根因调查与架构评估并行、交叉验证一致后才决策 |
| R5 | 无决策记录不开发;无独立验证不宣布完成;无用户实测不宣布验收 |
| R6 | Bug Fix / Feature / RC 三类 Sprint 禁止混型 |
| R7 | 快速修复与架构重构分离,两个决策记录,禁止混合 |
