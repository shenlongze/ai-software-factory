## ★ 两条更正（我先前结论错了 —— 留档，别让下一个读的人被误导）

```
 更正1【会话唯一入口】我报过"核心第1条未做（要手工敲 12 条命令）" —— ✗ 错。
   实测: `factory chain "<一句话需求>" --project <P>` **就是**那个入口, 且它覆盖到拆解:
     ② 建会话 → ① 定位 → ③ 理解(8 条事实) → ④ PRD → ⑤ **自动生成产品定义/交互设计/架构设计**
     → ⑥ 拆解 → ⑦ 细拆(18 模块 → 85 叶)
   真跑证据（宠物寄养预约小程序, 新项目 P-9816c063, 一条命令）:
     conv-c1fb109eb1b6 · PRD-e19c7b620ff4 · PLAN-646511ccf9（18 域/85 叶, 粒度只剩 5/85）✓
   我的错因: 只读该模块 docstring（写着"缺产物时只在结果里提示, 不阻塞"）就下结论, **没读代码**
     —— 代码里 s5 是**自动补齐**三件制品（缺哪个补哪个）。教训: 自述与代码不符时以代码为准。

 更正2【分析环】我报过"分析环在 CLI 上没有对应命令" —— ✗ 不准确。
   实际: `chain` 的第 ⑤ 步就叫"分析产物"（自动生成 产品定义/交互设计/架构设计 三件）;
        独立命令层面则是 `product develop` / `product ux` / `arch design` 三条。
   ⇒ 准确说法: **没有一条叫"分析"的独立命令**, 但"分析环"有实现载体（chain ⑤ + 那三条命令）。

 ★ 遗留（真实缺口, 未修）: chain 止于"拆解 + 细拆"（候选态）, 到"叶在执行"还差
   【人工确认门 tasktree confirm】+【factory run】两步 —— 确认是产品设计上的人工环节（第 6 环"确认/修改"）,
   所以不是缺陷; 但若你要"一句话到叶在执行", 需要把 confirm 的确认动作也纳入一次调用（等你定）。
```

## 卡点（本次实测新增）

```
 卡点1（硬断点）需求理解静默降级 —— ★ 2026-09-21 已修（五步, 见下）
   症状: 一句写得非常明确的需求 ⇒ 抽到 0 条事实, 界面只说"我暂时无法可靠理解这句话与产品的关联" ⇒
        把人引向"换个说法"(错误方向) ✗
   根因: **写 key 的地方 ≠ 读 key 的地方** ——
        `factory provider add`（唯一给人配 key 的入口）把 key 写进 `~/.hermes/.env`（**Hermes 的地盘** ✗）,
        而解析链只认【进程环境变量】+ 一个指向**源码目录内**的 .env（死路）⇒ 解析结果空
        ⇒ fallback_order()=[] ⇒ selected_provider_id()=None ⇒ complete_text() 返回 None ⇒ 降级
   反证: 按声明方式把 key 放进环境后 —— 同一句话 5 条事实 ✓
   ★ 为什么长期没被发现: 执行面走【另一条 LLM 通道】(hermes runtime 自己读 ~/.hermes/.env) ⇒
     执行照跑、界面照绿 ⇒ 只有"从会话开始"才撞到
   ★ 归属问题（Founder 原话）: 「配置不应该在 AI Factory OS 自己的配置文件么，和 .hermes/.env 有什么关系」
     ⇒ 正解 = key 归 **factory 自己的** `~/.factory/.env`（不是 Hermes 的，也不是源码目录）

   【修法（2026-09-21 已落地）】
    ① `_write_env_key()`: 写 `~/.factory/.env`（600）—— 不再写 ~/.hermes/.env
    ② `_default_env_file()`: 指向 `~/.factory/.env`（原来指源码目录 = 死路）
    ③ `control_plane._env_layer()`: 与 ② 对齐（原来回落读 control_plane.py 自己所在目录的 .env）
    ④ 降级理由可见: `complete_text.LAST_REASON` 留痕 + `_degrade_clarify(reason=…)` 写进回复
       （实测输出: "…（原因: 没有可用的 provider —— 降级链为空（查 providers.json 的 api_key_ref
        对应的环境变量, 或 ~/.factory/.env 是否已配））"）
    ⑤ 迁移 + 成文规定: 现有 key 复制进 `~/.factory/.env`（600）; `docs/ssot/code-placement.md`
       补上"key 本体存 `~/.factory/.env`、写读必须同源"（原先只写了"只存 env: 引用", 没说存哪）
   【验证】干净 shell（进程里无该变量）: `fallback_order=['deepseek']` · `complete_text` 正常 ·
        `conversation understand` 抽出事实 ✓; 反向: 挪走 ~/.factory/.env ⇒ 链空 + 理由可见 ✓;
        守卫 "LLM key 归属" 13/13（反向验证红且指名"写读不同源, 就是那个 bug"）

 卡点2 `conversation locate` 需要把需求文本再传一遍（两个位置参数 conversation_id + text）
   实测: 只传 cid ⇒ argparse 报错; 传了才跑 ✓ ⇒ UX 上像"它没读会话", 与实际设计不符

 卡点3 8 环里的"分析环"在 CLI 上没有对应命令
   实测: `arch design` 要的是 product + ux_ui 两个制品（强校验, 缺则拒 ⇒ 行为正确 ✓）,
        而 `understand` 是"项目理解/阶段识别"（不产出 product/ux）
   ⇒ 环名 ↔ 命令 的对应关系无单一出处（产品文档说 8 环, 命令是 12 条）
   ★ 这正是"会话唯一入口"要解决的形态问题: 环序应由系统编排, 不该让人拼

 卡点4 执行体写文件但没提交（留脏工作区）
   实测: EXR-005 说"脚手架已落地…npm run check 全绿", 但仓库 **18 个未提交文件、main 分支 0 提交**
   （此前 EXR-002/003 的执行体是自提交的 ⇒ 行为不一致）
   ⇒ 与"超时留半成品"(第二次报告发现 8)同族: 执行结束时应有一致的收尾契约（提交 or 明确不提交）
```
