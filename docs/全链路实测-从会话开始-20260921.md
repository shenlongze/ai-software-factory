## 卡点（本次实测新增）

```
 卡点1（硬断点, 已定位根因）需求理解静默降级
   症状: 一句写得非常明确的需求 ⇒ 抽到 0 条事实, 界面只说"我暂时无法可靠理解这句话与产品的关联" ⇒
        把人引向"换个说法"(错误方向) ✗
   根因: providers.json 里 deepseek 的 api_key_ref = env:DEEPSEEK_API_KEY, 而【该变量不在 CLI 进程环境】
        ⇒ fallback_order() 为空 ⇒ selected_provider_id()=None ⇒ complete_text() 返回 None
        ⇒ interpreter 走 _degrade_clarify（诚实降级, 但**不说是哪种失败**）
   反证: 把 key 按声明方式放进环境后 —— 同一句话 **5 条事实** ✓
   ★ 为什么长期没被发现: 执行面走【另一条 LLM 通道】(hermes runtime 自己读 ~/.hermes/.env) ⇒
     执行照跑、界面照绿 ⇒ 只有"从会话开始"才撞到
   两个可修点: (a) 降级理由要可见（"LLM 不可用: env:DEEPSEEK_API_KEY 未解析"）
              (b) 让 CLI 能解析 providers.json 的 env: 引用（或启动时明确报"未配置"）

 卡点2 `conversation locate` 需要把需求文本再传一遍（两个位置参数 conversation_id + text）
   实测: 只传 cid ⇒ argparse 报错; 传了才跑 ✓ ⇒ UX 上像"它没读会话", 与实际设计不符

 卡点3 8 环里的"分析环"在 CLI 上没有对应命令
   实测: `arch design` 要的是 product + ux_ui 两个制品（强校验, 缺则拒 ⇒ 行为正确 ✓）,
        而 `understand` 是"项目理解/阶段识别"（不产出 product/ux）
   ⇒ 环名 ↔ 命令 的对应关系无单一出处（产品文档说 8 环, 命令是 12 条）
   ★ 这正是"会话唯一入口"要解决的形态问题: 环序应由系统编排, 不该让人拼

 卡点4 执行体写文件但没提交（留脏工作区）
   实测: EXR-005 说"脚手架已落地…npm run check 全绿", 但仓库 **18 个未提交文件、main 分支 0 提交**
   （此前 EXR-002/003 的执行体是自提交的 ⇒ 行为不一致）
   ⇒ 与"超时留半成品"(第二次报告发现 8)同族: 执行结束时应有一致的收尾契约（提交 or 明确不提交）
```

## 与"盘点式测试"的区别（为什么必须从会话开始）

```
 盘点式（我第二次做的）: 读已有会话/事实/设计/树/执行/指标 ⇒ 只能证明"之前留下的产物还在"
 从会话开始（本次）:     新项目 + 新会话 + 一句需求 ⇒ 沿途必然撞到【真实断点】——
                        本次一个硬断点（LLM key/静默降级）+ 三个口径问题, 全是盘点看不见的
```
