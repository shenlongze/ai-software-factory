## 已知嫌疑点（上一轮实测得出，这次专门验它）

1. **需求/设计制品从来没生成过** ⇒ 这轮必须走 `product develop` → `arch design`，看它是否真能出制品。
2. **拆解的引用校验**：`tasktree decompose` 会硬拦"项目内无 design 产物"—— 看它是否真的拦住；若拦住，
   说明上一棵树的引用是**绕过校验**塞进去的（要找出那条绕行路径）。
3. **执行状态语义**：停手/零改动被记成 `completed`；环境性失败被记成 `cancelled`（不可重试）。
4. **门禁只在文案里**：`tasktree show` 说"需 confirm 才进执行"，但 `run` 不拦候选态树。

## 结论（一轮实测下来）

- **通的环**：会话 · 需求（理解/PRD）· 架构设计 · 拆解 · 派工/优先级 · 执行（真出代码、真提交、可溯源到设计制品）· 备份。
- **断的环**：监控 · 运维的"如实反映"（卡点 1/5）—— 工厂在干活，但**看板/指标/状态看不到**。
- **不平的路**：卡点 2/3/4/6/7（各有明确证据与修法）。
- **关键收获**：制品链一旦真实存在（product → ux → design → 树引用），执行体能拿到权威依据并**按设计写代码**；
  上一轮的"断链 + 停手"就是制品从未生成的直接后果。
