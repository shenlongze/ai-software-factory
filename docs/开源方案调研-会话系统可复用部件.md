# 开源方案调研 — 会话系统可复用部件（全网扫描 GitHub / Gitee）

> 日期: 2026-08-28 | 背景: 上一轮确认"Agent Loop 已同款, 模型/基础设施是差距"。
> 本轮全网扫描（GitHub/Gitee/开源社区）找**现成解决方案**，按我们缺的能力分类：
> 动态工具发现 / 上下文管理 / Hooks / 权限沙箱 / 完整 Harness / 平台级。
> 结论先行: **没有"整个会话系统拿来即用"的方案（定位不同）; 但每个缺口部件都有可抄/可用的开源实现，最值得先落地的是 BM25 动态工具发现 + Hooks 事件层。**

---

## 1. 完整 Agent 运行时 / Harness（参考架构，不直接替换）

| 项目 | 语言/许可证 | 说明 | 对我们 |
|---|---|---|---|

| **OpenCode** (`anomalyco/opencode`) | TS / MIT | 开源编码 agent，140k+ stars；build/plan 双 agent、子 agent、TUI+Web；社区插件生态 | 借鉴其 plan(只读)/build(全权) 双模式 = 我们的权限模式化 |
| **OpenClaw** (`openclaw/openclaw`) | TS / MIT(核心) | 自托管 agent **网关(Gateway)**：多 agent 路由 + 75+ 工具注册表 + Skills + 子 agent + SQLite 任务控制面(审计/归属/状态) + Docker 沙箱 + Hooks 事件总线 + 语义记忆 | ⭐⭐ 与"AI 工厂 + 外部执行器"定位最接近；**gateway/任务控制面/审计/Hooks 设计值得深读**（TS 不能直接复用代码，但架构可抄） |

| 其他轻量 | Rust `kkagent` / Python `pi-agent` / `jcode` / `openharness` | 各类"开源版 Claude Code" | 参考实现，价值一般 |

## 2. 动态工具发现（ToolSearch）— 我们最缺、最优先

**问题**: 我们 18+ 个静态工具每次全量塞给 DeepSeek，弱模型选择压力大 → 直接贡献"所答非所问"。

| 方案 | 语言/许可证 | 做法 | 可用性 |
|---|---|---|---|
| **tool-search-oss** (`Ag3497120/tool-search-oss`) | Python / MIT | BM25 工具路由：`catalog_summary()`（~400 token 目录）+ `discover_tools()`（top-5 全 schema）；50 工具下 **top-1 96% / top-3 100%**，上下文减 82%，TTFT 2-3x，零依赖；自带 Python MCP server | ⭐⭐ **可直接借鉴/安装**（⚠️ 作者已归档 2026-08，只读；MIT 可 fork） |
| **Eino ToolSearch** (`cloudwego/eino` + eino-ext) | Go / Apache-2.0 | 中间件动态工具选择：注入 `tool_search` 元工具，首轮只给静态工具+搜索工具，命中后累积加入可见列表；3 种模式（中间件管理/模型原生/客户端代理） | ⭐ 抄"累积可见"机制（比一次 top-5 更稳），Go 实现转写 Python |
| **Anthropic Advanced Tool Use 官方模式** | 文章(通用) | "defereed loading" 模式：目录摘要 + 按需 discover（tool-search-oss 即其开源版） | 设计源头，必读 |
| minion TST / spring-ai-tool-search-tool | Python/Java | 同类 TST 实现 | 参考 |

## 7. 落地建议（按性价比）

| 优先级 | 做啥 | 依据 | 预估 |
|---|---|---|---|
| **P0** | **BM25 动态工具发现**：tool-search-oss 模式（catalog_summary + discover_tools top-5），或 Eino 式"搜索后累积可见" | 直接减弱模型工具选择压力，是"所答非所问"根因之一；零依赖、1-2 天 | 1-2 天 |
| **P0** | **Hooks 事件层**：PreToolUse/PostToolUse（deny+reason），挂审计/校验/敏感动作门 | Claude 事件模型照抄；一劳永逸给"监控/审计/治理"留口 | 1-2 天 |
| **P1** | **上下文分层 + 缓存意识**：静态系统前缀固定在前（缓存命中），动态放后；与 TopicLedger 合并 | SR2 分层架构 + Codex 前缀缓存 | 2-3 天 |
| **P1** | **权限模式化**：plan(只读)/acceptEdits(改文件)/auto 分类 | OpenCode build/plan + Claude permission_mode | 2-3 天 |
| **P1** | **系统级沙箱**：借鉴 OpenAI UnixLocalSandboxClient 给执行器 | 安全差距 | 中 |
| **P2** | 深读 **OpenClaw** gateway/任务控制面/审计，输出《外部执行器网关设计》 | 与"外部委派"定位最接近 | 研究型 |

## 8. 结论

- **没有整体拿来即用的"会话系统"**（Codex/Claude 模型绑定、OpenClaw/OpenCode 是 TS 且定位单 agent/IDE）。
- **每个缺口部件都有开源答案**，核心是：**动态工具发现（BM25） + Hooks 层 + 上下文分层/缓存 + 权限模式 + 沙箱**。
- 语言栈（Python）决定我们以"抄架构/转写"为主，唯一可 pip 直用的是 tool-search-oss（MIT，建议 fork 归档版）。
- 最优先落地 **P0 两项**（动态工具 + Hooks），直接提升会话"像 Codex/Claude"的体感。
